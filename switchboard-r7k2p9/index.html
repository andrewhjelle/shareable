0. What we're building · the requirements

Switchboard is a personal desktop chat app that fronts a fleet of models across three lanes: local models (Ollama), subscription models (Claude via a Max login, not per-token billing), and API-key models (supported as a lane even when unused). A router picks the model for each message automatically, informed by question difficulty, the machine's specs and current load, privacy, and budget state, but routing is fully transparent, never hidden. The examples below are the evidence base; each requirement names the example it draws from.

North stars

  • Take load off the user. Smart defaults everywhere, automatic routing, zero config to start a chat.
  • Simple and fast. The default view is calm; detail lives in a side drawer, not the main surface.
  • Progressive urgency. Indicators get louder as anything nears capacity (usage budget, VRAM, context). Quiet when healthy, prominent when critical.
  • Transparent, never hidden. Every answer shows which model produced it and why, at a glance. This is the core differentiator.

Design states to cover

Budget Comfortable / Moderate / Warning / Critical · model download in progress · GPU busy vs idle · drawer closed vs open vs auto-opened on alert · router escalating a hard question to Claude vs answering locally.

Aesthetic

Personal tool, so it can have character. Desired range: from calm-minimal (Jan) to something with more personality. Desktop-first, dark mode primary. Deliverable: a variety of distinct visual directions (at least 3), not one converged proposal.

1. The chat apps

Open WebUI web · self-hosted · the category leader

  • Sidebar has typed sections; folders paginate and sort; chats pin and search. The information architecture scales to hundreds of chats.
  • Model switchable mid-conversation; Compare toggle fans one prompt to two models, both answers labeled.
  • Per-chat variables: a small form (tone, audience) filled once and carried through the conversation and its forks.
  • /status panel shows context usage, queued messages, running tasks.
STEAL The hover preview card (find the right chat without opening it), model sizes printed in the picker rows, and the usage heatmap-by-model as an idea for our usage page's by-lane view.
STEAL Picker lives in the composer, not a distant toolbar: the decision point sits where you type. Our override chip does the same.

LM Studio desktop · the model-manager benchmark

  • The Discover tab is the signature: staff-picked models front and center, and every model and quantization carries a colored hardware-fit badge computed against YOUR detected GPU/RAM (green rocket = runs well) BEFORE you download. No official screenshot was fetchable; see the docs live.
  • Chat view: system-prompt panel + live sampling controls beside the thread; two chats side by side by dragging tabs.
  • The Bionic shot shows their agent-era layout: three panes with a real artifact viewer, and capacity surfaced in the composer.
STEAL Fit-before-download is the roster manager's core interaction. Our device profile adds the state LM Studio lacks: "fits when the GPU is idle" (overnight lane).
STEAL Context counter directly in the composer, exact and numeric.

Jan desktop · the minimalist

  • Hub groups each model's quantizations into Small / Balanced / Large with a Recommended tag and live VRAM/RAM estimates before download.
  • Drop a .gguf into the models folder and it appears in the picker: zero-friction bring-your-own-model.
  • Every conversation auto-saves as a named thread; local API server is first-class.
STEAL The overall calm: this is closest to the "simple and fast" north star. Also the Small/Balanced/Large + Recommended grouping for quants.

LibreChat web · the artifacts benchmark

  • Fullest preview pane in the category: React/HTML/SVG/Mermaid/Markdown, inline cards that expand, fullscreen, SVG/PNG export.
  • contextUsage / contextCost config: a real-time context and cost gauge inside the conversation UI. The clearest live meter of any app here.
  • Presets save endpoint+model+parameter combos next to the picker.
STEAL Model identity printed on every answer (avatar + name), response versioning, and the artifacts pane behavior (expand, fullscreen, export).
AVOID Their documented layout bug: Parameters and Artifacts share one right-panel slot, and hiding one hides both. Our rule: independent surfaces, independent close controls.

Msty desktop · the split-view benchmark

  • "Add Split Chat" divides the window per model; one prompt fans to all panes in real time, labeled. Local and cloud models mix freely in one view.
  • Now a 4-product suite (Studio chat / Go agents / Nexus gateway+usage / Stack knowledge): the same chat-vs-governance separation our spec makes.
STEAL The split mechanic IS our "multiple windows" requirement, and doubles as a live mini-gauntlet: same prompt, local vs Fable, side by side. Also note their circular fit gauge on model cards.

Chatbox + AnythingLLM the two ideas worth keeping

  • Chatbox: provider-first setup with a "Check" button that verifies the connection before you can create a chat; personas as the sidebar's organizing unit.
  • AnythingLLM: Workspace = isolation boundary. Documents, vectors, conversations, AND the model binding scoped together; one workspace local-only, another cloud.
STEAL The connection Check button for onboarding (verify Ollama + claude CLI reachable), and workspace-style isolation as the mental model behind our Private chats: privacy is a property of the chat, not a per-message checkbox.

2. Routing · who shows their work, who hides it

OpenRouter, RouteLLM, and the ChatGPT lesson

  • OpenRouter auto-router: a classifier assigns ~30 task types, then ranks models by 7-day community share-of-spend within your cost tier. The reasoning is hidden; you learn which model served you only post-hoc from the response metadata. Sticky session_id keeps a conversation on one model.
  • RouteLLM (LMSYS): no rule taxonomy at all; routing is learned from human preference data, and the whole cost/quality tradeoff collapses to one calibrated number: "route N% to the strong model."
  • ChatGPT GPT-5 "auto": shipped as one unified system with a hidden real-time router. Users could not tell which model answered; it became a trust crisis within days, and OpenAI restored the manual picker. The transparency existed in the System Card, not the UI, and that gap was the whole problem. GitHub Copilot's hover-to-see-model is what forum users keep asking every tool for.
STEAL The drill-down dashboard (any number opens the requests behind it), sticky sessions, and RouteLLM's single-knob calibration as the mechanism our budget state turns.
AVOID Hidden routing. Automatic is fine; invisible is not. This is the entire case for our per-answer badge row (model · reason · latency · left-machine), which nobody surveyed ships.

3. Quota pacing · the dial already half-exists

cc-budget, the tracker ecosystem, LiteLLM

  • cc-budget (Claude Code statusline plugin) already renders the owner's mental math for the exact same quota: pace marker, direction arrow, color escalation (amber 70% / red 90%), reset countdown, progressive disclosure.
  • The Max-tracker ecosystem (ClaudeMeter, ClaudeUsageBar, Claude Tracker, ccusage) converges on: session % + weekly % + exact reset time + threshold alerts, living in a menu bar or status line. Nobody puts it IN the chat surface.
  • LiteLLM proxy dashboard handles the dollar side: per-key/team budgets, soft alert at a threshold, max alert at 80%.
  • Research found no product anywhere with a rolling daily allowance that carries unused budget forward and tightens after overspend.
STEAL The cc-budget visual grammar wholesale; it is proven on this exact quota.
(ours) Our two additions are the novel part: the allowance rolls over adaptively, and the budget state FEEDS the router instead of just displaying. Nobody surveyed closes that loop.

4. Deferred work · naming the trigger

Render farms and ML schedulers agree: AWS Deadline paints Pending jobs orange with the reason they wait; Weights & Biases' launch-queue plot exists to spot idle-queue windows and backfill them with preemptible low-priority jobs, which is exactly our overnight lane; SLURM's submitted → queued → running → done is the standard vocabulary. No screenshots fetched (CLI-first tools); W&B docs, Deadline docs.

STEAL Queue rows always name their trigger ("waiting for idle GPU"), and when the machine goes idle the queue announces what it is about to start, so an overnight run is never a surprise.
