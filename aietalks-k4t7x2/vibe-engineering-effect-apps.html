Context engineeringCoding agents

If you only read one thing

  • Arnaldi's core technique is cloning a library's actual source repo into the project directory rather than relying on MCP docs servers, because coding agents are trained to focus on their own code and tend to skip node_modules or gitignored files.
  • He argues a 1-million-token context window isn't necessarily an advantage because pushing in more information risks confusing the model, and in his team's own experiments, cutting a coding agent down to a single 'execute' tool call improved results.
  • Practical guardrails he uses: strict lint rules that ban specific escape hatches like 'as never as X' type casting, running small tasks in an exit-and-loop bash script instead of one long session, and writing prompts differently for GPT (no all-caps, it gets 'scared') versus Claude models.
01Why clone the dependency's repo instead of using docs or MCP

Arnaldi explains that coding models have been post-trained primarily to read and modify code in the project they're working on, not to consume external documentation or an MCP server they've never seen. He found that placing a library's source in node_modules gets under-weighted by the model, and that gitignored directories are skipped entirely by some tools like Cursor's indexer, so the only reliable way he's found to get good results with an unfamiliar library, in any language, is to clone its actual repository into the project.

“eight months ago I was thinking what if I just give the model access to code that means if I want to use effect I'm going to add the effect repository in my directory.”

02Context windows: bigger isn't automatically better

Arnaldi argues that a 1-million-token context window is not necessarily a good idea, because pushing more information into the context increases the chance of confusing the model, particularly when the session is being used for multiple unrelated things at once.

“good chance you're going to confuse the model, which is why a 1 million context window is not necessarily helpful, especially if you're doing multiple things in the same context.”

▶ watch at 09:08
03Guardrails: linters and banned patterns steer the agent

He treats a linter as an essential piece of a 'back pressure loop' that pushes the model toward correct patterns. As one example, he describes banning the model from writing 'as unknown as X' type casts, only to find the model discovered it could do the same thing with 'as never as X' since never is a bottom type, requiring him to ban 'as' more broadly.

“one thing we have not set it up yet is a llinter uh llinter is going to be an essential piece of the back pressure loop that helps the model drive in the right direction.”

04Model choices: open weights, tool count, and prompting style

Arnaldi says open-weight models lag frontier closed models by roughly three to six months. In his team's own experiments, reducing the number of tools available to a coding agent, down to a single 'execute' call in one test, improved outcomes. He also notes that prompting style has to differ by model family: he avoids writing in all caps because GPT models get 'scared' and become passive when shouted at, unlike Claude models.

“open weights models are kind of lagging behind by three to six months compared to frontier models.”

05Working loop: small tasks, exit, repeat

Rather than reusing one long session, which degrades as the context window fills with earlier, less relevant information, Arnaldi runs a simple bash script that tells the model to pick up one small task, implement it, and exit, looping that repeatedly instead of manually managing context resets.

“I use a very simple bash script that tells the model pick up a small task implement the small task and then exit and I run that in a loop.”
