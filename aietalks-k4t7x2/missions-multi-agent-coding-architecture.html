The Multi-Agent Architecture That Actually Ships

SpeakerLuke Alvoeiro · Factory Watchyoutu.be/ow1we5PzK-o · 18 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. Quotes are verbatim from the talk transcript with the time they were said.
Blueprint · full operating modelAgentic engineeringCoding agentsContext engineering

Factory missions runs multi-day coding tasks through an orchestrator, workers, and validators with a validation contract written before code and serial-execution guarantees.

If you only read one thing

  • Factory's missions system runs multi-day coding tasks using three roles (orchestrator, workers, validators) that combine delegation, creator-verifier, broadcast, and negotiation patterns.
  • A validation contract is written during planning, before any code, so correctness is defined independently of the implementation instead of by tests shaped after the fact.
  • Running features serially (not in parallel) cut error rates versus parallel multi-agent execution, because parallel agents conflicted and duplicated work.

Why this talk is a blueprint, not a take (ours)

Scope: Factory's missions system: the orchestrator/worker/validator architecture, the validation-contract mechanism, and the serial-execution rule that let a coding agent run unsupervised for up to 16 days.

A three-role multi-agent structure (orchestrator plans and writes a validation contract before code exists, workers implement one feature at a time with clean context, two validators check behavior as well as code) plus a structured-handoff mechanism that keeps context from being lost across a multi-day run. Reported production numbers from a sample build show 60% of time and tokens on implementation and a final state of 50% test-to-code lines covering 90% of the codebase.

Prerequisites the talk implies:

  • An orchestrator capable of decomposing a goal into features, milestones, and a validation contract before any implementation starts
  • A workflow where each worker gets clean context per feature and commits via Git so state passes cleanly to the next worker
  • Two independent validators, one running tests/lint/type-check and code review, one driving the live application through computer use
  • A mechanism (Factory's is a structured handoff document) that forces agents to record what was and was not completed rather than just declaring success
  • Willingness to run features serially rather than in parallel, accepting lower raw throughput for a lower error rate

What the talk does not say:

  • Cost figures for a multi-day mission beyond the general mention of prompt caching to offset price
  • How the hundreds of assertions in a validation contract are authored or reviewed for correctness themselves
  • Failure or abandonment rate: how often a mission fails to reach a working state versus the 16-day success example shown
  • Team size or roles needed to operate missions day to day, versus the one human who scopes and approves the plan
  • How model selection per role (the "droid whispering" practice) is actually decided, beyond being customizable per project

If you were to replicate one thing first: Start by writing the validation contract during planning, before any code exists, since the talk credits that ordering as the reason validation catches real bugs instead of confirming the implementation's own decisions.

03Validation contracts, not after-the-fact tests, prevent drift

Validation contracts, not after-the-fact tests, prevent drift

  • The orchestrator writes a validation contract during planning that defines what "done" means before any code exists, because tests written after implementation tend to confirm the code's own decisions rather than catch bugs.
  • Two validators check each milestone: a scrutiny validator that runs tests/lint/type-check and spawns code-review agents, and a user-testing validator that drives the live application.

04Structured handoffs and serial execution keep long runs on track

Structured handoffs and serial execution keep long runs on track

  • Workers end each task with a structured handoff describing what was completed, what was left undone, and which commands were run, rather than just declaring completion.
  • The team tried running agents in parallel for throughput but found agents conflicted and duplicated work, so missions runs features serially with parallelism only inside read-only steps; the longest mission so far ran 16 days, with a belief runs of 30 days are possible.
