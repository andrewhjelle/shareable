The Multi-Agent Architecture That Actually Ships

SpeakerLuke Alvoeiro · Factory Watchyoutu.be/ow1we5PzK-o
Agentic engineeringCoding agentsContext engineering

If you only read one thing

  • Factory's missions system runs multi-day coding tasks using three roles (orchestrator, workers, validators) that combine delegation, creator-verifier, broadcast, and negotiation patterns.
  • A validation contract is written during planning, before any code, so correctness is defined independently of the implementation instead of by tests shaped after the fact.
  • Running features serially (not in parallel) cut error rates versus parallel multi-agent execution, because parallel agents conflicted and duplicated work.
01The bottleneck is attention, not intelligence

The talk opens with a claim that software engineering today is bottlenecked by human attention rather than model intelligence, since engineers can only supervise and review a few tasks at a time regardless of backlog size. Missions is framed as a system where a human scopes a goal and approves a plan, then the system executes for hours or days.

“The bottleneck in software engineering nowadays is not intelligence. It's now limited by human attention.”

▶ watch at 01:01
02Five building blocks, missions uses four

The speaker proposes a taxonomy of five frontier multi-agent communication patterns: delegation, creator-verifier, direct communication, negotiation, and broadcast. Missions combines four of them (delegation, creator-verifier, broadcast, negotiation) into a three-role architecture of orchestrator, workers, and validators.

“This is where one agent spawns another agent and the parent agent may say go figure out the database schema and then gets a response back.”

▶ watch at 02:04
03Validation contracts, not after-the-fact tests, prevent drift

The orchestrator writes a validation contract during planning that defines what "done" means before any code exists, because tests written after implementation tend to confirm the code's own decisions rather than catch bugs. Two validators check each milestone: a scrutiny validator that runs tests/lint/type-check and spawns code-review agents, and a user-testing validator that drives the live application.

“that validation contract defines what done sort of means before any coding is done”

▶ watch at 04:40

“Tests written after implementation don't catch bugs. They confirm decisions.”

▶ watch at 06:11

“critically it spawns dedicated code review agents for each completed feature within the milestone”

04Structured handoffs and serial execution keep long runs on track

Workers end each task with a structured handoff describing what was completed, what was left undone, and which commands were run, rather than just declaring completion. The team tried running agents in parallel for throughput but found agents conflicted and duplicated work, so missions runs features serially with parallelism only inside read-only steps; the longest mission so far ran 16 days, with a belief runs of 30 days are possible.

“it fills out a structured handoff detailing what was completed, what was left undone, what commands were run throughout that that agent loop”

05Production numbers from a sample build

On an example project (a Slack clone), 60% of both wall-clock time and token usage went to implementation, and by the end 50% of lines of code were tests, with 90% of code covered by those tests.

“60% of our time is spent on implementation, and 60% of our tokens as well.”
