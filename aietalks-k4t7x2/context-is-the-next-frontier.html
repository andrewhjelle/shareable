Building Agents Is Trivial Now, Context Is the Next Frontier

SpeakerJeff Ng · Unblocked Watchyoutu.be/HvMyYLTfvhg
Context engineeringAgentic engineeringMemory

If you only read one thing

  • Building an agent now takes far less engineering effort than 6 months ago, when it required a team and roughly a quarter, because cloud primitives and frameworks absorbed checkpointing, sandboxing, and observability.
  • In a live example, an agent recommended re-enabling async dispatch without knowing that exact change had caused an outage days earlier and had been deliberately disabled -- because it lacked the Slack thread and postmortem a human teammate would have known.
  • Connecting a context engine that reconciles and ranks information across docs, code, tickets, and Slack changed the same agent's recommendation from repeating the outage to avoiding it; the talk frames this as distinct from MCP, which grants access to raw sources but leaves reconciliation to the agent.
01Agent-building overhead has collapsed

The speaker says building an agent 6 months prior required a team's effort and roughly a quarter of work, because an agent is more than models and tools -- it needs checkpointing, sandboxing, and observability to run as a production service. He credits cloud infrastructure providers and frameworks with absorbing that complexity, to the point that defining an agent now mainly means choosing a model, writing instructions, and specifying tools and a sandbox location.

02The infrastructure work never improved the agent itself

He lists checkpoint/state persistence and sandbox isolation as necessary but non-differentiating: without durability, a crash can cause message history and tool-call state to be lost, forcing an expensive restart. He characterizes all of this category of work -- state persistence, sandboxing, observability -- as a tax paid to get an agent running, not something that makes the agent more capable.

“Crashing without durability can actually lead to a lot of state loss.”

▶ watch at 01:02

“They're all taxes one has to pay in order to get an agent out there to play the game.”

▶ watch at 02:38
03A live demo where missing context produced a wrong recommendation

Using a Linear issue-enrichment agent built on his own codebase, he shows it recommending re-enabling async dispatch to fix a latency regression. He then reveals this exact setting had caused an outage days earlier and been explicitly disabled by a support engineer -- context that lived in a Slack discussion and a postmortem ticket the agent never had access to.

“This had actually caused an outage a few days ago in one of our uh support engineers had explicitly disabled this uh before this ticket was uh shown.”

▶ watch at 05:44
04Context engine vs. MCP

He contrasts a context engine -- which reconciles, ranks, and scopes information across connected sources before handing the agent a synthesized understanding -- with MCP, which he says provides access but not understanding, leaving the agent to sort through raw, potentially conflicting results. Re-running the same demo with the context engine wired in, it surfaces the relevant postmortem and Slack conversation, and the agent's recommendation changes from repeating the outage to avoiding it.

“MCP is great at access, but access isn't understanding. An MCP hands the agent the raw results, and you know, you're now dependent on that agent to actually decide what to believe in.”

▶ watch at 09:52

“it's found the relevant Linear postmortem, as well as a Slack conversation where we've had the entire discussion between the engineering teams”

▶ watch at 10:54
05Closing framing

He closes by summarizing the talk's thesis in a single line about where the remaining gap lies for agents operating without a human in the loop.

“I think this quote encapsulates what we're trying to solve at Unblocked. The gap isn't intelligence, it's context.”

Commentary (ours)

The MCP-vs-context-engine framing is a vendor pitch (he works at Unblocked, which sells this layer), so the comparison should be read as directional rather than neutral -- the underlying observation that raw multi-source access still leaves conflict resolution to the agent seems worth testing against a team's own MCP setup rather than taken on faith (ours).
