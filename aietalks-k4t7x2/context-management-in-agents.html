01The vicious loop of building Alex on Alex

The vicious loop of building Alex on Alex

  • Arize built its AI agent Alex to operate on its own observability trace/span data, but doing so created a loop where growing span data hit a context limit, Alex failed, more data got added on retry, and it failed again -- meaning the system analyzing the data was constrained by that same data.

“Alex would run on our our traces span data. The spans would grow, there would be too much data, we'd hit a context limit, Alex would fail”

said at 04:06
02Truncation and summarization both failed

Truncation and summarization both failed

  • The team's first fix was naive truncation -- keeping only the first 100 characters of context and dropping the rest -- which worked for simple cases but caused Alex to forget everything, making follow-up questions read as new conversations.
  • Summarizing all context into fewer tokens looked like the obvious next step but proved too inconsistent, since the LLM had no principled control over what was important.

“we started off just taking the first 100 characters, and then we just dropped the rest. Pretty pretty naive. And it worked until it didn't”

said at 05:08

“that really sounded like the obvious solution, but it was too inconsistent. There was no control over what was important”

said at 06:10
03Smart truncation memory: what actually works

Smart truncation memory: what actually works

  • The approach Alex uses today keeps the first 100 characters and the last 100 characters of context, truncates the middle, and stores it so the agent can retrieve it if needed -- a combination of truncation and memory storage the team says has needed no changes in months.

“we take the beginning still 100 characters. We also take 100 off of the tail”

said at 06:40
04Sub-agents to offload heavy data

Sub-agents to offload heavy data

  • For data-intensive tasks like searching across hundreds of spans in a trace, the team concluded not all context belongs in the main agent, and moved heavy search/data work into sub-agents so the main conversation keeps only chat history and light context.
  • Long-session evals -- loading 10 turns and testing performance on the 11th -- surfaced failures that were previously invisible until a user reported them.

“heavy data, search all in one context. This was all handled in one agent. And then after basically what we have is these this main agent plus a sub-agent”

said at 10:15

“what we end up doing is we load 10 turns and then we test the 11th to understand how the context is doing”

said at 08:42
05What's still unresolved

What's still unresolved

  • Conversation length has grown from under 10 turns per session to regularly 20+ turns as users navigate across pages within one chat, and Arize still lacks true long-term memory across sessions.
  • The team's closing takeaway is that agents fail because of context, not prompts.

“when we started, I was seeing like less than 10 turns per conversation with Alex, and now I'm seeing folks really go, you know, push the limits up to like 20 plus”

said at 11:47

“agents don't fail because of prompts, they fail because of context”

said at 13:52

Commentary (ours)

The talk frames context management as a product/UX problem rather than purely an engineering one, but the actual fix described (head/tail truncation + memory store) is fairly mechanical; the more interesting open question -- what a 'principled context budget' looks like beyond eval-driven heuristics -- is flagged but not answered (ours).
