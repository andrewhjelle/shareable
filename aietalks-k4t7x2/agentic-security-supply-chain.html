Agentic Security: Permissions, Provenance, and the Agent Supply Chain

Blueprint · full operating modelSecurityCoding agentsAgentic engineering

Steve Yegge lays out a full agentic security stack: separate security review pass, deterministic scanners as tools, slopsquatting/AI-voice-scam threat categories, and a Snyk-plus-Chainguard workflow the agent calls into.

If you only read one thing

  • A bank's chief security architect pointed out that shipping code 10x faster at a constant defect rate means the vulnerability surface grows 10x, and Yegge notes security bugs don't lose urgency over time the way other bugs do (c1, c3).
  • Running Snyk against his own codebase after his coding agent's self-reported 'hardening pass' surfaced 241 vulnerabilities the agent had missed, which is why Yegge recommends giving agents security as a separate pass and routing it through tools like Snyk and Chainguard rather than asking the model to write and check its own secure code (c4, c5, c6, c7).
  • Five Eyes says open-source models will match frontier attack capability within months, not years, roughly six months by audience estimate, arriving alongside new personal-level risks like AI-cloned-voice family scams (c8, c9, c10).

Why this talk is a blueprint, not a take (ours)

Scope: A practitioner's framework, not a shipped product: how to harden an AI-heavy codebase and its agent workflows against the attack surface AI coding introduces, summarized in the speaker's own closing slide as four moves: govern, trust inputs, scan, monitor.

An argument for treating security as its own dedicated review pass, ideally first and last, rather than bundling it with correctness, routed through deterministic scanners (Snyk for code and dependencies, Chainguard for vetted upstream images) that the agent calls as tools, plus a warning that agent permissions and autonomous action are the next, largely unsolved, front.

Prerequisites the talk implies:

  • A scanner (e.g. Snyk) and a vetted-image supply chain (e.g. Chainguard) wired into the agent's toolset, not just run manually after the fact
  • A workflow that gives the agent one task at a time, since security and correctness bundled into one pass degrade both
  • A policy for what credentials and permissions each autonomous or always-on agent actually needs, reviewed the way service-account access would be
  • Willingness to run scanners against agent-reported 'complete' work rather than trusting the agent's own self-assessment

What the talk does not say:

  • The core evidence is one codebase and one live audience poll, not a benchmark; the deck's own slide (7 HIGH severity) and the spoken number (241 vulnerabilities) don't match, so treat the counts as illustrative
  • No worked example for the agent-permissions and autonomous-action problem the talk flags as unsolved, beyond adversarial supervisor agents as a direction
  • No detail on false-positive rates, scanner cost, or how much the Snyk/Chainguard tool calls add to agent token spend
  • No treatment of prompt injection despite being asked about it directly; the speaker calls it an open education problem with no good answers yet

If you were to replicate one thing first: Run an existing scanner (Snyk or similar) against a codebase your agent has already declared 'hardened,' before adding any new tooling, to see how large your own agent's self-review gap actually is.

Slopsquatting: hallucinated package names become real attacks

  • Yegge describes slopsquatting, where an LLM hallucinates a plausible-sounding package name and an attacker has already published a malicious package under that exact name.
  • The downloaded package builds, runs, and passes tests while containing a backdoor, making it hard to detect through normal review.

“it builds and it runs, and the tests pass, and it looks right, but what it downloaded was a backdoor”

Security needs its own pass, not a shared one

  • After his coding agent reported a completed security hardening pass on his own 30-year game project, running Snyk against the same codebase turned up 241 vulnerabilities the agent had missed.
  • Yegge generalizes this into a rule: give agents one task at a time, since asking for security and correctness together produces a half-finished job on both, so run security as its own dedicated review pass, ideally first and last.

Turn scanners into tools your agent calls

  • Yegge recommends adding scanners like Snyk and Chainguard directly into the agent's workflow as callable tools rather than relying on the model's own judgment, framing this as giving the agent's cognition an offload path it will use because it saves tokens.
  • He notes this only covers code-level risk and flags agent permissions and autonomous action as a related but separate open problem.
