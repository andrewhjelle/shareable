Agentic Security: Permissions, Provenance, and the Agent Supply Chain

SpeakerSteve Yegge · Gas Town Watchyoutu.be/yWS0udrIOc8
SecurityCoding agentsAgentic engineering

If you only read one thing

  • A bank's chief security architect pointed out that shipping code 10x faster at a constant defect rate means the vulnerability surface grows 10x, and Yegge notes security bugs don't lose urgency over time the way other bugs do (c1, c3).
  • Running Snyk against his own codebase after his coding agent's self-reported 'hardening pass' surfaced 241 vulnerabilities the agent had missed, which is why Yegge recommends giving agents security as a separate pass and routing it through tools like Snyk and Chainguard rather than asking the model to write and check its own secure code (c4, c5, c6, c7).
  • Five Eyes says open-source models will match frontier attack capability within months, not years, roughly six months by audience estimate, arriving alongside new personal-level risks like AI-cloned-voice family scams (c8, c9, c10).
01Faster shipping raises the defect surface, and security bugs don't decay

Yegge recounts a bank security architect's observation that shipping code 10x faster at a constant defect rate implies a 10x larger vulnerability surface. He contrasts this with how most bug classes lose urgency the longer they sit unfixed, arguing security bugs instead compound over time rather than fading in importance.

“that the defects surface goes up by 10x”

“that works for all classes of bugs except for security. There's no half-life on it biting you”

02Slopsquatting: hallucinated package names become real attacks

Yegge describes slopsquatting, where an LLM hallucinates a plausible-sounding package name and an attacker has already published a malicious package under that exact name. The downloaded package builds, runs, and passes tests while containing a backdoor, making it hard to detect through normal review.

“it builds and it runs, and the tests pass, and it looks right, but what it downloaded was a backdoor”

▶ watch at 03:42
03Security needs its own pass, not a shared one

After his coding agent reported a completed security hardening pass on his own 30-year game project, running Snyk against the same codebase turned up 241 vulnerabilities the agent had missed. Yegge generalizes this into a rule: give agents one task at a time, since asking for security and correctness together produces a half-finished job on both, so run security as its own dedicated review pass, ideally first and last.

“it found 241 vulnerabilities, right? Just a ton that Fable hadn't even thought to look for”

▶ watch at 07:52

“When you do things with LLMs, often you have to get them to do up to four to five reviews of the work that they did before it's like actually ready to ship”

▶ watch at 08:22

“you can't give them security at the same time as you give them correctness. They'll do a half-ass job of both”

▶ watch at 08:53
04Turn scanners into tools your agent calls

Yegge recommends adding scanners like Snyk and Chainguard directly into the agent's workflow as callable tools rather than relying on the model's own judgment, framing this as giving the agent's cognition an offload path it will use because it saves tokens. He notes this only covers code-level risk and flags agent permissions and autonomous action as a related but separate open problem.

“Give them sneak. Give them chain guard. And I still think there's a missing piece in this picture”

▶ watch at 09:54
05The gap to frontier attack capability is closing fast

Yegge cites a Five Eyes warning that it is now months, not years, before open-source models match frontier models' hacking capability, with his live audience polling landing around six months. He pairs this with a warning that AI-cloned voices are close to enabling convincing family-emergency scams, recommending people set up code words with family in person.

“They just announced that it is now months, not years, until it starts happening”

“And Mythos is real real good at hacking your systems”

Commentary (ours)

Yegge's numbers are anecdotal (one codebase, one live audience poll) rather than benchmarked, which is a real contrast with Nair's Snyk-benchmark talk in the same track; treat the '241 vulnerabilities' and '~6 months' figures as illustrative rather than measured. (ours)
