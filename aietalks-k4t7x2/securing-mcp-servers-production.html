Gives MCP server builders a concrete checklist (tool consolidation, schema-constrained inputs, stdio-vs-HTTP transport limits, CIMD over DCR for auth) to run before exposing a server to untrusted agents, backed by a load-test number show...

If you only read one thing

  • Every MCP tool description is a prompt-injection surface, and agent retries broadcast the full conversation history (including prior tool-call data) over the wire with each round trip (c1, c2).
  • Recommends consolidating fine-grained API calls into fewer, coarse-grained, single-outcome tools to shrink the attack surface, plus constraining input schemas and stripping tool responses to only what's needed (c3).
  • Long-lived, unscoped API keys still power more than 50% of MCP servers and stdio transport falls over under concurrency (20 of 22 requests failed at just 20 simultaneous connections in Lenses' own load test); the field is moving to OAuth 2.1 with CIMD, the preferred client-registration approach since November 2025, over the more phishing-prone DCR (c4, c5, c6, c7).

01Why most MCP servers aren't secure by design
Slide at 02:30 · click any slide to enlarge · 5 more from this section below

Why most MCP servers aren't secure by design

  • Building on a framing from Jeremy Lowin (creator of FastMCP) that agents differ from humans in discovery, iteration, and context, the talk argues each difference casts a 'security shadow': agents re-enumerate every tool description on every connection, making descriptions a tool-poisoning surface, and agent retries resend full conversation history, turning a poorly scoped server into a data-leakage channel.

“Attackers can embed hidden instructions inside descriptions that are invisible in the UI, but the model will follow them without question.”

said at 02:36

“An agent iterating over a poorly scoped MCP server is broadcasting your data with every retry.”

02Five design principles that double as security controls
Slide at 05:00 · click any slide to enlarge · 8 more from this section below

Five design principles that double as security controls

  • The talk presents five product-engineering practices for MCP servers that also close OWASP MCP Top 10 gaps: shrink the attack surface by consolidating fine-grained operations into coarse-grained, single-outcome tools; constrain inputs at the schema level; treat tool documentation as a defensive layer against tool poisoning; return only the minimum data an agent needs; and scope permissions at the tool/resource level rather than the session.

“Don't give the agent access to delete users when all it needs is to check an order.”

said at 05:14
03Stdio works for one developer, not for production
Slide at 09:30 · click any slide to enlarge · 8 more from this section below

Stdio works for one developer, not for production

  • Standard IO transport is a comfortable single-user, single-process, no-auth 'walled garden,' but has no gradual on-ramp to production, which requires the streamable HTTP transport plus OAuth, token management, CORS, TLS, and rate limiting all at once.
  • A load test on stdio under just 20 simultaneous connections failed 20 of 22 requests.

“20 out of 22 requests failed with just 20 simultaneous connections.”

said at 09:25
04From static API keys to OAuth 2.1 and CIMD
Slide at 12:40 · click any slide to enlarge · 8 more from this section below

From static API keys to OAuth 2.1 and CIMD

  • Long-lived, unscoped API keys stored in config files (still more than half of MCP servers today) create confused-deputy risk and are hard to revoke individually.
  • Dynamic Client Registration (DCR) solved self-registration for MCP's unbounded client/server pairing but is vulnerable to phishing since anyone can hit the register endpoint; Client ID Metadata Documents (CIMD), where the client exposes its ID on a public URL instead, has been the preferred approach since November 2025.

“It still represents more than 50% of the MCP servers out there.”

said at 13:04

“DCR is vulnerable to phishing attacks because it doesn't provide a reliable way to verify client identities.”

said at 19:19

“CIMD is a leap forward, and it is the preferred approach since November 2025.”

said at 22:29
05Enterprise-grade extras beyond auth
Slide at 22:50 · click any slide to enlarge · 4 more from this section below

Enterprise-grade extras beyond auth

  • Beyond OAuth scopes, true enterprise-grade access needs role-based permissions scoped to individual tools and resources (not just the session), data masking of PII fields like email, phone, and national insurance numbers before the agent ever sees them, full interaction logging for compliance, and end-to-end request tracing.

“agents should never be exposed to data that they have no business handling”

said at 22:59

Commentary (ours)

(ours) The talk treats design and security as inseparable ('a badly designed MCP server is also a badly secured one'), which reframes OAuth/transport hardening as necessary but not sufficient — the five design principles are presented as the layer that has to come first, before any auth work.
