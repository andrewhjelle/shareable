A Piece of Pi: Embedding The OpenClaw Coding Agent In Your Product

SpeakerMatthias Luebken · Tavon Watchyoutu.be/vAIDdLKB6-w · 20 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. Quotes are verbatim from the talk transcript with the time they were said.

Lays out a concrete architecture for embedding a coding-agent SDK (Pi, which OpenClaw is built on) inside a real product instead of shipping a chat UI: per-customer agent sessions, MD-file context injection, and CLI-first tool design

If you only read one thing

  • An agent is an LLM that runs tools in a loop; a coding agent is the same loop plus a shell and runtime, and OpenClaw is built directly on Pi's core agent, coding-agent, and session packages.
  • An OpenClaw instance that appeared to "learn" to handle a voice message by calling ffmpeg wasn't learning anything: it created and used a new tool call on the fly, a pattern any product can replicate.
  • Luebken's production pattern for embedding an agent in a product: one agent per customer, driven by a general "agent MD" harness plus a "customer MD" context file, feeding output back into the user's email inbox as drafts.

01What an agent and a coding agent are

What an agent and a coding agent are

  • Luebken defines an agent simply as an LLM that runs tools in a loop against some goal and context.
  • A coding agent is the same core loop with a shell and runtime added, which is what lets it execute commands rather than just call APIs.
  • He frames Pi as the minimal core SDK and notes OpenClaw is built on top of Pi's core agent, coding-agent, and session packages rather than being a separate implementation.

02The ffmpeg example: it looks like learning, but it's a tool call

The ffmpeg example: it looks like learning, but it's a tool call

  • He recounts an example where someone sent a voice message to an OpenClaw instance that had no built-in handling for voice messages, and the agent created and used a new tool -- ffmpeg on the local machine -- to process it.
  • From the outside this looks like the agent learning a new skill; Luebken's point is that under the hood it's just another tool call available to the agent, which is what makes the pattern replicable rather than mysterious.

03Design pattern: make it easy for the agent

Design pattern: make it easy for the agent

  • Luebken cites an architectural pattern he and a colleague converged on: build the surrounding system so the coding agent's job is easy, rather than building complex scaffolding around it.
  • He points to Cohere's approach as an example -- rather than teaching an agent to talk to Excel directly, they packaged small CLI tools (Pandas, OpenPyXL, LibreOffice utilities) into a dedicated skill.

“one architectural pattern that we're seeing is that make it easy for coding agents, right?”

04A production case: one agent per customer

A production case: one agent per customer

  • He walks through a client sales-process system that monitors an inbox for incoming requests and routes each one to a per-customer agent session.
  • Each agent is configured with a general-purpose "agent MD" harness file plus a "customer MD" file describing that customer's specific quirks, access, and discounts, and the agent produces a draft reply the user edits from within their normal inbox.
  • He closes by predicting coding agents will be a core building block for software systems going forward.
