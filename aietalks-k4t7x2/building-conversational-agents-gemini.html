01A new unified Interactions API for models and agents

Schmid introduces the Interactions API, launched in December in beta as a successor to Generate Content, designed to work the same way for both models and built-in agents (like deep research) and to look closer to industry-standard APIs (Chat Completions-style) than Google's previous proto-specific interface. It adds remote MCP support and, launched about two weeks before the talk, tool combination -- letting a call combine Google Search grounding with a developer's own custom function in the same request.

“the Interactions API is a new API we launched in December in beta, which hopefully will succeed Generate Content soon.”

02Server-side state changes the caching economics

Because the Interactions API keeps conversation state on the server (referenced via a previous-interaction ID) instead of requiring the client to resend full history, input-token caching becomes more reliable -- client-side edits like stripped line breaks otherwise silently break the cache. Schmid cites cached input tokens running about 90% cheaper, and startups using the Interactions API seeing two to three times better cache hit rates than before. Free-tier interactions are stored server-side for 1 day; paid usage is stored for 55 days.

“cache requests I think are 90% cheaper for the input tokens.”

03Designing skills for coding agents

Schmid frames the design principle behind their published Interactions API skill: a skill should cover something the model can't do reliably on its own, or encode a workflow-specific preference, rather than duplicating things the model already knows. Their skill primarily points the agent to markdown documentation and current model IDs rather than bundling all API documentation inline, so it doesn't go stale as the API changes.

“it should be either something the model cannot do reliably or if you have some personal preferences on like how to do a certain workflow”

04Live API: native audio, with real session limits

Thor demos the Gemini 3.1 Flash Live model, describing it as a native audio model that goes sound-token to sound-token rather than running a cascading pipeline of transcription, text generation, and speech synthesis. Session length is capped: without context-window compression, audio-only sessions are limited to 15 minutes and audio-video sessions to 2 minutes, after which the session terminates.

“it's it's kind of native audio model. So, what that means is we're not going through text. It's kind of not a cascading pipeline where um you're transcribing the text, running the text through an LLM, and then generating speech.”

05Native audio vs. cascading pipelines for production use

Asked about real business applications, Thor recommends that for many production use cases teams may be better off with a cascading pipeline rather than native audio, because a cascading setup gives observability at each step (e.g. the ability to rewrite a response before it's spoken) that the fully real-time native-audio approach doesn't currently provide.

“if you're you know like in in a real business use case you might be you know better off with kind of the cascading pipeline because it gives you sort of the observability at each step of the pipeline.”

Commentary (ours)

Several live demos during the session failed on stage (Google Search grounding not returning weather data, a custom background-color tool not firing), which the speakers acknowledged as unresolved bugs rather than intentional limitations -- worth treating the Live API's tool-calling reliability as still rough at this stage rather than production-proven, independent of the stated session-length limits (ours).
