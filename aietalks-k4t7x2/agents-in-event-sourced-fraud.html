A two-tier fraud architecture keeps the rule/ML engine for common cases and routes gray-zone cases to fan-out risk/behavior agents plus a verdict agent pulling context from a CDC-fed semantic layer under a 500ms SLA.

If you only read one thing

  • A two-tier fraud architecture keeps the existing rule-based/ML engine for most transactions and routes only gray-zone cases to a tier-two layer of fan-out agents.
  • Two specialist agents (risk analyzer, behavior analyzer) each reach a conclusion, and a third verdict agent reconciles their responses instead of relying on raw metrics, which cut false positives.
  • Agents pull context from a CDC-fed materialized semantic layer built across four bounded contexts (transaction, account, device, payment), using short-term in-memory storage to hit a sub-500ms SLA.

This reconstructs the tier-two flow described in the talk: gray-zone transactions fan out to two specialist agents pulling context from a CDC-fed semantic layer, then a verdict agent reconciles their conclusions under a sub-500ms, in-memory-only budget (ours).

Why this talk is a blueprint, not a take (ours)

Scope: A real-time transaction fraud-decisioning system for one team's existing event-sourced platform, adding an agentic tier only for the cases the existing rule/ML engine can't confidently resolve.

A two-tier pipeline where a tier-one rule/ML engine scores every transaction and auto-approves or auto-rejects most of them, escalating the gray-zone middle to a tier-two sub-orchestrator that fans the event out to a risk analyzer agent and a behavior analyzer agent (each with tools against a CDC-fed, denormalized fraud-indicator projection spanning four bounded contexts), then reconciles their outputs with a third verdict agent, all within a sub-500ms, in-memory-only budget.

Prerequisites the talk implies:

  • An existing event-sourced architecture (the talk uses Cosmos DB as the event store) with bounded contexts already separated by domain
  • A CDC/change-feed mechanism and message broker able to propagate updates into a materialized projection layer fast enough for a sub-500ms decision path
  • An existing tier-one rule-based or ML system worth keeping, since the design explicitly adds agents only for the cases that system can't resolve rather than replacing it

What the talk does not say:

  • No figures on how much the gray-zone/false-positive rate actually improved after adding the verdict agent, only that a raw-metric verdict reproduced the old problem
  • No cost, model choice, or per-transaction latency breakdown for the two analyzer agents plus the verdict agent within the 500ms budget
  • No detail on how the verdict agent's own decision gets audited or explained to a customer, the same gap the talk's opening anecdote pointed at

If you were to replicate one thing first: Start by measuring what share of your existing pipeline's decisions actually fall into an unresolved gray zone before building any agent layer to handle it.

The gray-zone problem existing systems can't resolve

  • The rule-based engine and later the third-party ML model could confidently approve or block transactions above and below certain thresholds, but a meaningful share of transactions fall into a gray zone where neither system can reach a clear verdict.
  • The team's response was not to replace the existing tier-one system but to add a tier-two agentic layer that only engages for that gray zone.

03Fan-out agents plus a verdict agent
Slide at 15:20 · click any slide to enlarge

Fan-out agents plus a verdict agent

  • Inside the orchestration layer's tier-two sub-orchestrator, an event fans out to a risk analyzer agent and a behavior analyzer agent, each equipped with tools against the semantic layer (fraud history, device trust, business rules, transaction-pattern plugins).
  • A third verdict agent reconciles both responses into a final decision rather than relying purely on a metric threshold, because pure-metric verdicts reproduced the same false-positive problem as the old rule-based system.

Commentary (ours)

The gray-zone-only routing pattern is a pragmatic way to introduce non-deterministic agents into a latency- and audit-sensitive path without disturbing what already works; the open question the talk doesn't address is how the verdict agent's own decisions get audited or explained to a customer, which was the exact gap in the anecdote that opened the talk.
