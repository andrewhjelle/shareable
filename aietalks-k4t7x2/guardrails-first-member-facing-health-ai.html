01The production baseline is already dangerous

A consumer AI assistant told a 60-year-old man to swap dietary salt for sodium bromide; after 3 months he was hospitalized with paranoia, hallucinations, and bromide levels 200 times the safe limit. A separate independent Mount Sinai test found a consumer health AI under-triaged life-threatening emergencies, including diabetic ketoacidosis, 50% of the time. ECRI, the patient-safety group hospitals use to rank risk, named AI chatbot misuse the number one health technology hazard of 2026.

02Code above the model, not inside it

Hinge Health's architecture puts a deterministic code layer above the model that runs on every turn before the model does; most turns still reach the model, but it never gets a vote on irreversible, high-stakes decisions such as emergency escalation, intent routing, and identity verification. The reasoning given is that even frontier labs' own published authority hierarchy (root, system, developer, user, guideline) means every layer above user is one prompt injection away from being overridden, so a prompt can't be trusted as a security boundary.

“Code on top, model below. Every turn goes through the code layer first. Most turns do reach the model, but the model never gets a vote on high stake calls”

03Monitoring is continuous, not a launch gate

Rather than treating evals as a pre-launch checklist, Hinge Health scores live production traffic continuously using three signal sources: automated judges scoring dimensions like clinical accuracy and drift, member thumbs up/down feedback, and sampled traces with 100% sampling on high-stakes cases.

“judges that continuously keep scoring real conversations as they happen. Not a saved golden data set. Live traffic”

▶ watch at 09:53
04Deciding what ships when stakeholders disagree

When clinical, legal, compliance, product, and engineering see the same bug differently, the talk offers a five-rule framework: severity is set by the worst plausible outcome, not the average; severity isn't determined by who has capacity to fix it; default to the safer mistake (hold and fix safety bugs when unsure, ship polish bugs when unsure); calibrate to what the org already tolerates in production, not what it claims to tolerate; and design for a human to read the signal, since people, not compute, are the bottleneck.

“Rule one. Worst case always wins. Severity is set by the worst pos- plausible outcome, not the average”
