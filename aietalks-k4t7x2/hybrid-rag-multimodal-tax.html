Bypassing the Multimodal Tax: Hybrid RAG, SQL RRF & UI Telemetry

SpeakerAbed Matini · Ogilvy Watchyoutu.be/Akm1sqvWG4A
Context engineeringLocal modelsSecurity

If you only read one thing

  • Dragging a full document into a chatbot burns tokens before any question is asked; converting to markdown and chunking first (by heading, paragraph, fixed 512 characters with 64-character overlap, or sentence) is cheaper and more traceable.
  • Dumping a whole 28-page PDF produces meaningless chunks (e.g. an isolated 'signature date') that increase hallucination; a live demo showed heading/Q&A-based chunking gave more accurate, referenceable answers than uploading the entire file.
  • Hybrid retrieval (BM25 keyword search plus semantic/cosine search), a small local model (Qwen 2.5 0.5B, about 400MB), and guardrails implemented in Python code rather than the system prompt, all tracked via LangFuse telemetry, reduced hallucination versus relying on prompt instructions alone.
01The two problems: token waste on upload, tool sprawl in production

Uploading a document directly to an LLM chatbot spends tokens on processing the document before any question is even asked. Separately, production chatbots that stack a vector database, keyword search, semantic search, and additional tools become complicated to manage as the tool count grows.

“as soon as we upload these documents, we going to basically lose some of our tokens that we supposed to have only for uh processing these documents without even asking a question”

02Structure-first ingestion: convert to markdown before chunking

Instead of sending raw documents straight to a cloud LLM, the pipeline uses Docling (referred to in the talk as 'Doc Link') to convert PDFs, Word docs, PowerPoint files, and images to markdown locally first, giving visibility into how chunking will actually happen before any tokens are spent on an online model.

“what we can do with Python is we're using Doc Link to convert those uh raw documents uh to markdown files”

▶ watch at 06:48
03Four chunking strategies, and why messy chunks hurt accuracy

The demo covers four chunking strategies: heading-based (each heading plus its content becomes a chunk, good for Q&A-style documents), paragraph-based, fixed 512-character chunks with 64-character overlap (for less-organized data), and sentence-based. A live comparison showed that dragging the entire 28-page employee handbook into the chatbot produced meaningless chunks (e.g., an isolated 'signature date' line) that reduce accuracy and increase hallucination, while heading/Q&A-based chunking returned answers with a clear, traceable source reference.

“one of the best practices for rag is you just divide based on 512 character, and you have 64% overlap between the chunks, so you won't lose the track”

04Hybrid retrieval: keyword search plus semantic search

The system combines BM25 keyword search with semantic (cosine-distance) search because semantic search alone returns similar-but-not-exact matches, which is a problem when exact terms matter -- e.g., a medical chatbot needs the exact medication name, not something merely similar.

“if it's a medical chatbot, you need the exact medication. You need don't need something similar or close to it. So, we need to have both both basically uh keyword search and um and the semantic search together”

▶ watch at 30:09
05Small local models, code-level guardrails, and telemetry

The chat model used is Qwen 2.5 at 0.5 billion parameters (about 400MB), chosen because a smaller model given well-vetted, pre-filtered context performs adequately and is less prone to fabricating information than relying on a bigger model with messy context. Guardrails (intent rejection, term dictionaries, an LLM classifier) are implemented in Python code ahead of the LLM call rather than in the system prompt, which makes blocking behavior deterministic and testable. LangFuse telemetry tracks each conversation by ID, including which model was used, how many chunks were returned, and latency.

“you don't need the biggest model. You if you can vet your data before sending it to your LLM, a smaller smallest model can sort you out and get a good uh uh answer for you”

Commentary (ours)

The core claim -- that a well-chunked, hybrid-retrieved context lets a 0.5B local model outperform naive full-document upload to a frontier model -- is demonstrated only on a single small FAQ/employee-handbook use case with a live but informal comparison; it would be worth seeing the same chunking-strategy comparison run against a harder, ambiguous-answer document set before generalizing the 'smaller model plus better context beats bigger model plus messy context' conclusion (ours).
