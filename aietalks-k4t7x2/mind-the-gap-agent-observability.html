If you only read one thing

  • Reliability for non-deterministic agents rests on three practices -- evaluate, monitor, optimize -- run continuously, not just once at build time.
  • Evaluation should check each decision point in an agent's flow (intent resolution, then tool call correctness, then task adherence), not just the final response.
  • An early-preview coding-agent 'observe' skill can auto-generate eval data sets, run evals, and optimize prompts, but its iterative optimization sometimes regressed (improving to 7, back to 8, then down to 5), so a human had to pick the best version rather than let it chase a perfect score.

01Agents are non-deterministic, and reliability needs three practices

Agents are non-deterministic, and reliability needs three practices

  • The speakers frame agent non-determinism as a production problem, not just a demo quirk, and name three practices for managing it: evaluate (quality, safety, performance), monitor (continuously, as requirements and environments change), and optimize (act on the data evaluation and monitoring produce).

02Evaluate at each decision point, not just the final answer

Evaluate at each decision point, not just the final answer

  • Using a weather-agent example, the speakers walk through evaluating intent resolution (did the agent understand what the user wanted), then tool call correctness (was the right tool called), then the overall response (task completion and task adherence), arguing that pinpointing failures requires checking each of these points separately.
  • A real example evaluation caught a groundedness failure where the agent's response gave a date of August 2024 instead of 2025.

“does the user uh the user wants to know the local weather? Has it been able to understand that intent and then make the next decision point that it needs to, which is make a tool call”

03Red teaming: a second AI attacks the first

Red teaming: a second AI attacks the first

  • Red teaming is described as having a second AI attack the first AI with defined risk categories and attack strategies, ranging from simple prompt manipulations (like reversing text to slip past a guardrail) up to a 'crescendo' attack that escalates gradually, like a frog in boiling water, until the agent has been compromised across a series of small steps.

“red teaming is actually kind of cool. With red teaming, what you do is you get a second AI to attack your first AI”

said at 58:56

“what a crescendo attack does is it starts it off like a frog in boiling water”

04An automated eval-optimize skill, and where it needed a human

An automated eval-optimize skill, and where it needed a human

  • A demoed early-preview 'observe' skill let a coding agent generate an eval data set, run a baseline evaluation, and automatically optimize the agent's prompt when it found a task-adherence failure.
  • Pushed further toward a perfect score, the optimization loop began oscillating -- improving to 7, regressing to 8, dropping to 5 -- and the presenter had to manually stop it and keep the best version (5) rather than let it continue chasing 10/10.

“your prompt is not actually perfect. Relevance is fine, but task adherence, there are cases where it's not actually completing the task you asked it to do”

said at 67:44

“it'll go back and forth and it'll keep regressing. And it'll keep finding that it it improves to seven and comes back to eight. It improves to seven, come back to five”

said at 69:47

Commentary (ours)

The oscillating optimization loop is a useful counter-example to the pitch that these tools remove the need for a human in the loop -- the demo itself showed the automated optimizer needing a human to recognize regression and stop, which the presenters frame as expected rather than a flaw (ours).
