Lays out a playbook for scaling coding agents across a whole team rather than one developer: staying model/harness agnostic, exposing one persistent agent session across Slack/app/GitHub, converting meeting and support signals directly i...

If you only read one thing

  • Superconductor's core recommendation is to stay model/harness agnostic because token-seller incentives aren't aligned with the buyer's, and to keep one persistent agent session addressable from Slack, the app, and GitHub instead of trapping it on one laptop (c1, c2).
  • Running agents in isolated cloud sandboxes with scoped credentials matters because autonomous agents can find and misuse a stray token -- one cited failure mode is an agent finding a laptop token, believing it's staging, and deleting production data (c3, c4).
  • On Superconductor's own codebase benchmark, Anthropic models kept improving in quality without getting faster or cheaper, while Codex was faster and cheaper, and the team (1.5 billion tokens/month) made Codex their default with 4x the session volume at a lower overall cost than Claude Code (c6, c7, c8).

01Stay model and harness agnostic

Stay model and harness agnostic

  • Singh's first lesson is to avoid locking a team into one model or harness because the best option can change weekly, open-weight models like GLM are now competitive and cheaper, and the companies selling tokens are incentivized to sell more of them than a team actually needs.

“the incentives of the people selling you tokens aren't really aligned with yours”

02One agent session across every interface
Slide at 03:40 · click any slide to enlarge · 8 more from this section below

One agent session across every interface

  • Rather than trapping an agent on a developer's laptop or even just in Slack, Superconductor keeps the same agent session addressable and visible across Slack, a desktop/mobile app, and GitHub, so context carries over regardless of where someone engages with it.
  • A 'meeting bot' extends this further by listening to a full meeting (demonstrated with a 4-hour Google Meet) and automatically creating tickets from ideas raised, linking to existing work rather than duplicating it.

“the agent didn't forget what you did in one place in Slack when you go and talk to it from GitHub, it's the same”

03Isolate agents in cloud sandboxes

Isolate agents in cloud sandboxes

  • Running agents in an isolated cloud environment rather than on individual laptops removes 'lid anxiety' but more importantly limits what an agent can access.
  • Singh argues agents should only be given the credentials they need and their network access should be explicitly scoped, because increasingly autonomous, resourceful agents can find and use stray credentials on a developer's machine in ways that cause real damage, and sandboxing also lets non-technical team members trigger real engineering work directly.

“you should only give your access give your agents access to only what they need”

04Benchmark on your own codebase, not public leaderboards
Slide at 13:10 · click any slide to enlarge · 2 more from this section below

Benchmark on your own codebase, not public leaderboards

  • Because public benchmarks like SWE-bench may have little to do with a team's actual stack (their example: SWE-bench is Python, Superconductor is Ruby on Rails), Singh recommends selecting real pull requests from your own repo and benchmarking harnesses against them for quality, cost, and time.
  • On their codebase, Anthropic models kept improving in quality but not speed and were noticeably more expensive, Codex and Cursor were fast and cheaper, and open models kept improving but remained slower; this data, not just vibes, drove them to switch their default to Codex, with roughly 1.5 billion tokens spent across the team in a month and Codex running four times as many sessions as Claude Code at lower overall cost.

“the Anthropic agents have just been consistently getting better, but not really any faster”
