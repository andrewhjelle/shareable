If you only read one thing

  • Codex Spark generates code at 1,200 tokens/second versus roughly 40-60 tokens/second for the Sonnet and Opus families, a 20x jump that has stayed flat industry-wide for about two years.
  • At 1,200 tokens/second, validation (test suites, linting, pre-commit hooks, diff reviews, browser QA) becomes essentially free and should run at every step rather than only before a push; the same speed also makes generating and cherry-picking many variants (e.g. 15 per sub-agent x 5 sub-agents = 75) practical for taste-dependent tasks.
  • Because context fills 20x faster, compaction that used to take 10 minutes now arrives in about 30 seconds, making an external four-file memory system (agents.md, plan.md, progress.md, verify.md) and small bounded task goals more necessary than before.

A 20x jump in coding-model speed

  • Codex Spark, released about a month before the talk by Cerebras and OpenAI, generates code at 1,200 tokens/second, compared to roughly 40-60 tokens/second for the Sonnet and Opus model families -- a speed that has stayed flat across major model families (Gemini, Claude, GPT) for about two years.

02Why inference is getting faster
Slide at 03:40 · click any slide to enlarge · 8 more from this section below

Why inference is getting faster

  • The speedup comes from optimization across the whole inference stack at once: hardware (the 'memory wall' means memory movement takes 50-80% of inference latency, driving chips like Cerebras's wafer-scale SRAM design), disaggregated prefill/decode inference (cited as the reason Nvidia bought Groq for a figure given as $20 -- likely billion), model architecture (mixture-of-experts activates only a subset of experts per token), and inference-layer optimizations like KV cache reuse.

“hardware and memory movement takes up 50 to 80% of that latency time for inference”

“This is why Nvidia bought Groq for $20 a few months ago”

“instead of activating the entire model all at once for every single token, we're only activating a subset of experts for every time”

03Make validation and variant generation free

Make validation and variant generation free

  • At 1,200 tokens/second there's no excuse not to run test suites, linting, pre-commit hooks, diff reviews, and browser-based QA at every workflow step instead of only right before a push.
  • The same speed makes 'cherry picking' practical: generating many variants of a design (e.g.
  • 15 versions from one agent, or 75 across five sub-agents) and picking the best, which the speaker frames as a way to artificially induce taste since models themselves lack it.

“at 1,200 tokens per second, a model like Codex Spark makes validation basically free. There is no excuse and no reason why you should not be doing things like this”

said at 10:14

“I can have it tell it to generate 15 versions in the same time that it would have taken the a previous model generate one version, and I can cherry pick the version that I like the best”

said at 10:45
04Context fills 20x faster too
Slide at 15:30 · click any slide to enlarge · 8 more from this section below

Context fills 20x faster too

  • Because generation is 20x faster, the point at which context fills and compaction triggers arrives proportionally sooner -- what took 10 minutes to fill now takes about 30 seconds -- making context management more critical, not less.
  • The speaker recommends externalizing memory with a four-file system (agents.md for sub-agent definitions, plan.md for the step-by-step checklist, progress.md for what's done, and verify.md for step-level checks) so every new session can pick up where the last left off.

“Now, if you take 10 minutes divided by 20, you are now getting compaction in 30 seconds. And so, context managing, especially with fast inference, is more important to think about than ever”

said at 15:23

“We have agents.md, which is where we're actually defining all our agents, our subagents. We have plan.md, which is what we're creating at the very beginning”

said at 15:54

Commentary (ours)

The core argument -- that faster generation multiplies existing bad habits rather than fixing them -- generalizes beyond this specific model; the four-file external-memory pattern is a concrete, reusable structure worth testing on any agent workflow prone to compaction loss (ours).
