01The story: a developer's friction becomes a coding agent's dead end

The story: a developer's friction becomes a coding agent's dead end

  • The speaker (platform engineering lead at a payments company, cited elsewhere in the talk as Banking Circle, servicing 700+ regulated financial institutions) opens with a scenario: a new developer hits a wall deploying their first application and has to informally ask teammates and another team for help.
  • He argues that this same situation, tolerable for a human, is essentially impossible for an AI coding agent, since an agent can't walk over and ask a colleague.

02Make the platform self-service, API-based, and local-first

Make the platform self-service, API-based, and local-first

  • The core recommendation is that any platform capability an agent might need should be triggerable without a human in the loop, exposed through a well-defined, schema-validated API (not just documentation or clicking through a UI), and usable locally so failures surface immediately (shift left) rather than after a slow round trip through CI.

“If I need any resources from this platform, if I need to be able to do anything through this platforms, I should be able to do it in my own.”

said at 06:48

“It could be based on many things, but agents are good at calling well-defined APIs.”

said at 08:20

“If something is going to fail, it should fail as soon as possible.”

said at 10:25
03Give the agent documentation and explicit success criteria

Give the agent documentation and explicit success criteria

  • Beyond precise task instructions, agents need an explicit definition of what counts as success, since they can't casually check a dashboard the way a human would.
  • Documentation should be structured for machine consumption, including project-level agent-specific files (agents.md, CLAUDE.md, or equivalent) and reusable skills files that codify house conventions.

“you can use the agent.md files or cloud.md, compiler_instructions.md, depending on on your agent of choice.”

said at 14:04

“it is important that you give it precise instructions, that you describe the task, that you tell the agent, this is what I need you to do”

said at 10:55
04Measure whether the changes actually worked

Measure whether the changes actually worked

  • The speaker recommends measuring platform changes before and after using existing frameworks (DORA delivery metrics, reliability metrics, support-ticket volume, developer-experience frameworks like SPACE) rather than assuming agent-readiness improvements paid off.

“we know that there is metrics about application delivery and we have the whole uh Dora um metrics on that”

05Use the AI moment as leverage for stalled best practices

Use the AI moment as leverage for stalled best practices

  • He closes by suggesting that best practices platform teams have struggled to get buy-in for (API-first design, local-friendliness, proper documentation) can now be pushed through because AI adoption has organizational attention at every level.

“Everyone from the executive level to the individual contributors are looking at AI now. It is a very hot topic.”

Commentary (ours)

(ours) The talk's own framing is that none of this is new advice — it's standard platform-engineering hygiene that agents simply make painful faster. That's a useful reality check against treating 'agent-readiness' as a distinct workstream rather than finishing the API/docs/observability work that was already overdue.
