If you only read one thing

  • Cua's driver runs computer-use agents in the background without taking over the screen, using undocumented OS-level APIs across Mac OS, Windows, and Linux (c1).

Background computer use, not screen takeover

  • Cua's driver (released in open source) lets a computer-use agent act on a machine without taking over the user's screen, unlike the 'computer use 1.0' human-loop pattern of screenshot-then-click.
  • It relies on undocumented APIs shipped in the Apple framework and works across Mac OS, Windows, and Linux, using accessibility-tree or screenshot-level observation with a fallback to a pixel-level background click.

02Kua Bench: a hard, verifiable GUI benchmark

Kua Bench: a hard, verifiable GUI benchmark

  • Kua Bench structures each task as setup, an oracle golden trajectory, and an evaluator, authored in a single Python file that works across five desktop platforms.
  • The catalog has over 130 verifiable tasks across 42 environments.
  • A collaboration with Snorkel AI added Kua Bench Kyad, testing computer-use agents on electrical-engineering tasks with software used by real professionals; the top agent fully passed only 6 of 25 tasks, all involving edits to an existing schematic, and no model scored above 30% reward overall.

“the top agent that we tested only got a full pass on six out of 25 of these tasks. Of those six, 100% of them involved editing an existing schematic”

said at 07:51
03Driver improves pass rate and token cost

Driver improves pass rate and token cost

  • On the Kua Bench basic dataset at 4K resolution, agents using the built-in computer tool got around 62% pass rate; switching to Cua's driver raised that to 80% while using 34% fewer tokens, attributed to the driver focusing on a single window rather than the full desktop.

“the pass rate jumps from 62% to 80% using 34% less tokens and this is primarily because KU driver focuses on a window rather than the entire desktop”

said at 08:57
04GPU pooling for RL training on computer-use environments
Slide at 11:30 · click any slide to enlarge · 5 more from this section below

GPU pooling for RL training on computer-use environments

  • Cua's infra team described idle GPU time during RL training as pure cost while sandboxes spin up or reset, and introduced a demand-based autoscaler that grows a warm pool of sandboxes to match GPU demand without needing to pre-specify pool size, which can shift over a multi-day training run.

“you finish your task on a sandbox and then you're waiting for either like a new sandbox to spin up or for your existing one to reset. Uh the problem here is that like this is just pure cost”

said at 11:11

“we use a demandbased autoscaler to detect um how many GPUs like currently need a sandbox and we can grow the pool to be that size uh on demand”

said at 13:12

Commentary (ours)

(ours) The 0% score on blank-schematic tasks versus passes only on edits to existing schematics suggests these agents are pattern-matching against a starting state rather than reasoning from a spec, which is a sharper capability gap than the aggregate 30%-ceiling number alone conveys.
