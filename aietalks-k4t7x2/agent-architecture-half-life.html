Your agent architecture has a half-life of 6 months

SpeakerDan Farrelly · Inngest Watchyoutu.be/X1kp-ABIIxQ
Agentic engineeringInfra & serving

If you only read one thing

  • Agent systems have three layers with different decay rates: execution (the brain, lasts years if built right), context (models/prompts/tools, changes fastest), and compute/sandboxes (the hands) (c1, c2).
  • The fix for constant rewrites is to decouple these layers so a stable execution layer survives model and framework churn, rather than coupling everything together (c3, c6).
  • The execution layer must provide resumability with externally-held state, flexible invocation patterns, and full-session observability, while sandboxes should stay ephemeral and never be used for durability (c4, c5, c7).
01Three layers, three decay rates

The speaker proposes thinking about agent systems as three conceptual layers rather than specific components: the execution layer (flow, state, durability, retries), the context layer (models, prompts, tools, memory), and the compute layer (sandboxes, runtimes, browsers). Each layer has its own half-life: prompts may last only a week, models last months, but a well-built execution layer can last years.

“It's where flow, state, durability, retries happen. Then there's the context layer. This is the knowledge. All right, this is models, prompts, tools, memory.”

02The thesis: decouple the layers

Most teams couple these layers together, so one layer's short half-life drags the others down as accumulating technical debt. The recommendation is to design the execution layer as a stable foundation and let models, prompts, and sandboxes be swapped out around it without rewriting the whole system.

“my thesis is think in layers. Decouple them.”

▶ watch at 04:09
03What a proper execution layer must do

It must support resumability, meaning long-running work (the example given is a 3-hour run) cannot hold its state only in memory or on disk; state has to live externally and durably so a failed step can retry without restarting from the beginning. It also needs to support many invocation patterns (crons, events, APIs, human-in-the-loop, sub-agent delegation) and provide full-session observability across LLM calls, tool calls, and infrastructure errors.

“a 3-hour run cannot hold state in memory or in disk. The state must live outside of the work.”

▶ watch at 07:13
04Sandboxes are the hands, not the memory

Sandboxes are ephemeral and stateless by design, so using them to hold durability, snapshots, or session state is called out as an anti-pattern; the execution layer, not the sandbox, should own context, sequence, and durability. Without a proper execution layer, harness code ends up absorbing ad hoc queues, workers, polling, and backoff logic instead.

“a sandbox is ephemeral and stateless by design. So, using it for durability, snapshots, or something in state, I think is an anti-pattern.”

▶ watch at 09:50

“your harness logic starts absorbing other concepts like queues, workers, polling, backoff, scheduling. And now you end up kind of a mess bad abstractions.”

▶ watch at 08:17
05Why this matters for emerging patterns

Background agents can run for minutes or hours with roughly 200 tool calls and are all but guaranteed to hit at least one failure, making them undebuggable without the right execution infrastructure. Ingest positions itself as this execution layer, pluggable with any model, framework, or sandbox.

“it could might run for minutes or hours. It's going to have maybe hundreds of calls to you know, maybe 200 tool calls. You're going to probably guarantee to”

“We're durable execution for AI agents. We're the execution layer.”

Commentary (ours)

(ours) The half-life framing is a useful mental model but the specific numbers (a week for prompts, months for models, years for execution) are stated as opinion rather than measured data, and Ingest is both the speaker's employer and the product being recommended as the solution.
