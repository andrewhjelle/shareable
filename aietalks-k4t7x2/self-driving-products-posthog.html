If you only read one thing

  • PostHog is building a pipeline that ingests product signals (trillions of events/month across errors, session replay, Slack, experiments), groups them into reports, runs a research agent, and ships a pull request -- aiming to replace dashboard-checking with reviewing ready PRs.
  • Off-the-shelf embedding models cluster signals by structural similarity (all errors together, all Slack messages together) rather than by the actual problem they represent; the fix was generating LLM queries about each signal and matching those in embedding space instead.
  • Key lessons: eval on real production data (not vibe checks), don't let agents attempt fixes on vague/generic reports (it will try anyway and produce noisy PRs), and don't over-optimize pipeline cost early -- running an agent against the same problem repeatedly first reveals patterns that can later be distilled into a cheaper one-shot call.

01The pipeline's goal

The pipeline's goal

  • Instead of a developer noticing a dashboard change hours or days later, filing a ticket, and eventually opening a PR, PostHog wants a background agent to investigate a product signal as soon as it happens and generate a pull request automatically, so the developer's main interface becomes reviewing PRs in GitHub rather than dashboards.

Ingesting and normalizing a high-volume, noisy signal stream

  • The pipeline ingests trillions of events a month across errors, session replay, logs, and experiments, first passing signals through an LLM safety classifier (to drop adversarial/public-abuse signals) then normalizing each into a common structure with source, type, content, and an assigned importance weight.

“we have a huge amount of events. We're ingesting trillions of events a month”

03Grouping signals into reports without embedding bias
Slide at 07:00 · click any slide to enlarge

Grouping signals into reports without embedding bias

  • Directly embedding raw signals clustered them by structural similarity (all errors together, all Slack messages together) rather than by shared underlying problem.
  • The fix was generating LLM-written queries describing what each signal is about and matching those queries in embedding space, which grouped related cross-source signals correctly.

“What the embedding model will do is it will notice structural similarity and it will put all of the errors together”

said at 06:13

“instead of matching in embedding space the signals themselves, uh we generate queries based off the signals”

04Research agent, actionability, and PR execution
Slide at 09:30 · click any slide to enlarge · 1 more from this section below

Research agent, actionability, and PR execution

  • Once a report crosses a weight threshold, a research agent (running the Claude Agent SDK in a Modal sandbox, with an internal MCP server, codebase context, and external MCPs like Linear/Notion) produces a summary, priority, and a Git-blame-based reviewer suggestion.
  • Reports are then routed to not-actionable (gather more evidence), needs-human-input (product decision, goes to an inbox), or immediately actionable (agent writes a fix, opens a PR, and iterates against CI/comments until green).

“the output of this research agent then, uh, is a summary of the problem. It gives a priority, how important we think this this problem is to work on”

said at 08:20
05Lessons learned building it
Slide at 11:30 · click any slide to enlarge · 3 more from this section below

Lessons learned building it

  • Testing only on internal vibe checks failed to catch problems that showed up on representative production data.
  • Throwing an agent at a vague signal (e.g.
  • 'onboarding is broken') produces noisy, low-value PRs because the agent will attempt a fix regardless of whether the problem is specific enough.
  • Early on the team over-optimized for token cost and delayed agent use as long as possible, which they called a mistake, since running an agent repeatedly against similar problems first reveals patterns that can later be compressed into a cheaper one-shot call or trained model.

“if you're not testing on representative data, it your you're basically just fumbling in the dark”

said at 11:26

“if you just throw an agent at a problem, it will try to fix something”

said at 11:57

“we tried to avoid using agents where we could or delay it till as late as possible in the pipeline. And when we were experimenting, this was a big mistake”

said at 12:59

Commentary (ours)

The 'tokens are free' lesson only holds because they eventually distill repeated agent runs into cheaper one-shot calls -- teams that skip that distillation step and just keep running full agents at scale will hit the cost wall they describe avoiding (ours).
