The Next Game Engine Won't Have a Manual

Informs the design of a domain-specific AI-authoring tool: instead of letting an LLM write arbitrary engine code (which reinvents boilerplate every time), the engine exposes a fixed vocabulary of tags that both the user and the AI assist...

If you only read one thing

  • Users describe intent in plain game-design language ("make this robot move with WASD and animate it") and an assistant applies pre-built tags to assets; no coding or asset import required (c1).
  • Pointing an LLM directly at a traditional engine's boilerplate (mesh, renderer, animator, rigid body, collider, audio source) makes it reinvent the same solution differently every time, so the engine instead exposes a constrained Asset Tag System the assistant applies to objects (c2, c3, c4).
  • Roughly 6,000-7,000 assets were tagged with a vision model rather than by hand, and scene context sent to the LLM is bounded using a level-of-detail-style priority scheme (c5, c6).

Why pointing an LLM at a traditional engine breaks

  • The speaker argues that today's powerful engines and LLMs still don't combine well: without a constrained vocabulary to work in, an LLM asked for something like a character-following camera reinvents the same solution differently every time.
  • Traditional engines also require assembling a lot of boilerplate per character (mesh, renderer, animator, rigid body, collider, audio source) before any actual game logic is added, and that boilerplate is largely the same across every game.

03The Asset Tag System
Slide at 09:30 · click any slide to enlarge · 3 more from this section below

The Asset Tag System

  • Nereu's answer is to describe every object as an asset with tags rather than hand-assembled components, borrowing the entity-component/data-oriented-design pattern from game development.
  • Systems query for assets by tag (e.g. vehicle + player + drivable) and act on them, so the same tag vocabulary is reused across every game built with the tool, and the AI assistant works by adding or removing tags rather than writing code.

“this system comes from something that we're calling the ATS or asset tax system”

said at 09:31
04Tagging thousands of assets, bounding the context
Slide at 16:00 · click any slide to enlarge · 1 more from this section below

Tagging thousands of assets, bounding the context

  • With roughly six to seven thousand assets in the library, manual tagging wasn't feasible, so a vision model was run against screenshots of each 3D asset to generate tags automatically.
  • To keep the LLM's context from growing unbounded as a scene fills up, the system borrows a level-of-detail approach from game rendering: objects near the user's focus (e.g. what's selected) get full tag and setting detail sent to the model, while distant/irrelevant objects get minimal information.

05What's still out of reach, and the actual goal
Slide at 16:20 · click any slide to enlarge · 1 more from this section below

What's still out of reach, and the actual goal

  • The speaker distinguishes this approach from a separate category of "world model" engines that generate a playable world on the fly, and predicts that real-time 4K rendering at 60 frames per second, plus physics simulation, is still far away for that approach.
  • The stated goal for Nereu isn't to one-shot a finished game nobody will play, but to get people unstuck so they can experience the process of making games.

Commentary (ours)

(ours) The bet here is narrower than it first sounds: rather than an LLM with open-ended engine access, the product constrains both the user's vocabulary and the model's action space to a fixed tag set. That tradeoff (less expressive, more reliable/composable) is the same one context-engineering practitioners make elsewhere when they replace open tool calling with a constrained action schema.
