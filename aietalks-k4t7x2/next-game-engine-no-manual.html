The Next Game Engine Won't Have a Manual

SpeakerArturo Nunez · Nereu Watchyoutu.be/VBCDhRrvlYo

If you only read one thing

  • Users describe intent in plain game-design language ("make this robot move with WASD and animate it") and an assistant applies pre-built tags to assets; no coding or asset import required (c1).
  • Pointing an LLM directly at a traditional engine's boilerplate (mesh, renderer, animator, rigid body, collider, audio source) makes it reinvent the same solution differently every time, so the engine instead exposes a constrained Asset Tag System the assistant applies to objects (c2, c3, c4).

01Describing a game instead of coding it

The tool, called Nereu (assistant name Bibi/Weeby), lets a user build a scene by describing intent in plain language: add a robot, make it move with WASD and animate, add buildings from a tagged asset library, add rain, have a camera follow the character. No coding, asset import, or component wiring is required from the user.

“now you don't need to be a programmer to to build whatever you want”

02Why pointing an LLM at a traditional engine breaks

The speaker argues that today's powerful engines and LLMs still don't combine well: without a constrained vocabulary to work in, an LLM asked for something like a character-following camera reinvents the same solution differently every time. Traditional engines also require assembling a lot of boilerplate per character (mesh, renderer, animator, rigid body, collider, audio source) before any actual game logic is added, and that boilerplate is largely the same across every game.

03The Asset Tag System

Nereu's answer is to describe every object as an asset with tags rather than hand-assembled components, borrowing the entity-component/data-oriented-design pattern from game development. Systems query for assets by tag (e.g. vehicle + player + drivable) and act on them, so the same tag vocabulary is reused across every game built with the tool, and the AI assistant works by adding or removing tags rather than writing code.

“this system comes from something that we're calling the ATS or asset tax system”

▶ watch at 09:31
04Tagging thousands of assets, bounding the context

With roughly six to seven thousand assets in the library, manual tagging wasn't feasible, so a vision model was run against screenshots of each 3D asset to generate tags automatically. To keep the LLM's context from growing unbounded as a scene fills up, the system borrows a level-of-detail approach from game rendering: objects near the user's focus (e.g. what's selected) get full tag and setting detail sent to the model, while distant/irrelevant objects get minimal information.

05What's still out of reach, and the actual goal

The speaker distinguishes this approach from a separate category of "world model" engines that generate a playable world on the fly, and predicts that real-time 4K rendering at 60 frames per second, plus physics simulation, is still far away for that approach. The stated goal for Nereu isn't to one-shot a finished game nobody will play, but to get people unstuck so they can experience the process of making games.

Commentary (ours)

(ours) The bet here is narrower than it first sounds: rather than an LLM with open-ended engine access, the product constrains both the user's vocabulary and the model's action space to a fixed tag set. That tradeoff (less expressive, more reliable/composable) is the same one context-engineering practitioners make elsewhere when they replace open tool calling with a constrained action schema.
