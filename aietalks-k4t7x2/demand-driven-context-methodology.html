Demand-Driven Context: A Methodology for Coherent Knowledge Bases Through Agent Failure

SpeakerRaj · IKEA Watchyoutu.be/_QAVExf_1uw
Context engineeringData curationAgentic engineering

If you only read one thing

  • Citing McKinsey, 88% of companies use AI but only 6% see value creation; the speaker attributes the gap to undocumented institutional knowledge that standard RAG/MCP retrieval layers don't reliably capture, especially since teams rarely run evals on that retrieval output.
  • The proposed fix, 'demand-driven context,' inverts the usual push model: give the agent a real work item, let it fail, capture what it was missing (a TDD-style loop), and curate only that gap into the knowledge base -- stored in GitHub so multiple agents/teams can contribute via normal PR review.
  • In a live demo running 14 real incidents through the loop, a documentation-confidence score rose from about 1.4 to 4.4, and consolidated curated context per domain averaged about 96K tokens, small enough to fit directly in a large context window.
01The gap between AI capability and delivery

The speaker cites a McKinsey figure that 88% of companies use AI but only 6% see value creation, and frames the cause using a red/orange/green classification of sample Jira tickets: models already handle general-knowledge (green) and teachable (orange) work, but struggle with the red category -- institutional knowledge that exists only within the company and its people.

02Why retrieval layers alone don't fix it

The industry's default fix is a retrieval layer (RAG, knowledge graphs, MCP servers) over sources like Confluence, Jira, and GitHub. The speaker argues that data coming out of these plugged-in retrieval systems is mostly undeterministic, unreliable, and untested, and that engineering teams typically don't run evals on that output the way a machine-learning team would.

“all when you plugging this MCP servers basically all this data coming out is mostly undeterministic. It's unreliable and it's untested”

“especially in engineering nobody does e-vals. Actually, it's it's more like a data machine learning concept but we don't do e-vals”

▶ watch at 08:54
03Demand-driven context: pull instead of push

Instead of pushing all documentation into an agent's context upfront, the proposed approach gives the agent a work item and lets it pull information as needed, similar to onboarding a new hire with a work item rather than requiring them to fully study the documentation first. The speaker draws an explicit analogy to test-driven development: write the failed test (give the agent a problem it will fail), then fill only the gap that failure reveals, repeating until the knowledge base is curated.

“So, we build everything and we push it to to it. So, in in this approach, it's more pull approach.”

▶ watch at 13:04

“We just write the failed test cases. Uh, we see what is a code that is missing uh, for the failed test case to pass and we just give that code”

▶ watch at 16:07
04Where curated knowledge should live, and how much of it you need

The speaker recommends storing curated context in a GitHub repository rather than a SaaS product, since GitHub's built-in PR and review process handles conflicts when multiple agents or teams contribute to the same knowledge base. He also argues for curating only the roughly 20% of documentation that is most useful as a cached context block, leaving the rest as links the agent can follow only when needed.

“So, I have a very opinionated opinion. Hear me out. I prefer it has to go to a GitHub repository because eventually somebody will actually come up with a you know, 20 million seed funded SaaS solution for you”

05Demo results

In a live demo running the loop across 14 real incidents, the tool's documentation-confidence score rose from about 1.4 to 4.4 as each cycle surfaced undocumented terms and gaps, then curated the answers back into the knowledge base. Audience Q&A on token cost established that consolidated context per domain averaged about 96K tokens, comfortably fitting inside a large context window without requiring further retrieval.

Commentary (ours)

The approach's own maintenance risks came out mostly in audience pushback rather than the talk itself: one questioner noted the demo shows only the happy path, where a filled gap is assumed correct rather than confidently wrong, and the speaker's answer (trust the most recently updated document, flag duplicates) doesn't fully address stale-but-plausible information -- worth weighing against the demoed confidence-score gains before adopting at scale (ours).
