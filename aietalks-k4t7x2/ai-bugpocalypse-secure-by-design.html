The AI bugpocalypse is here. Now what?

SpeakerJack Cable · Corridor Watchyoutu.be/7JgIS42mz7U
SecurityCoding agentsEvals & benchmarks

If you only read one thing

  • Even the best frontier models introduce vulnerabilities in about 20-40% of code they write, per the Backslash Bench benchmark from ETH Zurich and UC Berkeley researchers.
  • Memory-safe languages already prevent roughly 60-70% of vulnerabilities found in memory-unsafe code, and Android's memory-safety vulnerability share dropped from about 75% in 2019 to about 30% in 2022 just by writing new code in memory-safe languages.
  • Corridor's CEO predicts most shipped code will be reviewed by AI rather than humans within 6-12 months, and recommends hardening open-source foundations rather than only patching individual AI-found bugs.
01AI coding adoption and attacker capability are both scaling fast

The speaker cites Stack Overflow data that about 84% of developers were using AI coding tools and 30-40% of companies were encouraging their use, and notes coding agents are increasingly running autonomously (e.g., launched from Slack, running in the background) rather than synchronously inside an editor. He argues frontier models are simultaneously getting much better at finding and exploiting vulnerabilities across the full attack chain.

“about 84% of developers were using AI coding tools, 30 to 40% of companies encouraging use of AI coding assistants”

02AI-introduced vulnerabilities are measurable and mostly known classes

On the Backslash Bench benchmark, even the best models introduce vulnerabilities in about 20-40% of code written. The speaker notes a real-world example where Opus 4.6 introduced a vulnerability in a smart contract that led to a couple million dollars being stolen. He frames most AI-introduced bugs as not novel vulnerability classes but old, well-understood ones, and increasingly contextual issues like authorization bugs tied to a company's specific business logic that models weren't trained on.

03Memory-safe languages are a proven, durable fix

Roughly 60-70% of vulnerabilities in memory-unsafe-language products could be prevented by switching to memory-safe languages like Rust or Go, based on CVE data. Google's Android data shows the share of memory-safety vulnerabilities fell from about 75% in 2019 to about 30% in 2022 simply from writing new code in memory-safe languages, without rewriting old code -- evidence the speaker uses to argue systemic rewrites, not just one-off patching, reduce vulnerability rates for good even as models get smarter.

“approximately 60 to 70% of vulnerabilities in products written in memory unsafe languages can be completely prevented using memory safe languages”

04AI code review is becoming the bottleneck-breaker

Corridor's position is that security should prevent vulnerabilities before the pull request rather than block AI coding adoption, and the speaker predicts that within 6-12 months most shipped code will be reviewed by AI rather than humans, since human code review has become the development bottleneck.

“within the next 6 to 12 months, the majority of code that is being shipped will be reviewed uh not by human but by AI”

▶ watch at 13:08
05Policy recommendations from Congressional testimony

The speaker's Congressional testimony recommended preventing vulnerabilities in new code, hardening open-source software as the proving ground adversaries will test models against, and fostering American open-weight model development for fine-tuning and competitiveness. He also backed lifting export controls on Mythos and Fable models, arguing the benefit to defenders outweighs the risk given that adversaries already have access to powerful open-weight models via distillation.

“second is to harden the open-source foundation. Um this is incredibly important, right”

“the White House to lift the export controls on these models. And the perspective there is that the benefit to defenders far outweighs the risk”

Commentary (ours)

The Backslash Bench 20-40% vulnerability-introduction rate is a useful number to track over model generations -- if it doesn't fall as models get smarter, that would support the speaker's claim that this is a training-data and business-context problem rather than a raw-capability problem (ours).
