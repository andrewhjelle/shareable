Describes an internal agent (Studio, built on LangGraph and Opus) that lets non-technical teams query Snowflake/Linear/Notion directly and turn answers into reusable, non-LLM-dependent dashboard widgets

If you only read one thing

  • Studio lets non-technical teams ask business questions directly against Snowflake/Linear/Notion via a LangGraph agent on Opus, replacing slow Slack-and-dashboard request cycles.
  • Answers can be turned into reusable 'widgets' -- generated declarative code (UI, APIs, queries) that reruns live without invoking the LLM again, so cost and reliability don't scale with usage.
  • Reliability came from three practices: injecting tool-specific context only at the moment a tool is invoked (not preloaded), layering base/org/tool-specific rules, and validating that generated queries actually return data before hardcoding them into widgets.

The problem: slow, one-off answers to business questions

  • Non-technical teams (go-to-market, support) routinely need data answers that require SQL access, creating a cycle of explaining the question, waiting, getting an answer, and asking a deeper follow-up, often shared once in Slack and never reused.
  • WorkOS built Studio, an internal workspace (dashboard plus Slack bot) where people can ask questions and build reusable apps/dashboards themselves.

“You probably share that in Slack. Sort of a one-off. Doesn't really scale very well. Um we had this problem”

02Under the hood

Under the hood

  • A request (from the dashboard or Slack bot) hits an internal API that runs it through a LangGraph agent using Opus, with an integration proxy to Snowflake, Linear, and Notion and a guidance layer defining how to query each source (e.g., how to represent and join a customer in Snowflake).
  • Session state persists in Convex so context carries across sessions.

“We run a little API behind the scenes that takes that, parses it, and then runs it through Lane Graph, which is an agent that's both tied to uh LLM”

From one-off answers to reusable widgets

  • Beyond answering a single question, users can ask Studio to build a 'widget' -- sandboxed code combining UI, APIs, and the underlying query -- that reruns live for different time slices or filters without re-invoking the LLM.
  • One demoed widget let support search customer login/block history for a specific product (Radar) using a real query against production data, refined interactively (e.g., 'fix that visual bug').

“A widget is in this case, uh, basically like sandbox code that runs. Um, and it's both the UI, the APIs, and the query necessary to power like, uh, a fully usable tool”

“this has been really, really powerful for our support team. They use this in Slack all the time because they don't need um you know, different customers”

04Sequencing and layered context
Slide at 10:40 · click any slide to enlarge · 1 more from this section below

Sequencing and layered context

  • Studio runs pre-flight checks (tool connectivity, sufficient context, asking clarifying questions if not) before deciding which tools to call, and injects tool-specific context only at the moment a tool is invoked rather than preloading everything, to avoid blowing out the context window.
  • Context is layered: a base prompt, org-wide rules, and per-tool-setup specifics that persist if someone edits a tool's configuration.

“we actually, at the time it decides to invoke a tool, that's when we inject context around how to use the tool”

said at 10:56

“we make it run a lot of pre-flight checks. Um, so this is, you know, are all the tools connected correctly? Do you have enough context to be able to answer the question? If not, ask clarifying questions”

said at 10:25
05Distrust the model's own product knowledge, and validate before deploying
Slide at 10:50 · click any slide to enlarge

Distrust the model's own product knowledge, and validate before deploying

  • Because the product changes quickly, Studio is explicitly instructed to distrust the model's pretrained knowledge about WorkOS and instead look up primary sources like docs.
  • Before a query is hardcoded into a widget, Studio always runs it and validates it returns data, since a syntactically valid query returning zero rows would otherwise go unnoticed.

“we tell the LM to specifically like distrust uh knowledge around our product often just because like sometimes the model training is using outdated data”

said at 11:51

“if it's going to write a query to our Snowflake instance, we have it always run the query and validate that it gets data back”

said at 12:21
06Q&A: governance, permissions, and cost
Slide at 18:00 · click any slide to enlarge · 1 more from this section below

Q&A: governance, permissions, and cost

  • Widgets are declarative generated code, so once built they no longer invoke the LLM on each refresh, keeping the final product reliable and cheap to rerun; recurring domain quirks (e.g., a four-join customer-to-user relationship) are captured once in context rather than re-taught per employee.
  • Data access today is per-user (each employee connects their own Snowflake/Linear/Notion), which the team is replacing with org-level connectors and role-based default access; they report being willing to pay Opus-level cost because it outperforms cheaper models enough to matter for the answer-generation step.

“So, once the widget is created, it is reliable. It is not the it's not the LLM running the tool every So, when I hit like refresh here, this is actually just re-querying, uh, data from those tools”

said at 16:16

“Opus outperforms better than other models so much that uh, like I wouldn't trading the cost off would trade off quality in a way that we wouldn't deem acceptable”

said at 18:41

Commentary (ours)

The 'widgets stop calling the LLM once generated' design is the load-bearing idea here -- it sidesteps the usual agent-cost-scales-with-usage problem, but it also means a subtly wrong query becomes a silently-trusted permanent artifact unless someone audits it, which one questioner flagged and the speaker didn't fully resolve (ours).
