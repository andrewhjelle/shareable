If you only read one thing

  • PostHog's wizard handles 15,000 integrations a month by feeding fresh docs into context to counter 'model rot' and by pointing agents at thin 'model airplane' reference projects instead of full production apps.
  • To stop agents from improvising too many different integration patterns, the wizard withholds the end goal and 'breadcrumbs' the agent toward it, then interrogates the agent itself after every run at a stop hook to surface hidden failures like contradictory MCP tool instructions.
  • An early wizard version read users' .env files directly and sent contents up for inference; the fix was locking the agent to exactly two tool calls -- check if a key exists, write a new value -- with no env-file content ever leaving the machine.

01Model rot: training snapshots go stale fast

Model rot: training snapshots go stale fast

  • The speaker describes 'model rot' as the gap between a model's training snapshot and a fast-moving software project's current reality, since training a model is a large enough capital expense that snapshots persist for 6-18 months.
  • PostHog's fix is unglamorous: given large context windows, they load fresh markdown documentation from posthog.com directly into the agent's context rather than relying on the model's trained knowledge, letting the agent select from a menu of current docs based on what it detects in the project.

“models sit there no longer representing reality, right? They are a snapshot of the world and the web as it was, you know, 6, 8, 12, 18 months ago, perhaps”

said at 02:36

“with the context windows being what they are at this point, you can't beat just shoving a bunch of markdown files into the context and patching the holes”

said at 03:07
02'Model airplanes' constrain agent architecture choices

'Model airplanes' constrain agent architecture choices

  • Because models can produce technically workable but architecturally strange results, the PostHog wizard team maintains a fleet of 'model airplanes' -- thin, non-production reference projects with PostHog already implemented across multiple frameworks and languages, where non-essential parts like auth are stubbed out.
  • Pointing the agent at these gives it a token-efficient, consistent pattern to replicate for the correct shape of an integration.

“we maintain a fleet of what we call model airplanes. And these are projects that have PostHog implemented in them”

said at 05:12
03Breadcrumbing stops agents from improvising too many patterns

Breadcrumbing stops agents from improvising too many patterns

  • With 15,000 integrations a month, letting the agent freely improvise its path would produce thousands of different setups and an unmanageable support burden.
  • PostHog limits this by breadcrumbing: not telling the agent up front that it's doing a PostHog integration, instead starting with prompts like finding files with business value (logins, Stripe, churn indicators) before gradually working toward the actual integration task.

“to limit improvisation, what we do is breadcrumb the agent. We don't tell the agent up front exactly what we're going to do”

said at 07:18
04Interrogating the agent after every run surfaces hidden failures

Interrogating the agent after every run surfaces hidden failures

  • PostHog runs a stop-hook step after every wizard run that asks the agent itself what could have been done better to set it up for success, treating the agent as a research subject.
  • This surfaced failures the team wouldn't otherwise have caught, including an MCP tool instruction that contradicted another tool and a missing tool referenced across hundreds of runs.
  • The same trust concerns extend to security: an early wizard version read users' .env files directly and sent their contents up for inference, which the team fixed by restricting the agent to exactly two tool calls against env files -- checking whether a key exists and writing a new value -- so no env-file content is ever sent for inference again.

“at the end of every run, uh right at the stop hook, we ask a very simple question. We're doing a little bit of user research, but the user is in this case a robot”

05Prose over code: why the wizard is 90% markdown

Prose over code: why the wizard is 90% markdown

  • The speaker frames code as a depreciating asset that doesn't improve when a better model ships, whereas well-written prose instructions get more capable every time the underlying model improves.
  • Consistent with this, the PostHog wizard itself is composed of 90% markdown files and 8% tools for delivering and processing those markdown files, with the remainder being agent-harness code.

“The wizard that makes everybody so happy is 90% markdown files, 8% tools for delivering and processing markdown files, And then the rest is like Agent Harness stuff, right?”

said at 15:06

“Code has always been a depreciating asset. You write it, you might ship it into the world a little bit rotten cuz it's got some tech debt”

said at 14:35
