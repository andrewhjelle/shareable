patternHealthcare AIEvals & benchmarks

Lays out a concrete architecture (separate input/output LLM-as-judge guardrails around a core model) and a concrete workflow for turning a clinician's annotation of a flagged conversation into a typed eval that gates every future prompt,...

If you only read one thing

  • SonderMind built separate input and output LLM-as-judge guardrails around its Sonder core model specifically because separating them is more robust and harder to jailbreak than folding safety into one pass, even at added latency/cost (c2, c3).
  • The design goal is more correct triggers, not more triggers, because over-calibrated guardrails feel like a door slam to a vulnerable user; SonderMind had to disable the underlying frontier models' built-in guardrails because they filtered too aggressively (c4).
  • Every clinician annotation of a flagged conversation is converted into a typed eval (input, expected result, expected observation, category) that every subsequent prompt, model, or guardrail change must be scored against, and SonderMind open-sourced 200 input and 100 output guardrail scenarios as a shared baseline (c7, c8).

02Input and output guardrails sandwich the core model
Slide at 02:50 · click any slide to enlarge · 2 more from this section below

Input and output guardrails sandwich the core model

  • Sonder's architecture places separate input guardrails, which screen incoming user messages for whether intervention is needed before the core model responds, and output guardrails, which monitor the AI's responses and the conversation as a whole for clinical safety risk.
  • SonderMind deliberately implemented these guardrails as separate LLM-as-judge calls rather than folding them into the main response generation, judging that separation makes them more robust and harder to circumvent through prompt engineering, despite the added latency and cost.

03Correct triggers, not more triggers
Slide at 05:40 · click any slide to enlarge · 2 more from this section below

Correct triggers, not more triggers

  • SonderMind explicitly optimized for correct guardrail triggers rather than more frequent ones, because inappropriately guardrailing someone in a vulnerable moment can feel like a door slam to the face and increase isolation.
  • For a message indicating present-tense danger (a user hiding from a drunk, threatening husband), Sonder surfaces local resources and disengages from the conversation rather than continuing to chat.

“when you inappropriately guardrail on somebody, then that can often feel like a door slam to the face and make that person feel more isolated”

04Clinician annotations become typed evals that gate releases
Slide at 10:10 · click any slide to enlarge · 2 more from this section below

Clinician annotations become typed evals that gate releases

  • The talk uses the example of an indirect, coded risk message ('I packed a box today, just one to feel what it would be like to be gone') to argue that pattern-matching, verbose prompt rules, or a generic moderation API would miss the clinical nuance.
  • Instead, a flagged conversation is traced and handed to a licensed clinician to annotate; that annotation is converted into a typed eval with an expected result and expected observation, and every subsequent prompt, model, or guardrail change is scored against it.

05Open-sourcing the guardrail scenario datasets
Slide at 13:20 · click any slide to enlarge · 5 more from this section below

Open-sourcing the guardrail scenario datasets

  • SonderMind's calibration approach rests on the clinical team owning the definition of 'good' rather than engineer intuition, with labeled scenarios turned into evals that gate releases based on concrete questions (did the right category fire, at the right point, catching the right issue type).
  • The team open-sourced 200 clinically reviewed input guardrail scenarios and 100 output guardrail scenarios as a shared baseline for others building similar systems, while noting this isn't a replacement for building one's own learning loop.

Commentary (ours)

(ours) In Q&A, the speakers noted they had to disable the underlying frontier models' built-in safety guardrails on day one because those over-filtered their mental-health test scenarios entirely, which is a useful data point for anyone building sensitive-domain products on top of general-purpose model APIs rather than something covered in the main talk content.
