If you only read one thing

  • The Hub grew from about 20,000 models a few years ago to 3 million today, roughly a 150x increase, while serving over 14 million users (c1, c2, c3).
  • Regex-based search on the models collection worked at small scale but broke down as data grew, so the team moved to MongoDB Atlas Search (Apache Lucene) with tokens pre-computed at insert time (c6).
  • The next scaling step is MongoDB sharding, alongside migrating Kubernetes pod autoscaling from CPU/memory-based HPA to KEDA, which scales on real workload metrics like request queue depth (c7, c8).

02Why P99 matters more than P50
Slide at 05:20 · click any slide to enlarge

Why P99 matters more than P50

  • With 14 million users, even 1% experiencing slow search is about 140,000 people, so the team optimizes for P99 latency rather than median latency.
  • This drives several of the architectural choices described: precomputed search tokens, denormalized read collections, Apache Lucene-based full text search, Kubernetes autoscaling, and planned database sharding.

“P99 is much more important than P50 and we are paying a lots of attention to P99”

said at 04:50
03Metadata and binary storage are separated
Slide at 07:40 · click any slide to enlarge · 1 more from this section below

Metadata and binary storage are separated

  • MongoDB Atlas holds all Hub metadata (users, repositories, models, datasets, configuration, billing, access control) but not the model files themselves; the actual model artifacts, tokenizer files, and config files are stored separately in cloud object storage such as AWS S3.
  • This separation lets metadata and binary storage scale, and be optimized, independently.

“MongoDB does not store the models themselves. It stores everything about the models.”

said at 06:22
04From regex search to Atlas Search
Slide at 11:10 · click any slide to enlarge · 3 more from this section below

From regex search to Atlas Search

  • The original search implementation used MongoDB's regex operator against a search-token array on the models collection, sorted by a trending score recalculated every five minutes.
  • That approach worked while the dataset was small but broke down as it grew, so the team switched to MongoDB Atlas Search, an Apache Lucene-backed full text search layer accessed through the standard MongoDB aggregation pipeline's $search operator.

“This solution was working well as long as data set was small. Reax doesn't scale well.”

said at 10:37
05What scales next
Slide at 18:00 · click any slide to enlarge · 2 more from this section below

What scales next

  • The team runs a 7-node MongoDB replica set with a hidden analytics node isolated from production traffic, and plans to move to sharding, cutting the dataset into pieces across separate shards, since a single replica set will not keep up with continued growth.
  • At the Kubernetes level, the Hub currently uses a horizontal pod autoscaler (CPU/memory-based) plus Cast AI for node autoscaling, and plans to migrate to KEDA, which scales on real application metrics like requests per second rather than resource utilization alone.

“with 14 million users, 3 million models and our grow soon single MongoDB replica set will not be enough. The next step is sharding.”

said at 16:30

“HPA scale only based on CPU and memory. KDA scale on real application metrics like request per second or event loop utilization.”

said at 20:07
