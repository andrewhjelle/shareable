The evolution of agentic surfaces

Anthropic's Applied AI team traces Messages API to Agent SDK to Claude Managed Agents, and argues the harness - not the model - is now the limiting factor.

SpeakersGagan Bhat & Isabella He · Anthropic Applied AI Watchyoutu.be/K0X9QDRkIdg
harness designmanaged infrastructurelong-running agentsmemory & dreamingoutcomessessions

If you only read one thing

  • The thesis in one line: “when the model moves and the harness doesn’t, it degrades the agent” — harness fixes for one model become dead weight on the next (context anxiety on Sonnet 4.5, gone on Opus 4.5).
  • The architecture answer: decouple brain from hands, make the session log the durable source of truth — not the context window — and let either half die and resume.
  • The frontier features are memory compounding: dreaming (periodic batch rewrite of memory from transcripts) and outcomes (a grader agent that keeps the worker retrying until a rubric passes).
01Facts — what the talk actually says

Three surfaces in three years

Messages API (tokens in, tokens out; you hand-roll the loop) → Claude Agent SDK (the Claude Code harness in a box; you still host, scale, and secure it) → Claude Managed Agents: Anthropic runs the loop, sandbox, credentials, sessions, and observability, and what’s left to you is the part that differentiates — task, context, domain expertise.

“you own the product, you own the task, you own your context, and you call Claude managed agents to get production-grade infrastructure”

▶ watch at 05:33

Harnesses go stale

The engineering story that carries the thesis: Sonnet 4.5 exhibited context anxiety — wrapping up early as it neared its window limit — so the team built context resets into the harness. Opus 4.5 didn’t have the behavior; the fix became pure overhead (latency, cache discards). Harnesses encode assumptions about what the model can’t do, and those assumptions now expire on model-release cadence.

“when the model moves and the harness doesn't, it degrades the agent”

▶ watch at 08:48

The session log is not the context window

Everything the agent does is written play-by-play to a durable session (agent + environment = session; states idle/running/rescheduling/terminated). Because the log outlives the window, the harness can re-read slices of discarded context, resume after crashes on either side, and hand the same trace to your observability UI.

“the harness can actually just read in slices of that context from the session log into its current window”

▶ watch at 15:25

Lessons from the field

Four, from enterprise deployments: (1) credentials in vaults, decrypted only at tool runtime — the model never sees tokens; (2) decoupling bought 60% faster time-to-first-token at P50, 90%+ at P95, because reasoning starts while the container warms (or skips it); (3) session logs triple as observability, memory, and the raw material for dreaming; (4) security-conscious teams get self-hosted sandboxes in their own VPC and MCP tunnels that never touch the public internet.

“60% faster time to first token for P50 use cases or median use cases. And over 90% improvements in latency ... in P95”

▶ watch at 23:55

“you can effectively keep credentials away from your agent, and the model never sees your security tokens”

▶ watch at 22:32

Dreaming and outcomes

The two frontier features: dreaming runs transcripts + current memory through a periodic batch process that rewrites memory — self-improving agents, aimed at org-scale memory (runbooks, team knowledge). Outcomes attaches a separate grader agent to your rubric; the worker retries until the grader passes it.

“it allows us to extract new insights ... that essentially feed back and edit the memory as needed to make the next day's agent sessions automatically much more intelligent”

▶ watch at 27:52
02Context & cross-talk

Against the OpenAI talk (same stage, same week)

  • Agree: hours-to-days runs as the design assumption; both engineer around the finite context window (opposite mechanisms — OpenAI rations what enters, this talk makes what leaves recoverable); both attach sidecar judge agents to the loop, though for different jobs (completion grading here, safety escalations at Codex).
  • Split: Anthropic’s flagship surface is managed, Anthropic-run infrastructure (the Agent SDK stays as the self-host rung); OpenAI open-sources theirs and pushes features into an open API standard. Opposite ecosystem bets. (The harness-is-the-limiting-factor thesis is stated here, not there — the Codex talk is merely consistent with it.)
  • Contrast (not a disagreement): different bottlenecks in different architectures — container setup here, network transport at Codex’s inference speeds. Both can be true.

Extrapolation (ours)

“Harness staleness” transfers far beyond Anthropic’s stack: any workflow tuned around a model’s current weakness — retry wrappers, chunking regimes, context rationing — is a depreciating asset with a one-release half-life. Audit yours on every model upgrade the way this team audited context anxiety. And the managed-vs-open split is a genuine fork for anyone platform-shopping this year: portability argues for the open side, time-to-production for the managed side.
