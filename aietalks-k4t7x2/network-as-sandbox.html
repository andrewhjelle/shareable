What if the network was the sandbox?

SpeakerRemy Guercio · Tailscale Watchyoutu.be/BM2JX9hqsVQ
SecurityAgentic engineeringInfra & serving

If you only read one thing

  • Aperture puts a single provider API key behind a network gateway; agents in the sandbox get a tailnet identity/tag instead of a key, so access can be revoked or scoped without touching a key at all (c5, c7).
  • Because every request is forced through the network layer, Tailscale can show per-identity token spend, full request/response bodies, and every tool call/bash command an agent made, including a PR bot (c6, c7).
  • They deliberately built this at the LLM-request layer rather than the MCP layer, since a growing share of agent activity is unstructured bash/code execution that MCP-layer controls would miss (c8).
01A sandbox needs a boundary and permissions

The talk opens by reducing a sandbox to two components: a boundary (something in, something out) and a set of permissions/identity. The speaker argues today's two dominant ways of giving an agent permissions -- provider API keys, or OAuth/OIDC -- both place the credential inside the sandbox with the agent, meaning the agent itself holds the keys to its own access.

“first is a boundary, right? So, that's just there's a thing in and there's a thing out.”

▶ watch at 01:03
02API keys inside the sandbox are a liability

Putting a real (even synthetic) API key inside an agent's sandbox is risky because models can be resourceful about using or misusing keys, especially when run in a loop for a long time.

“the models are very clever at uh doing things with keys that they maybe shouldn't necessarily do”

▶ watch at 02:10
03Tailscale/WireGuard identity replaces the key

Tailscale is built on WireGuard, which issues keys to every node on a network; Tailscale layers identity on top so each connection carries user, group, and tag information -- for example a PR-review bot running in a GitHub Action can be tagged rather than issued a key, and access can be governed by that identity.

“WireGuard basically lets us, you know, give a set of keys to all of the, you know, any node on a given network.”

▶ watch at 03:10

“with each connection that happens over Tailscale uh you get a user if that user is logged into the device.”

▶ watch at 04:10
04Aperture: an LLM gateway with no key in the sandbox

Aperture takes a single API key per provider (Anthropic, OpenAI, Gemini, Vertex, Bedrock, etc.) and puts it behind the gateway; the sandbox connecting to Aperture has no key at all, only its network identity. The gateway dashboard shows token usage, cost per model, and, per identity, every request and response body -- including a demo where asking Claude Code to say hello cost 20 cents.

“you can take a single key from any given provider. You can put it on Aperture.”

▶ watch at 05:45

“with all of the context in Claude code, even if you just ask it to say hello, that costs you 20 cents.”

▶ watch at 07:50
05Full tool-call visibility, and why it's done at the LLM layer

Because every model call and tool call must pass through the gateway, the speaker says they have a guarantee of having seen every tool call an agent made -- not something read out of the container or the harness. The team originally considered building this at the MCP layer but moved to the LLM-request layer after finding that in their own internal usage, bash commands dominate agent activity over structured MCP tool calls.

“I have a sort of a guarantee uh that I've seen every tool call that this thing has ever like this thing has ever made uh through the instance.”

Commentary (ours)

Putting identity at the network layer instead of in the agent's credential store is a genuinely different tradeoff than the usual proxy/logging middleware pattern -- it's worth watching whether other vendors converge on doing this below the MCP layer once more agent traffic becomes raw code execution rather than structured tool calls (ours).
