The Next Medium: Why Real-Time Interactive Video Changes Everything

SpeakerAhmed Ahres · Reactor Watchyoutu.be/5dCAmSDOAjI
Generative mediaInfra & serving

If you only read one thing

  • Real-time video is pitched as a different medium, not faster batch generation: you can steer output mid-generation instead of getting back a finished file. (c2, c8)
  • The hard infra problems are session memory and sub-100ms global latency routing, not the model itself. (c6, c7)

01Real-time changes what a medium is, not just its speed

Ahres frames the talk around a historical analogy: GPS didn't just make maps faster, it created Uber, an application that couldn't exist with a static, pre-produced map. He argues the same shift is coming to video: today's generators (Veo, Sora, Kling) return a finished, unchangeable file, which he calls a 'slot machine' — you prompt, you get a result, and you can't touch it.

“Then GPS came. GPS made it real time.”

02Three categories of real-time model

Reactor groups the current landscape into three types: infinite, interactive, real-time generators like the one behind Vio/Sora but without the 5-30 second cutoff; controllable-character world models like Google's Genie 3, aimed at games, interactive fiction, and robotics training data; and live, interactive avatars, which the talk describes as still 'kind of weird' and not yet solved.

“The first one is these are Vio, think about Vio or Sora, but real-time and interactive”

▶ watch at 04:36
03Control and advertising as the near-term unlocks

The talk's two concrete near-term use cases are creative control (real-time steering ends the 'slot machine' problem for filmmakers and content creators) and in-video advertising: inserting a relevant ad or logo live, based on what a viewer has been looking at, rather than pre-producing creative. Ahres expects brand caution to slow this but predicts it happens eventually.

“real-time actually ends the slot machine type of mentality and actually gives you the the control that you need”

04The infra problem: streaming, memory, and global latency

Ahres argues building infrastructure for real-time generation is a different engineering problem than batch inference: it requires continuous streaming rather than request/response, live session memory (current live models still lose track of what happened when a character turns around), and sub-100ms latency anywhere in the world, which means routing users to geographically local GPUs rather than a single cloud region.

“one of the things that live live real-time models struggle with is memory”

▶ watch at 12:22

“it needs to be sub-100 millisecond latency anywhere you are”

▶ watch at 12:52
05No evaluation standard exists yet

Asked directly how to measure consistency, Ahres says the entire research community — including DeepMind — has not solved evaluation for real-time video models. Fidelity (pixel quality) is tractable, but judging consistency and algorithmic quality is currently done by human eyeballing, not a benchmark.

“evaluation for these real-time models is an unsolved problem”

Commentary (ours)

The GPS/Uber and film/Instagram analogies are doing a lot of argumentative work here and are worth treating as rhetorical framing rather than established fact (ours) — the claim that real-time necessarily creates new categories of application, rather than just faster versions of existing ones, is plausible but unproven for video specifically, and Ahres himself concedes evals don't exist yet to measure whether the real-time output is actually good.
