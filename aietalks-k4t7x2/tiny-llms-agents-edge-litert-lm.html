If you only read one thing

  • Function Gemma, a 270-million-parameter model dedicated to function calling, reached 85-90% reliability on Google's internal eval across 10 voice-to-function-calling tasks for Android developers.
  • Gemma 4's smallest edge models are named for their RAM footprint (E2B needs about 2 billion parameters resident in RAM), and measured on-device throughput ranges from about 133 tokens/sec on a Raspberry Pi up to thousands of tokens/sec on a high-end Android GPU.
  • For models under 1B parameters, Brick says fine-tuning on synthetic data typically gains 20-40 points on a given eval versus prompting alone, which is why Google's own on-device apps (like the Eloquent transcription-polishing app) use separately fine-tuned small models rather than one combined model or a skills-based approach.

02Gemma 4 edge model sizes and measured throughput

Gemma 4 edge model sizes and measured throughput

  • Gemma 4's E2B model is named for needing about 2 billion parameters resident in RAM to run, since RAM footprint is a key constraint for on-device deployment.
  • Brick's team measured throughput ranging from thousands of tokens per second on a high-end Android GPU or MacBook down to roughly 133 tokens per second on a Raspberry Pi, sufficient for simple image-analysis use cases.

“E2B is called that because it has it um only needs about two billion parameters to be present in RAM to to run the model”

said at 11:30

“on a Raspberry Pi we can get um about 133 tokens per second which is sufficient to do um kind of simple image analysis use cases with reasonable latency”

03On-device agent skills: disclosure and constrained decoding
Slide at 24:30 · click any slide to enlarge · 8 more from this section below

On-device agent skills: disclosure and constrained decoding

  • Google's agent-skills architecture only loads a one-line description of each skill into the model's context by default; the model requests the full skill contents only if it decides that skill is relevant, which keeps context usage low on edge-class models.
  • Separately, the runtime applies constrained decoding specifically to tool-calling outputs, which Brick says matters much more for reliability on small models than on larger ones.

“the way we've structured the skills is there's a kind of oneline description, the oneline descriptions of the skills is what the agent sees and then if it thinks that sounds interesting, then it asks for more”

said at 24:08

“for really small models on device this is a very helpful tool that helps us um have stronger guard rails for the model uh so that we can up the quality so we have something that is um useful in production”

said at 28:47
04Fine-tuning tiny models
Slide at 61:40 · click any slide to enlarge

Fine-tuning tiny models

  • For sub-1B-parameter models, Brick reports fine-tuning typically gains 20-40 points on a given eval compared to prompting alone, calling it essential for most narrow tasks at that size.
  • The standard workflow generates a low-digit-millions-to-tens-of-millions-scale synthetic dataset with a larger cloud model, then fine-tunes the small base model on that data to produce a derived model for a specific narrow task.

“our experience is on a given eval um like fine-tuning is between 20 and 40 points on the eval. So it's like it's a really really significant win for tiny models, right?”

said at 65:40

“once you have a few, you know, lowdigit millions or tens of millions depending on how ambitious you want to be of synthetic data, you kind of put that into a fine-tuning workflow”

said at 61:31
05Separate small models instead of one combined model
Slide at 58:40 · click any slide to enlarge · 8 more from this section below

Separate small models instead of one combined model

  • In Google's own Eloquent app, transcription and text-polishing are handled by two separate fine-tuned tiny models rather than a single combined model, even though one model could technically do both.
  • Brick frames this as a mobile-development modularity pattern: separate models are easier to debug and can be reused independently across other features.

“We could probably have built like one LLM to do all of this, right? But it's actually like sometimes like one of the other realities of mobile development is”

said at 59:26

Commentary (ours)

The talk is a product/engineering walkthrough rather than an independent benchmark -- the reliability and throughput figures are Google's own internal evals on their own runtime, not third-party verified numbers (ours).
