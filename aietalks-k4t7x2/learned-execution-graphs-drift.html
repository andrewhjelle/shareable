If you only read one thing

  • Execution graphs are short-lived, per-request DAGs (distinct from persistent property graphs like Neo4j) used to represent and baseline how a request actually flows through services (c1, c2).
  • A cheap tier-one check (like an airport boarding-pass glance) runs first, and only escalates to deeper analysis when the observed request deviates from its learned baseline (c3).
  • Drift is split into structural (nodes added/removed), volume, and covariate categories (e.g., a service that was 60% local / 40% international traffic seeing that mix shift), each requiring a different baseline response (c4, c6).

Execution graphs: modeling request flow as a short-lived DAG

  • Pandya distinguishes execution graphs, short-lived structures built to model how one request moves through a system, from persistent property graphs like those queried in Neo4j.
  • Representing the request-processing pipeline (edge layer, gateways, auth, orchestration, downstream services) as a DAG orders the expected sequence and captures what context passes between nodes, including loops as separate trackable entities.

Three categories of drift, each needing a different baseline

  • Pandya categorizes drift as structural (a node is added or removed from the pipeline, requiring the baseline to account for the new step), volume-driven (a service can't keep up with increased request load, requiring scaling or async handling), and covariate (the underlying traffic mix shifts, e.g., from mostly local to more international requests, requiring separate baselines per segment even though nothing is technically broken).

04Training the baseline and rolling out automated response

Training the baseline and rolling out automated response

  • The baseline was trained by injecting millions of OpenTelemetry traces over seven days and introducing synthetic problems before anything went live.
  • Once a fix or automation is identified, it's rolled out gradually, first to a small percentage of machines, verified, then expanded to the full node population.

05Operational lessons: tune structural-change detection and use per-client baselines

Operational lessons: tune structural-change detection and use per-client baselines

  • Pandya flags that a delayed telemetry event from one node can look like a structural change (missing node) if detection isn't tuned to distinguish delay from removal.
  • He also recommends against one generic baseline for all traffic of a type, e.g., using separate baselines for real-time payments versus wire payments rather than one number for all POST requests.
