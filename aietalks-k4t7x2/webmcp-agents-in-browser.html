Compares MCP transports (stdio vs HTTP), shows a working MCP app (an embedded comic reader with call-server tool calls), and previews WebMCP, an emerging browser API that lets any webpage expose its own JS functions as agent tools instea...

If you only read one thing

  • MCP apps are sandboxed single-file HTML/CSS/JS bundles (no external network access, no local storage) that agents can render inline, letting a tool return a full mini-UI instead of a wall of text.
  • MCP resources are a good fit for pre-priming an agent's context with docs, but the spec is loosely implemented and the speaker can't find a client that surfaces them in its UI.
  • WebMCP (imperative via navigator.modelContext.registerTool, or declarative via form attributes) lets a webpage expose its own JS functions directly as tools so browser agents stop relying on screenshots or DOM traversal, but it is early and not a strict MCP-spec implementation.

This traces the contrast the talk draws between screenshot/DOM-based browser agents and WebMCP letting a page register its own JS tools; the standard is still being worked out by a standards group (ours).

Two MCP transports, two different setup costs

  • stdio spawns the MCP server as a local process controlled by the client, communicating via standard input/output and staying alive for the session; it requires users to edit a JSON config with command-line arguments.
  • HTTP runs the server as a web service the user just adds by name and URL in their client's connector settings, working well with serverless setups, but the speaker notes it is still not easy to get non-technical users to add an HTTP MCP server themselves.

02MCP apps: sandboxed inline mini-UIs

MCP apps: sandboxed inline mini-UIs

  • MCP apps bundle HTML, CSS, and JavaScript into a single file returned by a tool call and rendered inline in the agent chat, demonstrated with a comic-reader tool ('get page') that looks and behaves like the live website.
  • Because the app runs sandboxed in an iframe, all assets must be embedded as base64, there is no local storage or cross-iframe state, no direct network access (tool calls must go through call_server), and links require explicit host permission.

“They're single HTML files. So, everything that you need there has to be embedded base64”

03MCP resources are underused because clients don't expose them

MCP resources are underused because clients don't expose them

  • The speaker argues MCP resources are the right vehicle for loading full reference material (e.g., all comic transcripts) into context for meta-analysis, rather than looping many individual tool calls, and that agents dislike using tools to fetch markdown into context.
  • She reports she cannot find a client that actively surfaces resources in its UI despite the spec existing, and asks agent-harness builders to implement resource support.

“I would really love to use MCP resources, which are the perfect vehicle for this and skills and so many other things, but the spec is loosely defined”

said at 10:22

“it is loosely implemented, and I cannot find a client where I can actively get to these resources. They're on the server. They just ain't visible in your UI”

04WebMCP: turning any webpage into a tool server
Slide at 17:40 · click any slide to enlarge · 8 more from this section below

WebMCP: turning any webpage into a tool server

  • Browser agents today struggle with navigation because they rely on screenshots or DOM/XML traversal, both compute- and token-intensive.
  • WebMCP, demoed via the MCP-B debugging extension, lets a page register JS functions as tools an agent can call directly -- either declaratively by adding tool-name/tool-description attributes to a form, or imperatively via navigator.modelContext.registerTool with a name, description, input schema, and callback.
  • The speaker stresses WebMCP takes inspiration from MCP but is not a one-to-one spec implementation, and the standard is still being worked out by a standards community group.

“they rely on taking screenshots and guessing how to use the navigation or traversing the DOM, which burns tokens chewing up XML, which is really not a great use”

said at 17:35

“Web MCP is to MCP as a JavaScript is to Java. Inspired by riding the hype wave of But if you actually look under the hood, it's taking inspiration”

said at 18:06

Commentary (ours)

WebMCP's positioning as 'JavaScript is to Java' relative to MCP is a useful caveat for anyone assuming API compatibility between the two; treat WebMCP integrations as bespoke until the spec stabilizes (ours).
