01Context engineering is mostly agentic search

Context engineering is mostly agentic search

  • The speaker frames context engineering as deciding what from available context sources goes into the context window, and argues the underlying search tool or tools doing that selection deserve more credit than they usually get -- calling it her personal hot take that context engineering is roughly 80% agentic search.
  • She contrasts this with early RAG's fixed retrieval pipeline, where a query is always run against a database regardless of whether context is actually needed, which in the worst case can confuse the LLM with irrelevant retrieved information.

02Search tools fail in a few predictable ways

Search tools fail in a few predictable ways

  • Working with internal and external teams at Elastic, the speaker lists three recurring failure modes: the agent decides it can answer from parametric knowledge and skips retrieval entirely, the agent calls the wrong tool (e.g. web search instead of database search), and the agent generates the wrong search parameters, particularly as tool parameter lists grow more complex.
  • In audience Q&A she adds that a more powerful model measurably reduces this parameter error rate, though a strong model alone doesn't eliminate errors.

03Live demo: a narrow semantic search tool breaks on an unfamiliar query

Live demo: a narrow semantic search tool breaks on an unfamiliar query

  • A semantic search tool built with a fixed top-3 result limit correctly found a talk about regulatory constraints, but when asked about a query it hadn't seen before ("GEA"/"GEPA"), it returned unrelated results, including a talk about DeepMind's Gemma models.
  • The speaker concludes the tool is useful only for a very narrow scope of use cases, motivating the rest of the talk's move toward more general-purpose and skill-augmented tools.

04The shell/bash tool is versatile -- and can 'cheat' at semantic search

The shell/bash tool is versatile -- and can 'cheat' at semantic search

  • A shell or bash tool lets an agent run arbitrary terminal commands, making it able to explore local files, run custom database CLIs, or hit an HTTP API via curl.
  • In a demo, an agent given only grep chained together a list of synonyms (regulation, compliance, GDPR, governance) to approximate a semantic query and found the right session, which the speaker calls surprisingly good bash-based cheating at semantic search, though not necessarily the most efficient approach.
  • She separately notes agents are notoriously bad at counting, so having a search tool perform aggregation itself is more efficient than dumping all results into the context window for the agent to count.

05Practical guidance: combine specialized and general-purpose tools

Practical guidance: combine specialized and general-purpose tools

  • The recommendation is to curate a combination of specialized tools (simple parameters, low floor, few agent mistakes) and general-purpose tools (shell tool or raw query execution, high ceiling for unexpected questions), rather than relying on one tool for everything.
  • In Q&A, the speaker cites a Vercel blog post benchmarking agents with a bash tool, a database tool, and a hybrid of both, finding the hybrid agent achieved the highest accuracy by first using the database tool and then verifying results with the shell tool.

Commentary (ours)

The Vercel hybrid-tool result (database tool first, shell tool as verification) is a specific enough pattern that it's worth checking against our own agentic search setups -- using a cheap general-purpose tool as a sanity check on a specialized tool's output, rather than picking one or the other (ours).
