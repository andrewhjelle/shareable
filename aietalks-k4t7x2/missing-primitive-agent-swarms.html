The Missing Primitive for Agent Swarms

SpeakerLou Bichard · Ona Watchyoutu.be/5Sui_OnSRlY
Agentic engineeringCoding agentsContext engineering

If you only read one thing

  • A software factory is defined as incrementally moving the human out of the loop in the SDLC, not just running many parallel coding agents at once.
  • Runtime, orchestration, and triggers for background agents are effectively solved (VMs beat containers for isolation because containers aren't a bulletproof security boundary and suffer noisy-neighbor compute contention); coordination between agents is the missing piece.
  • GitHub is not a coordination layer for agents -- PRs, merge conflicts, and CI fixes get too noisy for a human to know when to intervene -- and agents don't respect coarse five-step SDLC diagrams because each step hides many micro-steps.
01Defining the software factory

The speaker defines a software factory as the commitment to incrementally moving the human out of the loop within the SDLC, distinct from an individual running many parallel coding agents at once. He notes this framing is still early -- many people at the conference were not yet thinking in these terms.

“I added a definition in this slide as well just to quickly define what I believe to be as a software factory which is sort of the commitment to incrementally moving the human out of the loop within the SDLC”

02Large companies are already running background-agent infrastructure at scale

Stripe built an internal system called 'minions' on top of existing infrastructure to drive thousands of pull requests with coding agents; Ramp built a similar internal system called 'inspect.' Ona's own 'fleet' feature automates agents across many repositories for tasks like CVE remediation or bumping test coverage, calling these individually simple but hard to run consistently across thousands of teams/repos.

“Stripe has one. There's what they call minions which is built on top of their existing infrastructure where they've then plugged in these coding agents and they're able to then drive thousands of pull requests inside of inside of Stripe”

▶ watch at 03:07
03Harness engineering: encoding process into the repo

Referencing OpenAI/Ryan's harness engineering blog, the speaker frames harness engineering as an extension of context engineering: everything in a repository -- skills, agents.md, unit tests, and any other feedback source -- that helps an agent complete SDLC steps. In practice this means running the agent, observing where it gets lost, and encoding that knowledge back into the repo or context.

“really another extension on context engineering whereby everything in your repository from skills to agents.md to unit tests, everything that you could possibly use to give feedback to your agent is for me harness engineering”

▶ watch at 05:12
04VMs, not containers, for agent isolation

Ona runs coding agents inside full virtual machines rather than containers, because containers are not a bulletproof security isolation boundary and suffer noisy-neighbor compute contention when run on Kubernetes/pods. Runtimes, orchestration (scaling agents up/down), and triggers (webhooks, PR/ticket creation) are described as largely solved problems at the infrastructure level.

“a container is not bulletproof isolation boundary. So, if you have an agent running in there and you want to secure it, you this challenge is for a container”

▶ watch at 06:45
05What's actually missing: coordination

The speaker argues agents don't respect the coarse five-step SDLC diagram teams typically draw, because each step hides many micro-steps agents must be taught to follow deterministically; context window consumption degrades agent effectiveness, and agents tend to skip steps (e.g., skipping tests) out of sycophancy. GitHub and tools like Linear are reused human-oriented tools that make poor coordination layers for agents, leaving coordination as the primitive still missing -- something the speaker believes may be solved via state machines, durable execution, and a CLI-based gateway construct.

“GitHub is not a coordination layer for agents. It gets incredibly overwhelming. You know, you can have your agents raise a pull request, you can review it, you can then solve the merge conflicts, you can fix the CI build, etc.”

“the SDLC is not this. It you know, this is the conceptual SDLC that we present and talk about with each other. Very coarse-grained five steps of the SDLC. Agents don't respect this”

Commentary (ours)

The claim that runtime/orchestration/triggers are 'solved' reflects Ona's own product maturity in that area; the honest signal here is what's still unsolved (coordination), which is a more defensible read on where the field actually stands (ours).
