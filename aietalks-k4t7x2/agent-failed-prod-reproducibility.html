Your Agent Failed in Prod. Good Luck Reproducing It.

SpeakerTisha Chawla & Susheem Koul · Microsoft Watchyoutu.be/Lc8zRh9muoY
Agentic engineeringEvals & benchmarksInfra & serving

If you only read one thing

  • Setting temperature to zero doesn't make an agent reproducible -- it's not even bitwise deterministic on real hardware because of batch-dependent floating-point ops and MoE routing, and it just repeats the same reasoning error identically.
  • The real target is replayability (capturing what a run did, well enough to debug it) rather than bitwise determinism (guaranteed identical output), and recording should happen at method-level 'boundaries' rather than the network layer.
  • Chronicle's boundary annotation records every input/output at each node so failed production traces can be replayed with the LLM stubbed out, turning them into free, rerunnable, deterministic regression tests.
01A trading agent mis-parses a dollar amount as a share quantity

The talk's running example: a user asks an agent to sell $1,000 of stock, but the agent puts the raw number 1,000 into the order quantity field instead of computing shares, selling 1,000 shares (~$190,000) instead of $1,000. The API returned a clean 200 OK with zero exceptions or alerts, so nothing in the dashboards flagged the error.

“Instead of doing the math, the agent sells the raw number 1,000 and dumps it straight into the quantity field”

▶ watch at 01:34
02Temperature zero doesn't fix or reliably reproduce the bug

The speakers argue that setting temperature to zero is a common but flawed reflex: it doesn't fix a broken reasoning path, it just makes the model repeat the same logical error the same way. They cite hardware-level non-determinism -- floating-point non-associativity, batch-dependent execution, and mixture-of-experts routing that depends on what else is in the batch -- as reasons temperature zero isn't even truly bitwise deterministic on real GPU infrastructure.

“Setting the temperature to zero doesn't fix a broken reasoning path. It just means the model is going to make the exact same logical error, the exact same way, at the exact same time”

▶ watch at 02:37

“Running the same prompt a thousand times can still return dozens of completely different responses just due to the underlying GPU non-determinism and the MOE architectures which are there”

▶ watch at 03:09
03Replayability, not bitwise determinism, is the right target

The speakers distinguish bitwise determinism (same input, same output -- not available from hosted APIs and not actually wanted, since randomness is part of what makes the model good) from replayability (capturing a run well enough to debug it later). They recommend recording at method-level 'boundaries' rather than the network layer, since large parts of an agent's work (local retrieval, in-process tools, memory) never touch the network.

“The other one is replayability, which is re-validates a run that already happened well enough to debug it. That's observability. You don't need the model deterministic. You need the run recorded, and you don't freeze the model. You capture what it did”

▶ watch at 05:44

“Record at the boundary instead because you need to capture what enters each node and what leaves it”

▶ watch at 06:14
04Chronicle: boundary annotations turn failed traces into test cases

Chronicle is a proof-of-concept tool that annotates any node (tool call, LLM call, retrieval) with a boundary annotation recording every input/output pair plus metadata like model or code version. Because the LLM can't be controlled, the recommended fix is guardrails on tools; recorded traces can then be replayed with every node except the changed one stubbed, so a full agent run becomes a rerunnable, free, model-free test case for deterministic nodes, while subjective aspects like tone or trajectory still need LLM-as-judge behavioral testing.

“You cannot control the LLM. That's what this entire discussion is about. You cannot enforce bitwise determinism. What you can do is you can put guardrails on your tools to enforce some level of uh credibility on your production agent”

▶ watch at 09:49

“Now, when we talk about testing in AI agents, I want to draw a very clear distinction here. There are two ways of testing AI agents, and both of them are equally important”

▶ watch at 11:56

“keep the generation time variation alive. Don't try to pin the temperature to zero. After all, that is what brings the agency into your agent”

▶ watch at 13:28

Commentary (ours)

The deterministic-vs-behavioral testing split maps well onto the broader agent-testing problem of separating what can be pinned down (tool calls, guardrails) from what can't (LLM judgment calls), and the boundary-annotation pattern looks portable to any agent framework with a clear node/edge structure, not just this specific trading example (ours).
