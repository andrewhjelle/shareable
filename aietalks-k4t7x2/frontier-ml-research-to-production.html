If you only read one thing

  • The handoff problem: software engineers know production-grade code but not ML research methodology, while ML researchers know the latest papers but haven't built production APIs.
  • A 'research prototype taxonomy document' (domain context, business goal, type contract, persistence layer, system architecture, merge plan) makes prototypes legible to engineers joining the project.
  • A Python mono repo of one-researcher-per-microservice, decoupled behind a gateway, plus Graphite stacked diffs for asynchronous PR review, is how prototypes get decomposed and shipped.
▣The system in one picture (ours, from the slides and the transcript)

This traces the handoff Higharc uses to get a research prototype into production: a taxonomy document makes it legible, the mono repo of one-researcher-per-microservice isolates the work, and Graphite stacked diffs let subject matter experts review slices asynchronously (ours).

01The two-sided handoff problem
Slide at 01:30 · click any slide to enlarge · 7 more from this section below

The two-sided handoff problem

  • Software/platform/infrastructure engineers are familiar with building robust production-grade code but not with computer vision or LLM training methodology, while ML researchers are current on the latest papers and can combine concepts creatively but haven't typically been responsible for production-grade APIs.
  • The talk frames closing this gap as a systems and process problem with three levers: research legibility, code repository structure, and decomposition into reviewable PRs.

“our uh ML researchers who are very up-to-date with the latest papers and can uh pull together these concepts in novel and creative ways to develop new features”

Research prototype taxonomy document

  • Modeled on the pragmatic-engineer-style technical design document, this document (kept in Notion) captures domain context for engineers unfamiliar with the field, the business goal, the type contract between the ML repo and the core product repo, the persistence layer, overall system architecture, and a merge plan, before software engineering help gets pulled in.

“how important it is to write out technical design documents, request for comment, whatever you want to call it, specifications before building software as a way to align teams”

“we call the research prototype taxonomy document. So, it's really just a technical design document from software engineering uh with some specific twists”

03Mono repo of decoupled microservices
Slide at 06:40 · click any slide to enlarge · 8 more from this section below

Mono repo of decoupled microservices

  • The ML/AI work lives in a separate, all-Python mono repo of cleanly isolated, fully decoupled microservices behind a single gateway, structured with roughly a one-to-one ratio of researcher to microservice, each with a simple layered architecture (API, business logic, data) and standardized build/dependency tooling.

“we basically have a a separate um repository from our core product repo and this is uh all Python based, right? It's all AI ML stuff and it's basically a mono repo of uh cleanly isolated and fully decoupled”

said at 06:43

“it's pretty much a one-to-one researcher to microservice ratio. So, we find that works really well.”

said at 07:16
04Decomposing prototypes with Graphite
Slide at 11:20 · click any slide to enlarge · 8 more from this section below

Decomposing prototypes with Graphite

  • Once a prototype is mapped out via the taxonomy document, it gets sliced along dependency-graph axes and decomposed into stacked diffs using Graphite, which supports asynchronous review so specific subject matter experts can review tightly scoped slices in parallel rather than blocking on one large PR.

“we really like Graphite because it allows for asynchronous review, right? I could be working on a PR all the way up here while a domain specialist is still reviewing a different PR.”

said at 11:24
05Diagnostic checkpoints
Slide at 13:00 · click any slide to enlarge · 4 more from this section below

Diagnostic checkpoints

  • As a health check across the three levers, the talk suggests asking whether it's obvious where staff should concentrate effort and what tasks to pluck off for production -- if there's ambiguity, the research legibility process needs revisiting.

“is it obvious where they should concentrate their efforts? And is it clear uh what kind of tasks they need to pluck off to bring this prototype into production?”
