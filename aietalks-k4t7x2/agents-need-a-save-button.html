If you only read one thing

  • Traces alone are read-only telemetry disconnected from the runtime state (variables, filesystem, code) that produced them; a durable runtime layer beneath the harness can checkpoint that state so executions can be replayed and altered at any point (c1, c9)
  • DoorDash's replay-based simulation of customer bots cut a multi-hour manual review process to about 5 minutes with hundreds of simulations and 90% fewer hallucinations, staying within two points of production behavior (c3)

The problem: traces are read-only, disconnected from runtime

  • The speaker contrasts agents with documents, which have had persistent save/auto-save since the 1980s.
  • Agents today have only traces -- emitted telemetry of tool inputs and outputs -- which are disconnected from the actual runtime: in-flight variables, filesystem state, and the code path taken are lost once the trace is stamped.
  • He frames this as a missing link between observability spans (e.g.
  • OpenTelemetry) and the execution itself.

“A trace gives you the emitted telemetry data of how an agent calls tools in the input and output of that state.”

Why a save button matters: replay and what-if questions

  • A save/checkpoint capability enables replay: going back to a point in an agent's history and asking what-if questions, such as swapping the model, mocking a tool's return value, or intentionally degrading an input.
  • The speaker describes an emerging category of tooling that sits below the agent harness/framework, adding a durable runtime and augmenting traces with the code execution and environment needed to reconstruct full state.

“save allows you to replay. You can go back in history and ask the what if question.”

said at 01:35

Closing the loop: checkpoint, replay, diff, decide

  • The proposed methodology is to checkpoint state during production runs, replay a cohort of runs that matter (expensive, slow, or risky ones), diff the replay against the original baseline, and then decide whether to route/ship the change.
  • The speaker describes this as evaluating using production checkpoints rather than synthetic tests, and cites DoorDash's blog post (June 1) describing a simulated environment that replayed customer bots, cutting a process that took hours down to about 5 minutes across hundreds of simulations with 90% fewer hallucinations while staying within two points of observed production behavior.

“now they've reduced it to 5 minutes uh with hundreds of simulations, have 90% less hallucinations, and they're”

“it's basically evaluating using your production checkpoints. So, checkpoint replay diff decide. And this is really the methodology”

04Demo: Kitaru, a runtime layer for checkpoint and replay
Slide at 04:40 · click any slide to enlarge · 8 more from this section below

Demo: Kitaru, a runtime layer for checkpoint and replay

  • The speaker demos Kitaru, a tool recently launched by ZenML (an orchestration-space company he co-founded) that adds a runtime layer below the agent harness and connects to traces to checkpoint state at each tool call, storing code, artifacts, and environment together.
  • In the demo he replays a customer-support/refund agent from a chosen checkpoint with a swapped model (GPT-5 Nano) and separately with a mocked policy-lookup tool, then uses a diff view to compare the original run against both forks side by side, including a Kitaru MCP server that can analyze a JSON cohort report for red flags.

“we're going to be using a tool called Kitaru. Kitaru is a very new tool that is launched by the team at uh ZenML”

05The risk of trusting a single replay
Slide at 13:30 · click any slide to enlarge · 8 more from this section below

The risk of trusting a single replay

  • The speaker warns that a naive model swap often looks cheaper and faster on a single replay but can create a false economy if quality drops, citing a study from BrainTrust.
  • He adds a Tau-bench-related figure: a model that passes 60% of the time is only self-consistent about a quarter of the time, meaning one replay is an anecdote and cohort-level analysis is needed.
  • In his own demo, a cohort replay across many support cases -- not just one -- led the agent's own analysis to conclude the cheaper model should not be shipped, despite the single replay looking favorable.

“what I've personally seen is that having a naive model swap usually or often times doesn't work”

Commentary (ours)

The DoorDash and Tau-bench figures are cited secondhand from external sources rather than independently verified in the talk, and the closing demo verdict comes from a tool built by the speaker's own company, so the specific numbers (90% fewer hallucinations, 60%/25% self-consistency) are worth treating as illustrative rather than benchmarked claims about replay tooling in general.
