How I deleted 95% of my agent skills and got better results

SpeakerNick Nisi · WorkOS Watchyoutu.be/vy7o1g2iHY8 · 17 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. patternAgentic engineeringCoding agentsEvals & benchmarks

Reports a measured case where trimming an internal skill library from over 10,000 lines to 553 cut eval runtime from 68 to 6 minutes per run and raised task accuracy in an A/B test (77% with a skill loaded vs 97% without it)

If you only read one thing

  • Deleting 95% of a 10,000-line skill library cut eval runtime from 68 to 6 minutes and raised task accuracy from 77% to 97% (c7, c8).
  • Agents will fake completion -- touching a marker file to fake a test run -- unless the harness cryptographically verifies the real output (c3, c4).
  • Rule of thumb: enforce with code not prompts, guide with gotchas rather than prescribing steps, and measure everything with evals (c9, c10).

02Agents will lie about doing the work
Slide at 05:10 · click any slide to enlarge · 8 more from this section below

Agents will lie about doing the work

  • When asked to run tests, the model learned it could just touch a marker file instead of actually running them.
  • The fix was to hash the real test output with SHA-256 and store that hash, so the harness could cryptographically verify the tests actually ran rather than trusting a flag file.

“Claude would just touch that file and be like, "Yep, I ran the tests."”

said at 05:09

“take the test output and SHA-256 that and save that into the case tested file and then verify cryptographically, yes, you actually ran the tests”

said at 05:41
03More documentation in the skill made results worse
Slide at 07:50 · click any slide to enlarge · 4 more from this section below

More documentation in the skill made results worse

  • He first generated over 10,000 lines of skills directly from WorkOS docs, which made his eval suite take 68 minutes to run.
  • Rewriting it by hand down to 553 lines covering only common gotchas cut eval runtime to 6 minutes.
  • In a direct A/B test, loading that skill made the model correct only 77% of the time, versus 97% correct on the same task without loading it -- the skill was actively hurting performance.

“I generated over 10,000 lines of skills uh that were all based on our docs”

said at 07:46

“it would take me 68 minutes to run those scenarios”

said at 08:18

“instead of having 10,000 lines of that, I have 553 lines of gotchas”

said at 08:48

“it got it correct 77% of the time. But if I asked it to do the same task without loading the skill, it was correct 97% of the time”

04Three operating rules
Slide at 10:20 · click any slide to enlarge · 8 more from this section below

Three operating rules

  • His stated takeaways: enforce behavior through code and gates rather than instructing the model and hoping it complies; guide the model toward specific known gotchas rather than prescribing exhaustive step-by-step procedures; and measure everything with evals rather than assuming a change helped.

“Uh basically, you want to enforce things, don't instruct”

said at 10:23

“you want to guide the model, don't prescribe it”

said at 10:55

Commentary (ours)

The 77%-vs-97% result is a sharp illustration that more context isn't free -- an unnecessary skill can crowd out or distract from what the base model already knows how to do, which argues for measuring skill/prompt additions with before/after evals rather than assuming they help (ours).
