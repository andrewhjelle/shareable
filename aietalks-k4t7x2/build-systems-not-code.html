Build Systems, Not Code

SpeakerAngie Jones · Agentic AI Foundation Watchyoutu.be/ZD9-4fW2HhM · 19 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. patternAgentic engineeringContext engineeringMemory

Walks through applying classic software-engineering discipline (decomposition, separation of concerns, idempotency, threat modeling) to agent design using a concrete house-hunting agent example

If you only read one thing

  • An agent is not the system -- it's one part of a larger system with files, tools, humans, and other agents, so design the whole system before letting a coding agent build it (c1, c2).
  • Giant prompts are the agentic equivalent of a bloated class; decompose them into skills, schemas, scripts, and sub-agents by separating concerns (c3, c4, c5).
  • Use code for tasks with an exact answer, agents for judgment, and humans for authority, and give agent outputs a structured contract so downstream systems can act on them (c6, c7).

Systems thinking: the agent is part of a system, not the system

  • Using a house-hunting agent ('Relocation Scout') as the running example, the speaker argues an agent should be treated as one component with boundaries, responsibilities, dependencies, and failure modes inside a larger system of files, tools, humans, and other agents.
  • She warns against just letting a coding agent build the agent without first thinking through that whole environment.

“an agent is not the system, right? It's part of the system. And that system has files and tools, humans, even other agents”

02Workflow design and the giant-prompt code smell
Slide at 03:20 · click any slide to enlarge · 7 more from this section below

Workflow design and the giant-prompt code smell

  • She argues an agent needs a workflow, not just a goal, with every run ending in stop, retry, or escalate, and that this path shapes the rest of the architecture.
  • She identifies the 'giant prompt' as the agentic equivalent of a bloated class or function -- a prompt that accretes edge cases, safety rules, and exceptions until the agent starts drifting -- and recommends decomposing it into distinct jobs.

“an agent needs more than a goal, it needs a path”

said at 03:08

“That's four different jobs crammed into a single prompt. And then you wonder why your agent is drifting and not sticking to the script. The script is too long”

said at 05:42
03Separation of concerns: skills, schemas, scripts, sub-agents
Slide at 06:40 · click any slide to enlarge · 8 more from this section below

Separation of concerns: skills, schemas, scripts, sub-agents

  • For Relocation Scout's four crammed-together jobs, she assigns each to the tool suited for it: listing normalization becomes a reusable skill, the short-list format becomes a schema, commute calculation becomes a deterministic script, and neighborhood research becomes a sub-agent, since sub-agents work best scoped to one task without full session context.

“So, the process to normalize the listing, should that stay buried in the prompt? Or maybe it actually become a skill”

said at 06:46

“Architecturally, they're sort of like functions, right? So, you give them one specific task to do. You call them when it needs to be done. And they can do it really well because that's all that they have in scope”

said at 08:20
04Code for determinism, agents for judgment, humans for authority
Slide at 11:00 · click any slide to enlarge · 1 more from this section below

Code for determinism, agents for judgment, humans for authority

  • Her rule of thumb: use code when a task has an exact answer (e.g., calculating commute time, deduping listings), use the agent's model for interpretation, ambiguity, and judgment, and reserve final authority (e.g., approving a house tour) for the human.

“use code for determinism, use agents for judgment, and then use humans for authority”

said at 10:57
05Structured contracts, idempotency, and threat modeling
Slide at 11:20 · click any slide to enlarge · 8 more from this section below

Structured contracts, idempotency, and threat modeling

  • She recommends writing agent decisions into a structured, queryable memory (she uses Compendium Wiki) rather than free-form text whenever another system must act on the output, since a contract makes the handoff safe.
  • She also describes designing for idempotency -- so a retried run doesn't repeat an already-completed action like sending an email -- and threat modeling untrusted input (listing copy, forum posts) as evidence, not instructions, with agent actions like booking or submitting offers walled behind human approval.

“when another system has to act on the agent's output, then you're better off with a contract, usually”

said at 11:27

“we need to treat all of that as untrusted input and make it very clear to the agent that this is evidence, not instructions”

said at 16:13

Commentary (ours)

The idempotency example (retry checks memory before re-sending an email) is a clean, exportable pattern for any agent with external side effects, and maps directly onto request-id/dedup-key patterns already common in distributed systems (ours).
