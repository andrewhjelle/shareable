Gives concrete, dated prompting techniques (blind spot pass, reference-as-map, implementation-note logging) for working with Anthropic's Fable model, from the Anthropic engineer who built Claude Code's ask-a-question tool

If you only read one thing

  • Frames working with Fable as 'unhobbling' it: capability shows up in spiky jumps (giving Claude a code-execution tool solved a Pokemon-name puzzle it couldn't answer from memory alone), and Claude Code's system prompt was recently cut by 80% because newer models do better with context than heavy constraints and examples.
  • The 'ask you a question' tool went from barely functioning in Opus 4, to interviewing him with dozens of questions in Opus 4.5, to building full HTML question reports in Opus 4.8 and Fable.
  • Recommends techniques for surfacing unknowns before prompting Fable on unfamiliar problems: a 'blind spot pass' over unfamiliar code, giving Claude a reference example ('a map') instead of writing a full spec, and logging implementation notes whenever the model hits an unspecified decision point.

Capability overhang: models are smarter than they first appear

  • The speaker frames Anthropic models as grown rather than designed, so their capabilities surface unevenly ('spiky').
  • His example: a viral claim that LLMs can't name which Pokemon end in 'aw' (Croconaw and Drednaw) fails for a plain chat model but succeeds once Claude is given a code-execution tool to fetch and filter the full list.
  • He also notes Claude Code's system prompt was recently cut by 80%, reflecting that newer models perform better with context rather than heavy constraints and examples.

The ask-a-question tool got dramatically better across model generations

  • The 'ask you a question' feature, which lets Claude show a multiple-choice dialogue, could barely be called reliably in Opus 4 and required significant tool tweaking to work at all.
  • By Opus 4.5 it could interview the speaker with dozens of questions about a spec, and by Opus 4.8 and Fable it can build a full HTML report with embedded questions.

“For Opus 4, it could barely call it. I had to like really tweak the tool to make sure that it was uh, that it would work, right?”

03Finding your unknowns before prompting Fable

Finding your unknowns before prompting Fable

  • Because Fable can traverse much larger areas of a problem than earlier models, the speaker stresses identifying unknowns in advance.
  • His techniques: a 'blind spot pass' where Claude reviews unfamiliar code or domains to surface gotchas before you prompt further; giving Claude a concrete reference example ('a map') instead of writing out a full spec, which he calls one of the most powerful techniques; and asking Claude to log implementation notes whenever it hits an unspecified decision point during a run.

“I like to do what I call a blind spot pass. So, I like to say something like, "Hey, I'm working on a new auth provider that I know nothing about uh like in this code base”

said at 10:20

“One of the best ways to give Claude a map is to give it another map, right? So instead of me writing out the spec, uh I can just say, "Hey, here's some code that represents what I want to be done, right?”

said at 12:55

“something else I've like really appreciated is implementation notes. So, if uh while you're running Fable uh and it runs into an unknown, ask it to log it, right?”

said at 13:57
04The tradeoff calculus is changing
Slide at 17:00 · click any slide to enlarge · 5 more from this section below

The tradeoff calculus is changing

  • The speaker argues that classic 'good, fast, cheap -- pick two' tradeoffs are being upended by models like Fable, framing his own resolution as being 'less reasonable' about assumed constraints.
  • As an example, he built his own presentation deck in about 4 hours using Fable the night before the talk.

“there are so many tradeoffs that you make implicitly in your head, right? Like good, fast, cheap. Now it's pick three, right?”

said at 17:03

“for example, I made this deck last night in about 4 hours with Fable”

said at 17:34

Commentary (ours)

The consistent pattern across the model-generation examples (system prompt shrinking, examples becoming a constraint rather than a help, ask-a-question tool needing less scaffolding) suggests a general rule worth testing directly: as a new frontier model ships, re-test whether existing few-shot examples and hard constraints in a harness are now net negative rather than assuming they're still needed (ours).
