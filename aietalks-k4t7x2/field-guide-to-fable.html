Field Guide to Fable

SpeakerThariq Shihipar · Anthropic Watchyoutu.be/9fubhllmsBU

If you only read one thing

  • Frames working with Fable as 'unhobbling' it: capability shows up in spiky jumps (giving Claude a code-execution tool solved a Pokemon-name puzzle it couldn't answer from memory alone), and Claude Code's system prompt was recently cut by 80% because newer models do better with context than heavy constraints and examples.

01Capability overhang: models are smarter than they first appear

The speaker frames Anthropic models as grown rather than designed, so their capabilities surface unevenly ('spiky'). His example: a viral claim that LLMs can't name which Pokemon end in 'aw' (Croconaw and Drednaw) fails for a plain chat model but succeeds once Claude is given a code-execution tool to fetch and filter the full list. He also notes Claude Code's system prompt was recently cut by 80%, reflecting that newer models perform better with context rather than heavy constraints and examples.

“There are a thousand Pokémon, right? And turns out there are two who whose names end in AW, Croconaw and Drednaw, right?”

02The ask-a-question tool got dramatically better across model generations

The 'ask you a question' feature, which lets Claude show a multiple-choice dialogue, could barely be called reliably in Opus 4 and required significant tool tweaking to work at all. By Opus 4.5 it could interview the speaker with dozens of questions about a spec, and by Opus 4.8 and Fable it can build a full HTML report with embedded questions.

“For Opus 4, it could barely call it. I had to like really tweak the tool to make sure that it was uh, that it would work, right?”

03Finding your unknowns before prompting Fable

Because Fable can traverse much larger areas of a problem than earlier models, the speaker stresses identifying unknowns in advance. His techniques: a 'blind spot pass' where Claude reviews unfamiliar code or domains to surface gotchas before you prompt further; giving Claude a concrete reference example ('a map') instead of writing out a full spec, which he calls one of the most powerful techniques; and asking Claude to log implementation notes whenever it hits an unspecified decision point during a run.

“I like to do what I call a blind spot pass. So, I like to say something like, "Hey, I'm working on a new auth provider that I know nothing about uh like in this code base”

“One of the best ways to give Claude a map is to give it another map, right? So instead of me writing out the spec, uh I can just say, "Hey, here's some code that represents what I want to be done, right?”

04The tradeoff calculus is changing

The speaker argues that classic 'good, fast, cheap -- pick two' tradeoffs are being upended by models like Fable, framing his own resolution as being 'less reasonable' about assumed constraints. As an example, he built his own presentation deck in about 4 hours using Fable the night before the talk.

“there are so many tradeoffs that you make implicitly in your head, right? Like good, fast, cheap. Now it's pick three, right?”

Commentary (ours)

The consistent pattern across the model-generation examples (system prompt shrinking, examples becoming a constraint rather than a help, ask-a-question tool needing less scaffolding) suggests a general rule worth testing directly: as a new frontier model ships, re-test whether existing few-shot examples and hard constraints in a harness are now net negative rather than assuming they're still needed (ours).
