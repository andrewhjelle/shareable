I Run a Fleet of AI Agents Across Three Machines. Here's What Broke.

SpeakerKyle Jaejun Lee · KRAFTON Watchyoutu.be/4kYl2_mqmnQ · 9 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. Slides below are frames from that recording, reproduced for reference and study; rights remain with the speaker and the conference. Quotes are verbatim from the talk transcript with the time they were said.
patternAgentic engineeringInfra & servingContext engineering

Walks through five concrete failure modes of scaling personal coding-agent usage past a single machine (over-delegation, unreadable tmux panes, out-of-memory, credential collisions, laptop sleep/crash) and the fixes applied

If you only read one thing

  • The speaker replaced a flat pile of agents (where he personally acted as scheduler, memory, and reviewer for 5-6 live contexts) with a hierarchy of scoped agents (CEO/VP/manager/worker), reducing his own review load to one point of approval.
  • Agent state was moved out of the model's context window into per-entity workspace files on disk, so instead of compacting/summarizing a full context window, the agent resets and re-reads its handoff/history files.
  • Scaling to three machines surfaced five failures: agents doing work instead of delegating, unreadable crowded tmux panes, out-of-memory swap exhaustion, crossed credentials between workspaces, and a laptop losing all in-flight jobs when it slept/lost power.
▣The system in one picture (ours, from the slides and the transcript)

The hierarchy, disk-backed state, and review gateway form the core loop; cross-machine sync and the always-on Linux host were added once a single laptop stopped being enough (ours).

The bottleneck was the human, not the agents

  • Running 5-6 live agent contexts in tmux panes made the speaker personally the scheduler (deciding who does what), the memory (holding what each agent was doing), and the reviewer (checking all of it), which he says does not scale.
  • The fix modeled after how executives run large organizations was a hierarchy of agent types (CEO, VP, manager, worker), each a real entity with its own scoped context and approval boundary, so he only reviews what reaches the top.

“I'm not running agents anymore. I've become the scheduler, deciding who does what. I'm the memory, holding what every one of them is doing, and I'm the reviewer, checking all of it”

said at 01:03

“Each one is its own agent with its own scoped context and its own approval boundary. Context flows down. Each layer only gets the slice it needs”

said at 01:34
02State lives on disk, not in the context window
Slide at 01:20 · click any slide to enlarge

State lives on disk, not in the context window

  • Each entity gets its own workspace on disk with a mission, current status, and a handoff folder holding the actual work product; shared context lives in a shared directory and machine-bound state lives under a machines directory.
  • Instead of compacting (summarizing) a filling context window, the speaker resets the context completely and has the agent read back its own handoff and history files to resume exactly where it left off.

“Every entity gets its own workspace on disk. Shared context that everyone has to honor lives in shared. Machine-bound state lives under machines”

said at 02:05

“So, instead, I don't compact, I reset. And by reset, I mean right inside Claude, I clear the context completely”

said at 02:37
03A review gateway enforces alignment
Slide at 01:20 · click any slide to enlarge

A review gateway enforces alignment

  • Because plans drifted as they flowed down the hierarchy, the speaker built a review gateway where any layer that wants to act submits its plan and blocks until approved; approval fires a hook that starts the work automatically, giving one web inbox as the single control point.
  • The gateway itself was built by an infra team inside the agent fleet, agents building tools that run the agents.

“Any layer that wants to act submits its plan and then it blocks. It waits. Nothing runs until I approve. And the second I approve, a hook fires the work off automatically”

said at 03:40
04Five failures when scaling past one machine
Slide at 01:20 · click any slide to enlarge

Five failures when scaling past one machine

  • Scaling triggered five distinct failures: agents doing tasks themselves instead of dispatching to a worker (fixed with a CLI harness forcing delegation), managers spawning so many worker panes that tmux capture-pane could no longer read them, out-of-memory swap exhaustion from stacked sessions, git credentials crossing over between workspaces (fixed with fully separated environments per workspace), and a MacBook losing all in-progress jobs when it lost power or dropped off the network.

“my agents kept doing the work themselves instead of dispatching it down to a worker. The orchestrator is supposed to delegate. Instead, it just rolls up its sleeves and does the task itself”

said at 04:11

“the moment it loses power or drops off the network, every in progress job dies with it. And one time I'd pushed so many workers onto it that the whole machine just gave out”

said at 05:44
05Multi-machine coordination and what's still unsolved
Slide at 01:20 · click any slide to enlarge

Multi-machine coordination and what's still unsolved

  • Cross-machine context syncs via git commit/push, with tmux send-keys over SSH poking the other machine to pull; per-machine directories hold machine-specific state while shared state changes only through a pull request to avoid silent divergence, and one always-on Linux box hosts the single review gateway since the Mac sleeps.
  • The speaker lists four unsolved problems (consistency across machines, local-only tools like the browser and MCP servers, secure credential handoff, and resource management) and says these map to what Kubernetes already solves, so he plans to build his orchestration layer on top of it rather than reinvent compute/secrets/tools.

“These are the exact questions Kubernetes already answers. So, that's where I'm headed. I'm not going to reinvent compute, secrets, and tools. Kubernetes already nailed those”

said at 08:18

Commentary (ours)

The claim that these problems map cleanly onto Kubernetes is directional rather than demonstrated in the talk; personal-agent orchestration has different trust and approval semantics (a human review gate) than typical container scheduling, so the fit may be partial (ours).
