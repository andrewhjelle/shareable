Designing Agents (The Floor Is the Frontier)

SpeakerBen Hylak · Raindrop Watchyoutu.be/jHMiYtjoJfA
Evals & benchmarksAgentic engineering

If you only read one thing

  • Ceiling (best-case capability) matters less to user trust than floor (worst-case failure); floor-raising is the practical work.
  • Clustering traces for issue detection doesn't scale — it can't reliably track when an issue started or how fast it's growing.
  • Agents are bad at finding anomalies themselves; feed them deterministic signals (like keyword-frequency spikes) and have them investigate, not detect.
01Evals as fixed test sets don't survive a changing stack

Hylak argues most public discourse on evals is stuck in the earlier chatbot era, where a fixed eval set made sense because the space of possible answers was narrow. With agents, the harness and model change constantly, so eval sets built around a specific tool-calling pattern break the moment you switch harnesses (he cites an 80% eval failure rate after a switch to Claude Code CLI). His recommendation is to treat evals as code — unit and end-to-end tests run locally — rather than as a slow-changing curated set or managed prompt playground.

02Floor over ceiling

He frames agent quality as a ceiling (best emergent capability) versus a floor (worst thing the agent can do — recommend a competitor, delete data, send an unwanted email). User trust is broken by floor incidents, not by capability gaps, so floor-raising is where practical effort should go.

“the floor is like what is the worst thing your agent can do”

▶ watch at 10:16
03Two facts every issue needs

For any discovered issue, Raindrop's practice is to always establish two things: when it started, and what percentage of users it affects. Knowing an issue is new (versus long-standing) reframes it as something caused by a recent change; knowing the affected percentage sets the urgency.

“you need to know when it actually started, and you need to know how many people it affects”

▶ watch at 13:20
04Clustering traces is a one-off tool, not a monitoring system

A common naive approach is to cluster all traces to find issues. Hylak says this is useful for one-off analysis but doesn't scale as ongoing monitoring, because clusters can't reliably track when something started or how it's growing over time, and cluster boundaries (what counts as "the same issue") are inconsistent across products.

“the first one is that clusters are not issues”

▶ watch at 15:54

“it's useful for one-off analysis, but it just doesn't really scale well”

▶ watch at 15:54
05Don't ask agents to detect anomalies — ask them to investigate ones you've found

His closing lesson: agents are poor at anomaly detection on their own. The workable pattern is to pull out deterministic signals (e.g., keyword-frequency spikes) first, then hand the agent a specific anomaly to investigate rather than asking it to scan for problems unprompted.

“agents are very, very bad at anomaly detection. So don't ask your agent to find anomalies”

▶ watch at 18:27

“ask it to investigate anomalies you've already found”

Commentary (ours)

The floor/ceiling framing is a useful lens for prioritizing agent QA work, though it's worth noting Raindrop sells exactly this kind of production monitoring, so the pitch against clustering and fixed eval sets doubles as a product argument (ours).
