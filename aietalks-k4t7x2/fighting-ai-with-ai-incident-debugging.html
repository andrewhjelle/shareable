Describes a concrete internal-tooling pattern for debugging AI systems too complex for a human to trace by hand: export the debug UI's state as a flat file system that coding agents can grep, and build a small CLI so agents can read/edit...

If you only read one thing

  • Incident.io downloads their debug UIs into flat file systems that Claude Code/Codex can grep through directly -- the biggest unlock for debugging systems with hundreds of prompts and dozens of agents.
  • They built a small CLI ("eval tool") so coding agents can read/edit eval YAML suites without hitting the context limit, letting an agent write a failing eval, fix the prompt, and confirm the rest of the suite still passes.
  • Daily backtests roll up to one accuracy number (86% RCA accuracy) that doesn't explain why it moved, so they run parallel sub-agent analysis pipelines (~25 agents at once) with cohort clustering to explain regressions and propose fixes.

02Eval YAML files became unmaintainable for coding agents

Eval YAML files became unmaintainable for coding agents

  • Production evals grew to include near-complete incident reports as test data, and once these YAML files got large, coding agents would blow their context limit just reading and editing them.
  • The team built a small CLI called "eval tool" that lets an agent list, edit, replace, or add test cases without loading the whole file, which then let an agent be asked to fix a failing prompt end to end: write a failing eval, modify the prompt, and confirm the rest of the suite still passes.

“if you want to do a quick like read and like modify the eval suite, you'd be boosting that into the context, and you'd quickly hit your context limit”

“we ended up creating a small CLI tool that we call eval tool um that was designed to allow agents to leverage our eval suite files”

03Downloading debug UIs into file systems was the biggest unlock

Downloading debug UIs into file systems was the biggest unlock

  • Because coding agents like Claude Code are strong at working with plain file systems, the team started exporting every debug UI's content (including trace views) as a downloadable, self-documenting file system that gets dropped into a sandboxed Claude Code session.
  • The speaker argues file systems are more effective agent context than an MCP server or a bespoke tool, because the agent can grep in bulk and cross-reference against the actual codebase to locate the fix.

04Scaling from one investigation to a repeatable analysis pipeline

Scaling from one investigation to a repeatable analysis pipeline

  • Daily backtests run thousands of investigations across customer accounts and roll up to a single accuracy figure, which doesn't explain why the number moved.
  • To get an explanation, the team downloads investigations into a file system and runs a structured, markdown-playbook-driven pipeline (a repo called "scrapbook") that starts ~25 agents in parallel to analyze individual investigations before clustering results into cohorts of similar failure modes.

05Takeaway: build AI runbooks for repeated complex analysis

Takeaway: build AI runbooks for repeated complex analysis

  • The speaker's closing recommendation is that any complex, repeated analysis task should be turned into an AI runbook rather than done manually each time.

Commentary (ours)

The eval-tool CLI and file-system-export pattern both address the same underlying problem -- agents can't work with UI/YAML abstractions built for humans -- by converting internal state into the flat, greppable format agents are already good at. Worth checking whether other internal tools (dashboards, admin panels) at other shops have a similar human-only bottleneck (ours).
