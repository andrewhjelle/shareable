What Breaks When You Build AI Under Sovereignty Constraints

SpeakerBilge Yücel · deepset GmbH Watchyoutu.be/x2bH0RKPgdc
SecurityInfra & servingOpen source

If you only read one thing

  • Sovereign AI splits into four pillars: data, model, infrastructure, and operational sovereignty, each meaning explicit control over data flow, model choice, infrastructure, observability, and operations.
  • Sending EU citizen data to a US-hosted embedding API breaks data sovereignty even under GDPR, and a US-headquartered SaaS vendor can still be compelled to access data it hosts in Europe under the US CLOUD Act.
  • Retrofitting sovereignty into an existing system is disruptive: swapping a frontier API for a self-hosted model means rewriting API logic, updating prompts, and re-evaluating performance from scratch.

02Where control over data and infrastructure actually leaks

Under GDPR, European citizen data must stay within Europe, but sending it to an embedding API hosted in Virginia already breaks that even if the rest of the stack is EU-based. Infrastructure sovereignty spans a spectrum from air-gapped environments to private VPCs to sovereign cloud to SaaS; with SaaS from a US-headquartered company, the US CLOUD Act gives that company the ability to access data and applications it hosts even when everything runs inside Europe.

“if you send that data to an embedding model, to an embedding API hosted in Virginia in the US, then you are already losing the control of your data”

03Model sovereignty means being able to actually switch

A system that only works with one specific model provider is tightly coupled to it: if that provider's API goes down or raises prices, the system has no recourse. The speaker distinguishes this from swappability without architectural changes, since even a technically model-agnostic system can be too costly to switch in practice if the code doesn't already support it.

“if your system can only work with one specific model, you are tightly coupled with that model provider. If they are if the API is down, then you lose access”

▶ watch at 04:39
04What breaks when you retrofit an existing system

Replacing a frontier model API with a self-hosted model is usually the first move teams make when told to go sovereign, but it means translating the entire existing API logic to a new model architecture, updating prompts, and re-evaluating the system from scratch rather than a drop-in swap.

“you replace the frontier API that you have with a self-hosted model. And what happens? Then you need to translate this whole API logic to this new model architecture”

▶ watch at 07:15
05How Haystack addresses this, and a self-check

The speaker points to Haystack's YAML-serializable pipelines (for version-controllable, auditable configuration) and a dynamic BM25 tool search (so an agent with hundreds of registered tools doesn't have to load every tool definition into context) as concrete mitigations. She closes with three checklist questions for gauging how sovereign a system really is: can you swap models without changing application logic, do you have reproducible run logs stored in a compliant way, and can your team respond to an incident without calling a hyperscaler vendor.

“applications are serializable to YAML making them very easy to version. So, you can just after creating your application with Haystack, you can turn it into YAML, put it into your version control”

Commentary (ours)

The checklist frames sovereignty as a spectrum of vendor lock-in rather than a binary compliance box to tick, which is a more useful lens for scoping how much control a given deployment actually needs -- though the talk doesn't address how to price or timebox that retrofit work once sovereignty becomes a hard requirement (ours).
