Why, and how you need to sandbox AI-Generated Code?

Walks through one security technique, capability-based sandboxing, in depth rather than a full multi-system architecture.

If you only read one thing

01AI-generated code is untrusted code with your app's privileges
Slide at 01:50 · click any slide to enlarge · 6 more from this section below

AI-generated code is untrusted code with your app's privileges

  • The talk's central reframing: sending a prompt to an LLM and running the code it returns is functionally the same as running an untrusted code snippet from the internet, because the code runs with the same file system, network, environment variable, and credential access as the rest of the application.
  • Three concrete threat scenarios are walked through: non-malicious hallucination (bad imports, infinite loops, missing base cases), an LLM that reads and processes secrets while trying to be 'helpful,' and direct or indirect prompt injection that turns the LLM into an attack vector.

02Capability-based security: default deny, explicitly allow
Slide at 08:30 · click any slide to enlarge · 8 more from this section below

Capability-based security: default deny, explicitly allow

  • The organizing security principle presented is capability-based security, borrowed from browsers, OS process isolation, and mobile permission models: don't try to enumerate every dangerous operation to block, instead grant nothing by default and explicitly hand the code only the specific capabilities it needs.

“Don't enumerate what to block. Enumerate what to allow.”

said at 08:27
03Isolates vs. containers: pick by requirement, not preference
Slide at 31:50 · click any slide to enlarge

Isolates vs. containers: pick by requirement, not preference

  • V8 isolates (sub-millisecond startup, no file system or process model, run JS/TS/Python/WASM) suit fast tool calls and code interpreters.
  • Containers (full Linux environment, seconds to start, heavier) suit workloads needing git clone, npm install, dev servers, or long-running processes.
  • The decision rule presented is a single question about whether the code needs a file system, processes, or package installs.

“Does the code need a file system, processes, or package installs? If yes, it's container. Full stop. If no, isolates.”

said at 31:23
04Per-user isolation and keeping secrets out of the sandbox
Slide at 26:10 · click any slide to enlarge · 8 more from this section below

Per-user isolation and keeping secrets out of the sandbox

  • Each user must get their own sandbox with no shared execution environment or file system between tenants.
  • For secrets an external API call might need, the recommended pattern is to proxy the request through the application's own worker/backend, which attaches the real credential, so the API key itself never enters the sandbox where AI-generated (or injected) code could read it.

“Each user gets its own sandbox. The user ID is the isolation boundary. Never ever share sandboxes between users.”

said at 26:08

“proxy through your worker. The sandbox makes a request to your worker's endpoint, something like a proxy endpoint”

said at 27:44
05A universal eight-item checklist
Slide at 34:50 · click any slide to enlarge · 6 more from this section below

A universal eight-item checklist

  • The closing checklist applies to any sandboxing approach: default deny network, explicit minimal capabilities, per-user isolation, resource/timeout limits, secrets kept outside the sandbox via the proxy pattern, guaranteed cleanup (try/finally, max lifetimes), full logging for audit trails, and input validation before code reaches the sandbox.

“These eight things, if you do all eight, you are in a fundamentally better position than 95% of AI applications”

said at 35:01

Commentary (ours)

(ours) The isolates-vs-containers split maps directly onto Cloudflare's own product line (Workers isolates, Cloudflare Sandbox SDK/containers), so the specific tool recommendations are vendor-specific even though the underlying principles (capability-based security, secrets proxying, per-tenant isolation) are portable to any stack.
