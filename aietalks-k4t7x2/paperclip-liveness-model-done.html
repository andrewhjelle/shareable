What Does Done Even Mean? Agents and Paperclip's Liveness Model

SpeakerDotta · Paperclip Watchyoutu.be/7P0elyLIxXo
Agentic engineeringCoding agentsEvals & benchmarks

If you only read one thing

  • Agents can now produce more code and documentation than humans have time to verify, so a single green checkmark for 'done' hides a bundle of separate claims (artifact, evidence, rubric, owner, next step).
  • Paperclip's control plane targets three invariants -- productive work continues, only real blockers stop work, infinite loops are bounded -- via explicit task blockers, an audit trail for human approvals, and harness-agnostic watchdog agents.
  • The stated general recommendation is to separate the verifier from the author, often using a different model for each, and to give agents tools to produce actual evidence of completion rather than just asserting it.
01The failure mode: agents outpace human verification

The speaker argues programming is 'solved' in the sense that agents can now produce code and documentation faster than any human can verify, which creates a new failure mode where agents generate more work than humans have time to check. He reframes 'done' as a bundle of separate claims rather than a single status flip: that an artifact was produced, evidence exists it's complete, a rubric exists to verify against, an owner is known, and the next step is known.

“agents can actually create more work than humans have time to verify”

02Exhaustive human review doesn't scale

He states that exhaustive human verification fails at high volume, humans can only verify a limited number of tasks per day, and requiring universal human sign-off produces what he calls verification theater rather than real quality control.

“exhaustive human verification fails at high volume”

▶ watch at 01:34
03Balancing liveliness and verification

The talk frames the core design tension as liveliness (work keeps moving with no blockers) versus verification (a human has reviewed and trusts the work). Tasks that are fully live with no approvals produce what he calls classic AI slop, worse than producing nothing over time, while full peer review creates a review queue humans can't clear by hand. Paperclip's control plane targets three invariants: productive work continues, only real blockers stop work, and infinite loops are bounded.

“If you have tasks that are completely alive with no approvals, then what you get is this classic AI slop because you're producing a lot of things with kind of no quality control and it's worse than creating nothing after a long period of time”

▶ watch at 02:36

“You want to ensure that productive work continues. You want to make sure that only real blockers stop work. And you want to make sure that infinite loops are bounded”

▶ watch at 03:39
04Paperclip's mechanisms and recommended practices

Paperclip enforces explicit blockers between tasks, records human approval decisions in an audit trail, and supports 'watchdog' agents in a maximizer mode that push work toward a goal until it's achieved; the watchdog is harness-agnostic, working across Pi, OpenGL, Hermes, Claude Code, and Codex through one consistent interface. His stated recommendation, independent of Paperclip, is to treat 'done' as an object rather than a boolean, and specifically to separate the verifier from the author, often using a different model (e.g., coding with Claude, verifying with Codex).

“the watchdog within Paperclip is harness agnostic. You can use it with Pi, OpenGL, Hermes, Claude Code, Codex, whatever you're using, you have one consistent interface”

▶ watch at 04:41

“one of the best pieces of advice we have is that you stop treating done as a Boolean and treat it more like an object”

Commentary (ours)

The verification-theater framing is sharper than most 'human in the loop' advice because it names the actual failure: universal sign-off doesn't add trust once volume exceeds review capacity, it just adds latency (ours).
