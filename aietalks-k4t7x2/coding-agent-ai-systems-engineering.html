Your Coding Agent Should Do AI System Engineering

SpeakerBen Burtenshaw · Hugging Face Watchyoutu.be/JomVvNDjGb8

If you only read one thing

  • A modern GPU (H100) can do a petaflop/sec of compute but only 3 terabytes/sec of memory bandwidth, so kernel efficiency is usually memory-bound, not compute-bound -- the reasoning behind flash-attention-style kernels.
  • An agent-generated kernel for Qwen 3 8B on H100 achieved a 94% speedup, framed as compatibility/low-hanging-fruit rather than state-of-the-art, using Hugging Face's skills-based kernel workflow.

01Why kernel writing is usually memory-bound

The talk breaks kernel efficiency into compute, memory, and overhead, and notes most people assume compute is the bottleneck when it's usually memory: an H100 can do a petaflop/sec of computation but only has 3 terabytes/sec of memory bandwidth, leaving the GPU idle waiting on tensors. Custom kernels like flash attention address this by increasing arithmetic intensity -- doing more computation per memory read/write.

“Efficiency in deep learning, so efficiency in kernels, is split into three main sections. One, compute, two, memory, and three, overhead.”

02Agent-written kernels, benchmarked

Hugging Face's 'kernels' library distributes kernels as hub repos with a toml manifest describing hardware/CUDA compatibility, and pairs them with maintained, file-based 'skills' so an agent can go from zero-shot to few-shot on writing and benchmarking a kernel. An agent-generated kernel for Qwen 3 8B on H100 got a 94% speedup -- not state-of-the-art, but framed as easy compatibility gains for underserved hardware/model combinations. An open-source tool called upskill compares model performance on the same skill (e.g., GPT-OSS vs. Kimi vs. Haiku on accuracy and token usage) to evaluate whether a skill and model choice are worth their cost.

“we generated a a kernel for Qwen 3 8B for H100, and we found that we had a 94% speedup”

03From single-agent to multi-agent automated research

The talk's third and most autonomous tier extends Andrej Karpathy's Auto Research project (built on his nanoGPT/nanochat work, which had Claude Code iteratively write improvements to a training script) into a distributed four-role setup: a researcher that scouts Hugging Face/arXiv papers into hypotheses, a planner that queues jobs, workers that implement hypotheses as training-script changes, and a reporter that monitors runs and maintains a dashboard.

“Andre Karpathy a few weeks ago, maybe a month ago now, released a project called Auto Research, which was based on his other projects, nanoGPT and nanochat”

▶ watch at 10:20

“I tell it to use planner to propose up to first single change experiments, use reviewer to reject duplicates or stale ideas”

▶ watch at 13:57
04Infrastructure: HF Jobs and Trackio

Worker agents submit jobs to Hugging Face Jobs, which run on hub-provided hardware and return patches; the reporter agent tracks metrics in Trackio, an open-source dashboard whose data layer is plain parquet, so an agent (or a human) can bypass the UI entirely and query the underlying data directly for custom visualizations like Gantt charts. The speaker's closing claim is that the Hugging Face Hub already has the storage, tracking, and compute primitives needed to scale this kind of agentic systems-engineering work.

“Trackio is useful with agents because it uses a completely open data layer, basically parquet”

▶ watch at 13:26

“we have the the fundamentals in place like storage, tracking, and compute, which I think will allow us to scale our engineering”

Commentary (ours)

The 94% speedup number is a real benchmark result but explicitly not state-of-the-art -- the actual claim being made is about reach (agents can produce usable, if not optimal, kernels for under-served hardware/model pairs), which is a narrower and more defensible claim than 'agents can write SOTA kernels' (ours).
