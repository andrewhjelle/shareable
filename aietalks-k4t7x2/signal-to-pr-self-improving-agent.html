From Signal to PR: Anatomy of a Self-Improving Agent

SpeakerJason Lopatecki · Arize Watchyoutu.be/9HbzAWnKbo4
Agentic engineeringEvals & benchmarksContinual learning

If you only read one thing

  • Observability is shifting from human-clicked dashboards toward agents that read traces and logs and propose fixes themselves, since the bottleneck is no longer generating a fix but trusting it (c1, c2)
  • As that shifts, the job moves from responder to reviewer, which requires logging and tracing orders of magnitude more than before so agents have the code-path data to work from (c3, c4)
  • Getting an agent to debug well isn't just pointing it at the data -- it requires well-designed skills that pull the right traces and logs into files in the repo, and evals function as pre-processed data layered onto traces that a diagnosis agent also consumes (c6, c7, c8)
01From human-reviewed observability to self-fixing systems

The talk frames observability as shifting from a human-clicked UI to a combination of coding agents plus telemetry, where traces and logs act as the exhaust that lets an agent figure out what code path a failure took. The stated end goal is building systems that autonomously fix themselves, rather than the current state of a human making and reviewing fixes.

02The job moves from responder to reviewer

In the workflow Arize is building toward, an agent surfaces issues with evidence already gathered before a human even looks at them, shifting the human's role from grabbing a ticket and investigating from scratch to reviewing and driving an already-started investigation. Enabling this requires tracing and logging orders of magnitude more than teams do today, since humans can't dig through that volume of logs but agents can use it to reconstruct what path the software actually took.

“your job kind of moves from responder to reviewer”

▶ watch at 09:50

“by logging and tracing orders and orders of magnitude more than we do today, we can actually create these continuous loops that know what path was taking your software and and and actually have it fix itself.”

03Evals are data layered onto traces

The talk describes evals (an LLM-as-judge layer) as pre-processed data attached to raw traces, which the diagnosis agent (Signal) consumes alongside the raw trace data. The typical workflow is to build a specific eval once a particular failure type (e.g., a prompt-injection pattern) has been seen, so it can be caught automatically going forward.

“eval actually are data on the trace itself and so the agent knows how to uh grab the data from traces”

▶ watch at 18:06

“you build an eval for a failure you've seen before a lot of times”

▶ watch at 18:39
04Skill design matters more than just pointing an agent at data

Asked why not simply connect a coding agent directly to production data and let it fix things itself, the speaker says that's essentially what they do, but the real work is in designing the skill surface: getting the right traces into the repo as files in a format coding harnesses can use well, rather than assuming an agent can work well from raw access alone.

“you've got to kind of design the skill surface area in a way that Claude can really really work well and and and it's not just like point Claude at the data”

▶ watch at 17:35
05Products: AX, Phoenix, Signal, and customer-run sandboxes

Arize's product line includes AX (its SaaS platform, where the Signal agent currently lives) and Phoenix (open source). For customers unwilling to connect production systems to an external agent provider, Arize supports running the agent in the customer's own VPC via Arize-provided sandboxes or alternatives like Daytona, citing large companies from Uber to Booking.com as examples of this deployment pattern.

“we also have Phoenix which is open source if you just want to start tomorrow. Um Signal right now is is just available in in our AX SAS platform.”

“we install in the VPC of a lot of you know bigname companies out there um from from Uber to um to bookings to you name it”

Commentary (ours)

(ours) The distinction drawn between "point an agent at the data" and "design the skill surface" is the most concrete, transferable claim in the talk; it's a reminder that giving a coding agent raw access to telemetry is not the same as making that telemetry legible to the agent in a repo-native format.
