Full Workshop: Better Auth

SpeakerPaola Estefania · Better Auth Watchyoutu.be/JvKO40CFq-s
SecurityAgentic engineeringMCP & protocols

If you only read one thing

  • Current agent-to-service connections typically reuse the user's own credentials, so the agent is 'acting on behalf of us but pretending to be us' with no separate identity or audit trail (c1).
  • The proposed fix gives each agent its own identity backed by a private key so tokens can be signed, actions logged per agent, and access revoked without touching the underlying user account (c4, c5, c6).
  • Fine-grained capabilities (not broad OAuth scopes) plus a directory that maps user intent to specific capabilities are used to scope exactly what an agent can do, demonstrated live via an MCP connection to Gmail (c3, c9).
01Agents currently impersonate the user

Estefania opens by polling the room on who connects AI agents to Gmail, calendars, or other personal accounts via MCP servers or personal tokens. She characterizes the common setup as the agent acting on behalf of the user while pretending to be the user, since it reuses the user's own credentials rather than having any identity of its own.

“the agent is acting on behalf of us but pretending to be us”

▶ watch at 01:36
02Hire your agent: authority instead of credentials

She frames the fix through a hiring analogy: a company gives a new employee their own email and access rather than the CEO's login, and agents should work the same way. The closing thesis of the talk is that agents should be told to act within specific limits rather than told to pretend to be the user.

“You never say like, okay, this is the credentials of CEO, go and read the email”

▶ watch at 03:10

“we need to stop giving credentials our credentials to our agents we need to give them authority”

▶ watch at 37:00
03Capabilities and a directory replace broad scopes

Instead of coarse OAuth scopes like 'read', the protocol defines capabilities that map a specific user intent to a specific action a service can perform. Because most services don't yet expose this natively, the protocol builds a directory that translates existing OpenAPI specs (demonstrated against Notion) into a list of capabilities an agent can discover, compared to a phone directory.

“The other capability is what can do, but it's more cap down. So I can actually determine what an action agent can do.”

▶ watch at 09:24

“the directory will be like a phone directory for the agent”

▶ watch at 14:43
04Per-agent identity, private keys, and revocation

Each agent gets its own private key so it can sign tokens and be logged as a distinct principal rather than hidden behind the user. This produces per-agent audit logs showing what action was taken on whose behalf, and access can be revoked for a single agent without disabling the user's underlying account, demonstrated live in the workshop by connecting, using, and then revoking an MCP-connected email agent.

“the agent will have like a access to its own private key, they can sign tokens”

▶ watch at 17:52

“if every agent has identity, we can trace them down”

▶ watch at 07:52

“You can revoke access in the same way the agent will be revoked if you know who they are.”

▶ watch at 08:23
05Design note: directory, not proxy

Estefania distinguishes the protocol's directory component from a proxy, arguing that routing traffic through a proxy is not scalable because a proxy has to handle the data itself, whereas the directory only matches intent to capabilities and hands off the connection.

“proxy is a really bad idea. It's not scalable because proxy uses data”

▶ watch at 35:58

Commentary (ours)

The live demo (connect, read email, send email, revoke, fail to read) is a clear illustration of the mechanism, but the talk is explicitly framed as a V1/V2 draft of an open-source protocol still being iterated (a persistent-agent policy model was called out as in progress), so the specifics of capability declaration and directory coverage should be read as evolving rather than settled (ours).
