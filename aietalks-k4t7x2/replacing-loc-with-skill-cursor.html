Replacing 12K LoC with a 200 LoC Skill

SpeakerDavid Gomes · Cursor Watchyoutu.be/WE_Gnowy3uw
Coding agentsContext engineeringEvals & benchmarks

If you only read one thing

  • Cursor deleted around 15,000 lines of code by replacing its Git-worktree and best-of-N (multi-model comparison) features with markdown skills built on two existing primitives, agent skills and sub agents; the best-of-N skill runs about 40 lines versus roughly 4,000 lines of code before.
  • The hardest part is keeping the agent from escaping its assigned worktree: the old code made this physically impossible, while the new skill relies on aggressive prompting alone, which the speaker calls 'vibes-based,' and evals show smaller models like Haiku deviate from the worktree more often than Composer or Grok.
  • The skill-based rewrite gained multi-repo worktree support the old feature never had but lost feature discoverability, and Cursor is now adding worktree-staying tasks to its Composer RL training pipeline since Composer 2 had none for this environment.
01Markdown replaced about 15,000 lines of Cursor's worktree code

The speaker frames the talk around the idea that markdown is becoming a replacement for code, describing the deletion of Cursor's Git-worktree and best-of-N features in favor of markdown skills. He states the PR removing the entire prior implementation deleted around 15,000 lines of code.

“I'm going to be talking about how markdown is basically the new code.”

02Two existing primitives, skills and sub agents, did the reimplementation

Cursor rebuilt the worktree and best-of-N features using two primitives that already existed in the product: agent skills and sub agents. The best-of-N skill itself is about 40 lines of markdown, replacing a previous implementation that was around 4,000 lines of code, and the skill also has to handle cross-platform differences (Windows, Linux, macOS instructions).

“it's only around 40 lines of code, and it's all markdown. Like it's not even code”

03The hardest part: keeping the agent from escaping its worktree

The speaker identifies instructing the model to stay on its assigned worktree as the hardest part of the rewrite, requiring what he calls aggressive prompting. He contrasts this with the old code-based implementation, where it was physically impossible for the model to touch files outside its worktree; the new approach instead trusts the model, which he describes as a bit vibes-based.

“this is the hardest part, we'll spend a bit of time on this on the talk today, we have to instruct the model to stay on that word tree, right?”

▶ watch at 07:17

“It was physically impossible for it to do so. Now, we're trusting the model. So, it's you could say it's a bit vibes-based”

▶ watch at 12:26
04What the skill approach gained: multi-repo support

One concrete advantage of the new implementation is that it works across multi-repo setups (for example, separate front-end and back-end repos), something the old worktree feature did not support at all -- it was simply disabled in that case.

“Another big advantage is that the previous implementation did not work if you were working on multiple repos at the same time.”

▶ watch at 10:54
05Fixing agent drift with evals and RL training data

To address the agent drifting outside its worktree, Cursor is building evals (using Braintrust) that check whether a model worked inside its assigned worktree versus the primary checkout, and has already found that smaller models like Haiku deviate more often than Composer or Grok. Separately, Cursor's own Composer model had no RL training tasks covering this kind of environment as of Composer 2, and the team is adding such tasks to the RL pipeline for future versions.

“not all models are equally good at this. So, for example, Haiku, which is a smaller, less intelligent model, will very often deviate and start working in the primary”

▶ watch at 16:03

“at Cursor, we train our own model called Composer. And for Composer 2, uh the latest version of this model, we didn't have any RL tasks with these prompts.”
