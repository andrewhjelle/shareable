Why MCP and ChatGPT Apps Use Double Iframes

SpeakerFrederic Barthelet · Alpic Watchyoutu.be/c-2eEv2ou7Y
MCP & protocolsProduct & UXSecurity

If you only read one thing

  • MCP apps render UI via 'views' -- tool-call-triggered HTML/JS/CSS snippets discovered from tool-list metadata and rendered inside an iframe injected with tool results.
  • A single iframe with sourceDoc either shares the host's CSP/origin (letting third-party scripts read the host's local storage/cookies) or, if sandboxed with allow-same-origin, ends up back in the same unsafe spot -- neither is safe.
  • The double-iframe pattern (outer iframe on a per-app subdomain loading an inner sourceDoc iframe) isolates each app's origin from both the host and other apps, and traces back to Facebook's app marketplace architecture.
01How MCP app views work

MCP/ChatGPT apps add discoverability (apps surfaced in a store or mid-conversation) and interactive UI via 'views' -- HTML/JS/CSS snippets that render as the result of a specific tool call. Views are advertised as metadata on the tool-list call at conversation start, so the resource can be cached ahead of time or fetched when the tool call actually needs to render.

“Views are always rendered as a result of a tool call. So if your server exposed multiple tool to be used, you can actually add metadata on some of them”

▶ watch at 02:03
02Why a single sourceDoc iframe fails

Loading the view directly into an iframe with the sourceDoc attribute shares the same origin and CSP as the host, so ChatGPT's script-src nonce requirement blocks any third-party app script from executing. Relaxing that CSP to let scripts run reopens the same-origin problem: a loaded app script could read the host's local storage or cookies and exfiltrate them.

“the iFrame that you are spawning up is sharing the same origin and sharing the same therefore CSP as the host that is responsible for”

▶ watch at 07:18

“you are sharing same origin as your parent DOM. So the loaded iFrame scripts would be able to access local storage or cookies that are indexed by origin”

▶ watch at 07:48
03Why sandboxing alone and the src-attribute route also fail

Sandboxing the iframe to a null origin blocks origin-indexed storage (local storage, IndexedDB, cookies) entirely; adding allow-same-origin to fix that recreates the original escape-the-sandbox risk. Using the src attribute to point at each app's own server would require the host to add every new app's domain to its frame-src CSP directive indefinitely, which isn't feasible at store scale.

“the only way to actually provide an origin to a sandboxed iFrame is to put allow same origin, which is an additional attribute that”

“it would require open AI to modify the another CSP directive, which is basically the frame source directive listing all domains that are allowed to”

04The double-iframe solution

The working pattern serves the same small script-loader content on a unique per-app subdomain (an outer iframe with its own effective origin, isolating each app from the host and from other apps' local storage/cookies), which then loads the actual view content in an inner iframe using sourceDoc. This is the pattern actually implemented in production and is described as tracing back to Facebook's original app-marketplace architecture for third-party app UI.

“you want app ABC123 not to be able to access local storage from app ABC456 for example”

▶ watch at 12:56

“actually the first time this solution was implemented was back in Facebook days when they released their app marketplace”

▶ watch at 13:39
05Practical developer guidance and Skybridge

App developers must declare every external domain their app depends on (API calls, scripts, images) in MCP app spec metadata so it gets rewritten correctly inside the nested iframe; missing domains are a common cause of ChatGPT app store submission rejections. Alpic's open-source Skybridge framework adds end-to-end type safety and a CSP inspector dev tool that flags domains an app actually calls but hasn't declared in its metadata.

“declare all domains your application depends upon inside the provided metadata in the MCP app spec so that you are sure that they will be rewritten correctly”

“we've seen a lot of rejection coming from chat GPT app store submission because of missing CSP and app not working in production because of”

Commentary (ours)

The Facebook-app-marketplace lineage is a useful reminder that third-party-UI-in-a-trusted-host is an old problem with a known solution pattern -- worth watching whether MCP client vendors standardize a shared proxy-subdomain infrastructure rather than each host reinventing it (ours).
