Two Roads to Durable Agents: Replay vs. Snapshot

SpeakerEric Allam · Trigger.dev Watchyoutu.be/svCnShDvgQg
Agentic engineeringInfra & servingContext engineering

If you only read one thing

  • Replay-based durable execution -- wrapping every side effect in a cached step -- works for bounded workflows but breaks down as agent conversation logs grow, and agent task length is reportedly doubling every 4-7 months (c2, c1)
  • Trigger.dev splits agent durability into two separately-persisted layers: an append-only context log (LLM/tool calls) and machine-state snapshot/restore for the execution sandbox (c3)
  • Moving from CRIU process-level snapshots to Firecracker microVM snapshots, then compressing them, brought a full VM snapshot down to about 14MB with sub-second snapshot and a few-hundred-millisecond restore (c4, c5, c6)
01The replay model and where it breaks

The talk traces backend history from stateless CGI/PHP through the 'shared nothing' architecture to workflow engines that wrap side effects in cached, re-playable steps so a failed multi-step process can resume without re-running completed work (e.g., without double-charging a credit card).

“you'd write your code like this now, where you sort of uh wrap every single side effect in like a step that becomes cached as it's uh executed”

▶ watch at 03:36
02Agent sessions outgrow replay logs

When LLM calls and tool calls each become steps in a replay journal, the log grows with every turn and eventually hits entry-count or entry-size limits. The speaker cites a metric that the length of meaningful work agents can sustain is doubling every 4-7 months, moving from hours toward multiple days.

“agents uh can actually do meaningful work, and apparently it's doubling every 4 to 7 months”

▶ watch at 06:41
03Snapshot and restore for the execution layer

Because agents now need a full machine (files, subprocesses, running dev servers), Trigger.dev separates an append-only context log from execution-state durability, using snapshot-and-restore instead of replaying a log to reconstruct machine state. This lets a session pause (e.g., while a user is at lunch) without paying for a continuously running machine.

“instead of recreating the execution state from a log, we should use snapshot and restore”

▶ watch at 09:15
04From CRIU to compressed Firecracker snapshots

Trigger.dev first used CRIU (2011), a Linux user-space checkpoint/restore tool, but it only captures a single process and open files. In 2024 they moved to Firecracker microVMs to snapshot an entire machine, then added seekable compression and layering to shrink snapshots to about 14MB, achieving sub-second snapshots and a few-hundred-millisecond restores.

“We also have a couple other techniques for layering the snapshot, and we can get the the, um, snapshot down to like 14 megabytes compressed”

▶ watch at 13:55

“snapshots are like slightly under a second, and restores are a couple hundred milliseconds”

“you can run Alpine, and it's super fast, and you can snapshot running VM, and it's super fast”

05This isn't new

The speaker points to a 1966 IBM mainframe with checkpoint-and-restore for expensive long-running jobs, and to CRIU's 2011 debut as a user-space process suspend/restore tool, as precedents for today's snapshot/restore approach to agent durability.

“this is an IBM mainframe from 1966, and it actually has checkpoint and and restore”

“Fast forward to 2011, a thing called CRIU was um, developed. It was a way to like suspend and restore a uh, a process like from user space”
