Agents Need Feature Flags

01Agents ship without the safety rails web apps already have

The talk opens by contrasting today's agent deployments with a decade of web-team practice: canaries, segment targeting, kill switches, and rollout monitoring are described as solved, boring infrastructure. Agents that send money, send mail, modify databases, and spawn child processes are being shipped with none of that infrastructure, the way web teams shipped in 2008, and a prompt change merge is described as going to 100% of users instantly with no canary, no segment, and no rollback button.

“agents that send money, agent that send mail, agent that modify databases, agent that spawn child processes and we are shipping them with none of that infrastructure”

02Four incidents used to motivate the talk

The speaker cites four named incidents from the prior 14 months as the failure mode the talk addresses. 03A taxonomy of six agent-specific flag types

The proposed taxonomy maps one flag type to each of six agent behavior surfaces: prompt variant, tool access, model routing, memory policy, autonomy level, and kill switch. Autonomy level is presented as the single largest blast-radius dial, with three settings -- suggest (agent recommends, human acts), auto-approve (agent prepares, human confirms with one click), and autoexecute (agent acts alone) -- while a real kill switch is defined by three properties: it takes effect in seconds without a deployment, in-flight requests respect it at their next decision point, and its wiring exists from the design phase rather than as a 3 a.m. hot patch.

“Suggest where the agent recommend and a human acts. Auto approve where the agent prepares and a human one click confirms.”

▶ watch at 08:56

“It does not require any deployment, does not require any start, does not require any code changes.”

04Sub-agents can bypass the safety layer entirely

The architecture places a middleware layer between the user and the agent loop that resolves flags, routes tools and models, applies autonomy, and honors the kill switch, sitting on top of an existing flag backend such as LaunchDarkly, Unleash, or a homegrown service. The stated failure mode is a parent agent with flags properly applied spawning a child agent that calls the model and tools directly, bypassing the middleware so a flipped kill switch never reaches it.

“The biggest failure mode I see is a parent agent with flags properly applied that spawns a child agent.”

▶ watch at 13:07
05A five-step rollout playbook with numbers to track

The recommended rollout order is: wire the kill switch first, wrap every tool call to resolve a flag before execution, default autonomy to suggest and add auto-approve per surface as trust builds, move prompts into flag-resolved config, and track four numbers from day one -- kill-switch fires per week (target zero, investigate above two), rollback time to mitigation, canary error-rate delta, and flag audit-trail completeness. The closing recommendation, repeated as the single most important takeaway, is to ship the kill switch first.

“First one, kill switch fires per week. The target is zero. If you have more than two a week, then investigate”

▶ watch at 14:08

“Ship the kill switch first. If you do nothing else, give your agent one agentwide kill switch and one per tool kill switch.”

Commentary (ours)
