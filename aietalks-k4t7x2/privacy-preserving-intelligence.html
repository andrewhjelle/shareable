Privacy-Preserving Intelligence

SpeakerSteve Korshakov · Bee (acq. Amazon) Watchyoutu.be/IvE8n-ylFYY
SecurityMemory

If you only read one thing

  • The wearable captures about 10 million tokens per person per year, and within about a week of wearing it a user typically reveals extremely sensitive information (c1).
  • Encryption keys live only on the customer's phone and are never persisted by the company; a transparency-log attestation pipeline verifies workload integrity before the key is shared with confidential-compute inference nodes, with a forced 7-day key expiration in memory (c2, c3, c4).
  • The whole client/attestation codebase is deliberately kept small, about 20k lines in a memory-safe language, to keep it auditable rather than reinventing cryptography (c5).
01Why this data is unusually sensitive

The device is a microphone worn on the hand that records continuously and builds a personal AI agent from that data. A single person captures roughly 10 million tokens per year, and even within the first week of recording, people typically reveal extremely sensitive information to friends and family, making it, in the speaker's words, one of the most sensitive capture devices on the market.

“a single person usually like captures about 10 million tokens per year”

02Design goal: no one at Amazon can see the data

After Amazon's acquisition of the company, the stated mission was for no one at Amazon, including the team itself, to have access to the raw recorded data. This required stricter guarantees than Amazon's standard security posture, since being inside Amazon (versus just a customer of it) removes an existing trust boundary. The system was also built as a stateful, continuously running runtime with persistent memory (rather than a request/response model), likened to how Claude Code moved from short interactions to running for hours.

“we can see uh we can see this like as a like glimpse into the future how cloud code works”

▶ watch at 03:08
03Key management: phone-only, never persisted

Encryption is built on the encryption key living and staying only on the customer's own phone (iPhone or Android); the company never has it and never persists it. There is no opt-out and no way to disable or bypass the encryption. The phone connects to the backend and runs an attestation pipeline that verifies workload integrity and checks the workload against a public transparency log (built on Sigstore) before the key is shared with replica confidential-compute inference nodes, which do not have code replicated to them beyond a limited scope.

“the key leaves and manage it only on customer device”

▶ watch at 03:38
04Forced key expiration and audit posture

Anywhere the system holds a key in memory, it enforces a forced expiration of seven days, chosen as a realistic time horizon for something useful to still be done for the user (24 hours was judged too short). The company works with external high-profile audit firms and can provide any deployed image or manifest data to trace potential weak spots, using a private certificate authority rather than a public one to avoid populating the public transparency log with deployment metadata.

“we introduced everywhere where we have the keys in the memory uh uh the forced expiration of seven days”

▶ watch at 06:48
05Small, auditable codebase

The company deliberately minimized the amount of custom code it wrote, keeping the client/attestation codebase to roughly 20,000 lines in a memory-safe language so it could be fully audited and verified, reusing existing trustworthy software rather than building custom cryptography.

“it's just like about 20k lines on memory safe language”

▶ watch at 12:09
06Sandboxing agents against themselves

On tightly constraining what agents can do locally, the speaker's view is that nothing works except sandboxing agents so they simply cannot take harmful actions, comparing it to how a person's autonomic functions can't be stopped by will; he described trying other agent tools that became far less useful once locked down and said the company's own approach is to deploy a sandbox specific to each agent that limits what it can do.

“I think nothing works except like sandboxing and just not giving them a way to hurt themselves”

▶ watch at 14:05

Commentary (ours)

(ours) The interesting design tension is that the privacy architecture (keys only on-device, forced expiration, no company access) is in direct trade-off with the product's core pitch (a persistent, always-available personal agent); the 7-day key-expiration window is effectively where they drew that line.
