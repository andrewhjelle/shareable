Everything You Need To Know About Agent Observability

SpeakerDanny Gollapalli & Zubin Koticha · Raindrop Watchyoutu.be/-aM2EDTiaMs
Agentic engineeringEvals & benchmarks

If you only read one thing

  • Raindrop argues static evals with golden datasets aren't enough for production agents because tool, memory, and sub-agent combinations create an unbounded input-output space, and pitches monitoring implicit signals (regex, classifiers) alongside explicit ones (error rate, latency, cost).
  • A regex frustration-phrase detector pulled from Claude Code's leaked source tracked issue rate after every release; in a Raindrop customer example, shipping a new prompt version dropped user frustration from 37% to 9%.
  • Self-diagnostics, a single tool call plus one system-prompt line asking the agent to report anything noteworthy, surfaces tool failures and capability gaps, but tool framing matters: naming it 'report to your creator' gets more honest results than naming it after unsafe behavior.
01Why evals alone aren't enough

The speakers describe the traditional paradigm of testing agents against a fixed set of inputs and a golden dataset of expected outputs. They argue this breaks down as agents call growing numbers of tools, memory sources, and recursive sub-agents, creating a combinatorial space no fixed test set can cover, which pushes teams from a testing paradigm toward a production monitoring paradigm.

“The traditional paradigm we've been talking about is evals, right? Where you have this sort of test input and you want to see what is the output that comes out from the agent.”

02Two types of signals: explicit and implicit

Explicit signals are objectively verifiable, things like error rate, latency, cost, and regeneration rate. Implicit signals are semantic and harder to catch: regex phrase matching, trained classifiers, and self-diagnostics. As an example of a regex signal, the speakers point to a keyword list found in Claude Code's leaked source code that flagged frustration phrases and let the team track issue rate after every release.

“explicit signals deal with objective reality, things that are uh are verifiable true or false. For example, explicit signals are things like error rate.”

03Using signals to compare shipped changes

Once a team has a good set of signals, they can compare a shipped change against a control group the way an A/B test would, but using semantic signal rates instead of business metrics. In a Raindrop example, shipping a new prompt version dropped user frustration from 37% to 9%. The speakers say a signal-based comparison becomes useful once there are a few hundred events, before it would be statistically rigorous.

“let's say I ship a new version of the prompt, prompt 2.4. You can see, you know, what is the user frustration rate? It's gone down very substantially, 37% to 9%.”

▶ watch at 08:23

“it's not always like scientifically statistically significant, but if you see the user frustration rate go up, maybe it's something to look at”

▶ watch at 09:56
04Self-diagnostics: the agent reports on itself

Drawing on an OpenAI blog post about training models to self-confess misalignment, the speakers built a minimal self-diagnostic pattern: one extra tool call plus a system-prompt line encouraging the agent to report anything noteworthy. They found that how the tool is framed changes how honest the model is; naming it after unsafe behavior makes the model reluctant to use it, while framing it as reporting to its creators works better.

“one of the inspirations for this is basically OpenAI's like paper/blog back in December about how they were sort of like training the models to like self-confess any sort of like misalignment issues.”

▶ watch at 16:11

“All you have to do is basically write a simple a free a tool that it can call and then a simple line in your system prompt to encourage it to sort of like call that tool.”

“the tool naming also matters quite a bit. So you sort of wanted it to frame it as like report instead of like say unsafe uh bad tool use or something like that”
