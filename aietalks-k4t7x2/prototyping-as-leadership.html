Prototyping as Leadership: How a CTO Ships with AI Agents

For engineering leaders deciding whether to keep coding as they take on more management scope, this talk gives a concrete operating pattern: a context-heavy evening handoff, an overnight agent run, and a morning review block

If you only read one thing

  • Agrawal now ships two to ten PRs a week by running coding agents overnight, kicked off from a 5pm context-gathering block (c1, c2)
  • The same overnight-agent pattern extends to hill-climbing eval scores and training new models — his team trained a BERT PII classifier overnight after Opus and Haiku proved too slow and imprecise (c5)
  • None of this replaces personal review: his rule is to test everything himself before a PR goes up and never add reviewers to code he hasn't read, after agent-written code caused production incidents (c6, c7, c8)

Why building became part of the leadership job

  • With AI coding agents now able to work autonomously for hours, Agrawal argues the manager schedule is usable as building time again.
  • He fits two to three hours of coding a day around 15+ weekly meetings and seven direct reports, anchored by a morning review block and a 5pm block that kicks off an overnight agent run.

02The overnight loop

The overnight loop

  • His core workflow is a nightly cycle: gather context in the evening, hand the agent a detailed prompt, and let it run for hours.
  • He has agents write tests before building rather than after, and run an internal or borrowed AI code-review skill in a clean sub-agent to fix flagged issues before he wakes up.

03Beyond features: hill-climbing evals and training models overnight

Beyond features: hill-climbing evals and training models overnight

  • The same overnight pattern extends past shipping features to optimizing AI features against a hand-collected eval set, and to training entirely new models.
  • His team had an overnight agent run train a BERT-based PII classifier after Opus and Haiku proved too slow and imprecise for the task, using sandboxed (non-production) AWS access.

04The guardrails that make this safe
Slide at 15:40 · click any slide to enlarge · 1 more from this section below

The guardrails that make this safe

  • Agrawal is explicit that this only works because of organizational scaffolding already in place, AI code reviewers, CI, agents.md hygiene, and that agent-written code has still caused incidents and annoyed engineers on his team.
  • His personal rules: test everything yourself before the PR goes up, keep PRs small and readable, and never add other reviewers to code you haven't read yourself.

Commentary (ours)

The reported cadence leans heavily on infrastructure The Browser Company had already built (internal AI code reviewers, prototype-branch feature flags, agents.md hygiene) before this workflow was viable, teams without that scaffolding in place would likely see rougher results than the two-to-ten-PRs-a-week headline suggests.
