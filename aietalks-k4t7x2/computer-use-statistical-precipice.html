This talk names two concrete failure modes in how teams evaluate computer-use agents: static/deterministic benchmarks that a blind action-replay script can beat, and confidence intervals computed only from base-case rollouts that underst...

If you only read one thing

  • A scripted 'replay agent' that blindly repeats a recorded successful trajectory matches or beats the frontier model it was recorded from on standard deterministic benchmarks like OSWorld or Mobile World; pass@k on such benchmarks is mathematically the same exploit (c1, c2).
  • DIG World, built to resist this, uses a verified-compiler approach to generate diverse, checked task variations: 15 Android apps, 387 verified scenarios, 3.2 million valid configurations (c3).
  • Frontier models are inconsistent across trivial variations (starting screen, app theme), and confidence intervals computed only from base-case rollouts capture as little as 17-20% real coverage instead of the intended 95% — a gap that can cost hundreds of thousands of dollars a month in wrong deployment decisions (c4, c5, c6).

01The replay-agent exploit
Slide at 01:30 · click any slide to enlarge · 8 more from this section below

The replay-agent exploit

  • D'Oro defines a 'replay agent': record a successful action trajectory from a frontier model on each benchmark task, then blindly replay that fixed script at eval time with no reasoning.
  • On common benchmarks like OSWorld or Mobile World, this replay agent matches or beats the frontier model it was copied from, because those benchmarks are static and deterministic.
  • He and coauthors prove formally that the pass@k metric, evaluated on a deterministic environment, reduces to exactly this same replay-agent success rate.

“you will see that the success rate of this agent compared to the uh frontier model from which the agent was extracted is actually uh the same or even better”

“the details of how this metric works on a deterministic environment you will see that is literally um and we prove it like formally in the paper”

02Building environments that resist the exploit

Building environments that resist the exploit

  • The fix is to make environments multi-factorial (varying data, appearance, and initial state) while verifying every generated combination is valid — principles he groups under the acronym PRISM.
  • Applying this, his team built DIG World: 15 mobile apps across different domains, 387 verified scenarios, and 3.2 million verified configurations, generated by a 'compiler' that combines parameterized task templates, verifiers, and mock data, then rejects invalid combinations.

“So it's 15 apps on spanning different domains uh with 387 uh verified scenarios and uh a number of configurations”

said at 05:48
03Models aren't robust to trivial variation

Models aren't robust to trivial variation

  • Once an environment supports this kind of diversity, it can also measure whether a model's performance holds up when you vary things like the starting screen or the app's visual theme.
  • D'Oro reports that in the worst case, frontier models are 'pretty bad' at staying robust to these variations, even when the underlying task is unchanged.

“you can see that in the worst case frontier models are pretty bad actually at um being robust to these variations”

said at 09:59
04Honest uncertainty has a dollar cost
Slide at 12:00 · click any slide to enlarge · 4 more from this section below

Honest uncertainty has a dollar cost

  • Beyond environment design, D'Oro argues teams must measure both action-level and environment-level variation when computing confidence intervals.
  • Using only base-case rollouts (what most teams do today) yields roughly 17-20% real coverage against a nominal 95% confidence interval — the reported interval is overconfident.
  • He walks through a scenario with one million tasks, a 4% real performance mismatch between two candidate models, and a $12-20 cost per mistake, showing an overconfident interval can drive a deployment decision that costs hundreds of thousands of dollars in a single month.

“if you only use rollouts, so you only use the base case and what people would use normally actually in realistic cases you have something like 17% on 20% coverage”

“if you have one million tasks and there is a 4% mismatch in performance for real in the models and each mistake is like $20 uh like $12 on average”

“these are sort of uh things that we can think when we don't have enough time but actually a non-rigorous benchmark is misleading”

Commentary (ours)

The replay-agent framing is a clean falsification test for any benchmark: if a script with no reasoning can match your leaderboard scores, the benchmark measures determinism, not capability. (ours)
