  • Chrome DevTools MCP exposes the full DevTools toolset (click, fill form, console messages, network requests, Lighthouse audit, screenshots) as MCP tools an agent can call directly instead of scripting a browser blind (c2).
  • Chrome's built-in dev tools can now explain console/network errors and even apply a live CSS/DOM edit straight back into the source file via "apply to workspace" (c3, c4).

01Coding-agent skills as reusable, on-demand plugins

The speakers describe agent skills as lightweight, text-format plugins, built on an open spec supported by most coding agents, that are pulled into context only when their description matches the current task rather than always being loaded. The demo repo used skills for GitHub CLI issue lookup, front-end design guidance, Playwright control, and a custom-built Telegram-notification skill, all wired together through an agents.md instructions file.

“skills are lightweight plugins described in text format based on an open specification that's supported by by most coding agents nowadays”

02Controlling the browser through an MCP server

The Chrome DevTools MCP server exposes the same capabilities as the DevTools UI (clicking, filling forms, reading console/network output, running Lighthouse and performance audits, resizing, screenshotting) as callable MCP tools. In the demo, an agent used it to start the dev server, open Chrome, and run performance traces across simulated network speeds without the presenter touching the browser.

“Like click, fill form, get get console message, the network request, the lighthouse audit, navigate page, take screenshot, everything.”

03AI built into DevTools itself

Once enabled in DevTools settings, an "ask/debug with AI" icon appears next to console errors and failed network requests, offering an explanation and suggested fix in place. The same AI assist works on a recorded performance trace to explain LCP delays, and on selected DOM/CSS elements, where a live style change can then be pushed back into the actual source file via "apply to workspace" rather than staying a throwaway DevTools edit.

04On-device browser AI APIs

A draft W3C "web AI" API family (summarizer, proofreader, writer/rewriter, and a general multimodal prompt API) runs a model locally in the browser rather than calling a cloud provider. The model is roughly 4GB, downloads once per machine, and is then shared across every site that uses the API; the presenters demoed review summarization, proofreading, and an image-to-JSON-review generator, all offline. They flagged the APIs as highly experimental and still changing week to week.

05Preparing websites for agents: LLM.txt and Web MCP

LLM.txt (and the fuller llms-full.txt variant) acts as a map or full-content dump so an agent can find or ingest a site's documentation directly instead of crawling pages, which the speakers note also helps agents work with a framework's latest version rather than stale training data. Web MCP, still a very early proposal, lets a page register its own actions as named MCP tools directly on the page (via the navigator object) or auto-generate a tool schema from an existing HTML form's inputs and labels, so an agentic browser can call a tool instead of inferring clicks from screenshots and DOM coordinates.

“it's used by agents to act as a map uh to discover where it can find the information it needs on your website”

Commentary (ours)

(ours) The talk stacks four AI integration points at very different maturity levels under one banner; worth separating in any adoption decision — Chrome DevTools MCP and LLM.txt are usable today, while the on-device web AI APIs and Web MCP are explicitly described by the speakers as changing week to week and not yet stable enough to build production reliance on.
