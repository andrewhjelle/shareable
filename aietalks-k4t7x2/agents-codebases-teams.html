Agents, codebases, and teams

Describes organizational practices for rolling out coding agents across a full engineering team rather than a single power user: symptoms that indicate a broken setup (babysitting, silent context burn, a growing issue backlog), and a con...

If you only read one thing

  • Signs a team's agent setup is broken: engineers babysitting agents, blaming the model for what's actually a harness problem, and silently burning 500k-750k+ tokens of context on simple tasks (c1, c2).
  • Fixing this is framed as a leadership problem, not an individual one; Khandelwal's team built one high-trust skill ('ship it') that runs code-done to PR-ready end to end, often for over an hour, which won over skeptics once they saw it work (c3, c4, c5).
  • Scaling created its own mess -- 400-500 open issues within a couple weeks -- and the fix was progressive disclosure: a hard 100-line cap on skill.md files and keeping runbooks in code comments rather than loading everything upfront (c6, c7, c8).

Symptoms of a broken agent setup

  • Khandelwal lists observable signs that a team's agent workflow isn't working: people babysitting their agents, blaming a model version for what is really an unchanged harness, silently burning huge amounts of context and money on simple tasks, needing constant intervention on long sessions, and generating a steady stream of low-quality output.

Frame it as a leadership problem, not an IC problem

  • He argues the most impactful fixes to a codebase's agent-readiness require team-wide buy-in and can't be done by an individual contributor alone, so making engineers work well with agents needs to be treated as an organizational responsibility, not something left to each engineer to figure out on their own.

“It isn't really an IC's job. It's a job for leadership. It's a job for the company”

said at 05:40
03The one skill that built trust: 'ship it'
Slide at 09:50 · click any slide to enlarge · 8 more from this section below

The one skill that built trust: 'ship it'

  • The team invested in a single high-value skill called 'ship it' that takes code from done to PR-ready automatically: opening the PR, handling review comments and CI failures, and writing PR descriptions.
  • The skill often ran for over an hour, which initially worried people, but once they saw it deliver real value they became invested in trusting agents more broadly.

“it takes care of everything from code done to PR ready for review”

Scaling pains: issue overload

  • Wiring issues and boards directly into the repo caused the number of open issues to balloon to 400-500 within a couple of weeks, in part because multiple agents were creating issues without being coordinated correctly.

“we blew up to like 4 or 500 issues uh without like, you know, just I think within like a couple of weeks, which is a crazy number for like a repo”

05Progressive disclosure as the fix
Slide at 14:40 · click any slide to enlarge · 3 more from this section below

Progressive disclosure as the fix

  • To keep agents from burning context loading everything upfront, the team set a hard cap of about 100 lines per skill.md file and treats the skill as a folder the agent can explore rather than a monolith.
  • Documentation that an agent needs when it lands in a particular part of the codebase, like a runbook, is kept in code comments so it's discovered only when relevant, rather than front-loaded into a giant CLAUDE.md.

“we've kind of set a hard limit for like 100 lines in your skill.md cuz your skill is really a folder”

said at 14:59

“when you have like some code that requires like a runbook, make sure the runbook is reflected in the comments”

said at 14:59
