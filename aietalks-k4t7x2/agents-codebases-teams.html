Agents, codebases, and teams

SpeakerAditya Khandelwal · Amazon AGI Lab Watchyoutu.be/aeTb5BdmTTc

If you only read one thing

  • Signs a team's agent setup is broken: engineers babysitting agents, blaming the model for what's actually a harness problem, and silently burning 500k-750k+ tokens of context on simple tasks (c1, c2).

01Symptoms of a broken agent setup

Khandelwal lists observable signs that a team's agent workflow isn't working: people babysitting their agents, blaming a model version for what is really an unchanged harness, silently burning huge amounts of context and money on simple tasks, needing constant intervention on long sessions, and generating a steady stream of low-quality output.

“if you're seeing people in your team babysitting their agents, something's wrong”

02Frame it as a leadership problem, not an IC problem

He argues the most impactful fixes to a codebase's agent-readiness require team-wide buy-in and can't be done by an individual contributor alone, so making engineers work well with agents needs to be treated as an organizational responsibility, not something left to each engineer to figure out on their own.

“It isn't really an IC's job. It's a job for leadership. It's a job for the company”

▶ watch at 05:40
03The one skill that built trust: 'ship it'

The team invested in a single high-value skill called 'ship it' that takes code from done to PR-ready automatically: opening the PR, handling review comments and CI failures, and writing PR descriptions. The skill often ran for over an hour, which initially worried people, but once they saw it deliver real value they became invested in trusting agents more broadly.

“it takes care of everything from code done to PR ready for review”

▶ watch at 09:49

“the skill was running for over an hour. And that scared people, but once you actually figure out once they saw the value, they get invested”

▶ watch at 10:19
04Scaling pains: issue overload

Wiring issues and boards directly into the repo caused the number of open issues to balloon to 400-500 within a couple of weeks, in part because multiple agents were creating issues without being coordinated correctly.

“we blew up to like 4 or 500 issues uh without like, you know, just I think within like a couple of weeks, which is a crazy number for like a repo”

▶ watch at 11:52
05Progressive disclosure as the fix

To keep agents from burning context loading everything upfront, the team set a hard cap of about 100 lines per skill.md file and treats the skill as a folder the agent can explore rather than a monolith. Documentation that an agent needs when it lands in a particular part of the codebase, like a runbook, is kept in code comments so it's discovered only when relevant, rather than front-loaded into a giant CLAUDE.md.

“we've kind of set a hard limit for like 100 lines in your skill.md cuz your skill is really a folder”

▶ watch at 14:59

“when you have like some code that requires like a runbook, make sure the runbook is reflected in the comments”
