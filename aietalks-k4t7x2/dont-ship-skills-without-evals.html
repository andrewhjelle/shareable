Almost no skills have evals

  • Skill Bench indexed over 50,000 skills from GitHub and found almost none had evals attached; most were AI-written and not really tested.
  • The speaker distinguishes capability skills (temporary, teach the model something it can't yet do consistently, retired as models improve) from preference skills (durable, encode team-specific workflow or style, protected by evals so future model changes don't degrade them).

Skills work, but AI-generated ones can hurt

  • Skill Bench 1.1 found skills improve performance by roughly 15% on average across about 100 coding and productivity tasks.
  • A follow-up analysis found human-written skills perform best, AI-generated skills can negatively impact performance, and skill files should stay below 500 lines.

03Writing better skills: eight tips
Slide at 10:50 · click any slide to enlarge · 2 more from this section below

Writing better skills: eight tips

  • Recommendations include writing directive descriptions stating the why/how/when rather than passive essays, keeping the skill lean with details layered into reference files (since the description is paid on every model call and the body is paid whenever read), setting an appropriate level of freedom (use a script instead of a skill for fixed, deterministic workflows; describe goals and constraints instead), including negative test cases to prevent over-triggering, and removing 'no-ops' (instructions that don't actually change model behavior, a pattern flagged by AI educator Matt).

“AI generated skills tend to include a lot of no-ops. And no-ops basically is an instruction which does nothing to change the agent's behavior”

said at 11:20
04Building a skill eval harness
Slide at 12:50 · click any slide to enlarge · 4 more from this section below

Building a skill eval harness

  • For a new skill covering the Gemini Interactions API (released after the model's training cutoff), the team built 117 test cases in a JSON file with fields for the prompt, target language, whether the skill should trigger, and expected checks, run through a Python script driving a coding agent.
  • Most checks were cheap regex assertions (correct SDK, model, methods, no old patterns) rather than LLM-as-judge, and the skill improved valid Interactions API code generation to almost 90%.
  • At Google DeepMind, every skill change now triggers regression evals and is blocked from merging unless it improves the test cases.

“the the end result was that we improved the the performance up to like almost 90% for generating valid interactions API code with the latest Gemini models”

said at 12:53

“if a change happens to or like a diff to the skill file, the eval will be run, and there will also be a result, and the change will not be merged if it is not improving the test cases”

said at 17:00
05When to retire a skill
Slide at 17:00 · click any slide to enlarge

When to retire a skill

  • The speaker recommends always running evals with and without a skill enabled; if the model performs as well without it, the skill can be retired to save token cost and maintenance, but the eval itself should be kept so future regressions can be detected and the skill reintroduced if needed.

“run always evals with your skill loaded and without your skill loaded. Only that way you will know when you can retire skill or if a skill is really helpful for your performance”

said at 20:33

Commentary (ours)

(ours) The claim that AI-generated skills can degrade performance cuts against the common workflow of asking a coding agent to write its own skill.md after a session; the talk's implicit recommendation is that self-authored skills need the same eval gate as human-written ones, not a lighter one.
