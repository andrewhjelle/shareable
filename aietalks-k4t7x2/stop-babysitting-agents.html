01The gap is context, not intelligence

The gap is context, not intelligence

  • Citing Andrej Karpathy, the speaker frames the current bottleneck for agents as context rather than model intelligence: engineers now function as the 'context engine' for their agents the way a new hire builds context over their first months at a company, and most teams are still at the earliest stage of that process.

“The gap is not intelligence at this point. It is context.”

02Three myths about building agent context
Slide at 07:40 · click any slide to enlarge · 2 more from this section below

Three myths about building agent context

  • The speaker names three failed approaches.
  • Naive RAG over documentation suffers from a 'satisfaction of search' problem borrowed from radiology, where the agent stops looking once it finds a first plausible match rather than searching exhaustively.
  • Wiring up more MCP connections only provides access to data, not understanding or reasoning across it.
  • And massive context windows don't help either, since models can't meaningfully reason over huge amounts of stuffed-in context.

“the radiologist will scan, and when they find something, they're like, oh, there's something on your lung. They stop looking”

03A real context engine needs a social graph and conflict resolution
Slide at 08:10 · click any slide to enlarge · 1 more from this section below

A real context engine needs a social graph and conflict resolution

  • The speaker argues a context engine needs a social graph as a pivot point, since knowing who a user is and who they work with lets it retrieve relevant code, PR history, and collaborators.
  • It must also resolve conflicts between sources of truth, such as code running in main versus a correction posted in a Slack thread by a CTO, rather than letting the agent arbitrarily pick one.

“a key component of this is a social graph because you use that as a pivot point”

said at 08:14

“It should resolve conflicts. I don't know how many times I've looked at source code that's running in main”

said at 08:44
04Lesson: cached answers go stale
Slide at 12:20 · click any slide to enlarge

Lesson: cached answers go stale

  • The speaker warns against caching good answers for latency, since a cached correct answer effectively lies to the next person who asks, because the underlying systems and code may have changed since it was cached -- similar to how documentation goes stale the moment it's written.

“if you cache a correct answer, and then tomorrow someone asks the same question, and you answer it, you probably lied to them now”

said at 12:51
05Benchmark: context engine versus MCP-only access
Slide at 08:00 · click any slide to enlarge · 8 more from this section below

Benchmark: context engine versus MCP-only access

  • In a real integration task, an agent with only MCP access to the required SaaS tools produced code that compiled and passed all code checks, but a senior engineer judged it as fundamentally wrong and said shipping it would have broken the entire system.
  • The same task run with Unblocked's context engine instead produced a plan and code that passed senior review with only a minor nitpick.

“the naive run, which just had the MCP access, basically passed all the code checks. It compiled. But the senior engineer was like, this is totally wrong”

said at 05:09

Commentary (ours)

The caching lesson generalizes beyond context engines: any system that memoizes an LLM-derived answer about a live codebase or org is implicitly making a staleness bet, and the speaker's experience suggests that bet loses more often than teams expect (ours).
