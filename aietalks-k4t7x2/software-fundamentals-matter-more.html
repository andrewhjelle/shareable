"Software Fundamentals Matter More Than Ever"

Useful when deciding whether to trust a spec-driven, 'edit the spec not the code' AI workflow: the talk argues that skipping code review degrades output over successive AI passes, and offers two concrete artifacts -- a 'Grill Me' alignme...

If you only read one thing

  • Running a 'specs to code' loop (edit the spec, don't look at the code) produces progressively worse code each pass, so bad code is now the most expensive it has ever been (c1, c3).
  • A 'Grill Me' skill interviews the developer on every branch of a plan, replacing the assumption that human and AI already share an unstated 'design concept' before code gets written (c4, c5).
  • Restructuring a codebase into few, deep modules with simple interfaces (instead of many shallow ones) makes it testable enough that TDD and other feedback loops actually catch AI mistakes, and lets the implementation be delegated while the interface stays human-controlled (c6, c7, c8).

01Specs-to-code makes code worse each pass

Specs-to-code makes code worse each pass

  • The speaker describes running the 'specs to code' loop himself -- writing a spec, generating code, and editing the spec rather than the code when something breaks -- and finding the output got worse each time he reran it.
  • He grounds 'bad code' in John Ousterhout's definition of complexity: anything about a system's structure that makes it hard to understand and modify.

“I would run it, and I would try not to look at the code, but I would look at the code, and I realized I would get code out”

“Complexity is anything related to the structure of a software system that makes it hard to understand and modify the system”

said at 02:36

“I think code is not cheap. In fact, bad code is the most expensive it's ever been”

02Grill Me: aligning on a shared design concept before code

Grill Me: aligning on a shared design concept before code

  • Drawing on Frederick Brooks' idea of a 'design concept' shared between collaborators, the talk introduces a short skill called Grill Me that interviews the developer relentlessly about a plan until a shared understanding is reached.
  • A related 'ubiquitous language' skill, borrowed from domain-driven design, scans the codebase for terminology and produces a shared glossary that is kept open during planning.

“Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree”

said at 05:41

“it not only improves the planning, but it allows the AI to think in a less verbose way, and actually means that the implementation is more aligned with what you actually planned”

said at 09:19
03TDD depends on the code base, not just the AI

TDD depends on the code base, not just the AI

  • The Pragmatic Programmer's idea of 'outrunning your headlights' -- moving faster than your feedback loop allows -- is used to argue that AI needs test-driven development (red-green-refactor) to take small, verified steps rather than producing large amounts of code before checking it.

“outrunning your headlights. It's essentially driving too fast because the rate of feedback is your speed limit”

said at 10:52
04Deep modules over shallow ones

Deep modules over shallow ones

  • Citing Ousterhout again, the talk contrasts deep modules (simple interface, lots of hidden functionality) with shallow modules (complex interface, little functionality), arguing deep modules are what makes a codebase testable.
  • Once a module's interface is well designed, its implementation can be treated as a 'gray box' -- something to verify from the outside without reviewing every line inside.

“He talks about having deep modules in your codebase. Not shallow modules, not lots of modules that expose type kind of um lots of functions”

said at 12:26

“it also means you can kind of treat these modules, or these deep modules, as gray boxes”

said at 15:34
05Code is not cheap

Code is not cheap

  • The talk closes by rejecting the idea that 'code is cheap' in the AI era, framing AI as a tactical, on-the-ground programmer that still needs a human thinking at the strategic level -- the role that requires the software fundamentals the talk argues matter more now, not less.

“if we think about AI as a really great on-the-ground programmer, a kind of tactical programmer, a sergeant on the ground making the code changes, you need someone above that”

said at 17:08
