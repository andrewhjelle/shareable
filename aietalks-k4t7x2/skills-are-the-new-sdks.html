Skills are the New SDKs

SpeakerElvin Aghammadzada · DataRobot Watchyoutu.be/LC3-P7v3yoI
Agentic engineeringContext engineeringMCP & protocols

If you only read one thing

  • Context rot sets in around 40% context window usage ('the dumb zone'), so loading every instruction, MCP tool, and document upfront can make an agent perform badly before the conversation even starts.
  • 15 MCP servers can consume over 100,000 tokens per session just in tool definitions before any conversation happens; skills cut that by roughly 10x via progressive disclosure of metadata only.
  • LLM-generated skills currently hurt performance (more tokens, more reasoning time) versus human-written skills, per recently published research the speaker cites.
01Longer context does not mean better performance

The speaker cites a paper called 'context rot' showing that performance starts to degrade after about 25% usage of a context window, and separately frames a '40% context used' threshold as the point where an agent shifts from a 'smart zone' into a 'dumb zone.' He argues that loading many MCP tool descriptions and documents upfront can fill this budget before a user ever sends a message.

“there was a paper called context rot, and it proves that after 25% usage of the context window”

“if you would you are getting past this 40% context used it typically goes into a zone called dumb zone”

02Skills use progressive disclosure to cut token cost

He contrasts 15 connected MCP servers, which he estimates consume over 100,000 tokens in tool definitions alone per session, against skills, which expose only metadata (a small front-matter block, under ~100 tokens) to the agent at runtime and load the full body (under ~5K tokens) only when activated.

“if it's connected to 15 MCP server, I'm pretty sure it's consuming over 100,000 tokens per session just in tool definitions itself”

▶ watch at 12:43

“same operational headache becomes really small, probably at least 10 times smaller with skills”

▶ watch at 13:13
03Skills vs MCP are complementary, not competing

Both are Anthropic-originated. MCP defines what actions an agent can take and typically runs isolated in a separate environment; skills change how an agent thinks about a problem and can self-modify based on experience, running on the agent's own machine. A skill can itself expose or wrap an MCP server.

“MCP kind of definitions for what actions the agent should take. In a sense that it doesn't change the agent definition”

▶ watch at 16:07

“less than 100 tokens typically, which agent do have access to prior to the execution. And then second one is the markdown body”

▶ watch at 21:20
04The ecosystem and its risks

The speaker states there are 26+ platforms supporting skills and cites the open-source Claude Agent Skills repository as the most-starred repository in the ecosystem, ahead of prior popular repos, built by a coding agent with roughly ten tools plus skills on top. He flags risks: prompt injection in publicly shared skills, no process isolation compared to MCP, and marketplaces that lack verification, comparing the situation to early npm.

“actually the LM generated skills hurts the performance of LM in a sense that it uses more tokens”

▶ watch at 24:28

“these marketplaces still lack the verification control. Just like how NPM was scary 10 years ago”

▶ watch at 25:01

Commentary (ours)

The claim that a general-purpose agent with ~10 tools plus skills can replace domain-specific agent builds (ours, extrapolating from his Open Agent example) implies the build pattern for enterprise agents may shift from 'build an agent per use case' to 'build one agent, ship skill libraries per domain' -- worth testing against a real vertical use case rather than taking on faith.
