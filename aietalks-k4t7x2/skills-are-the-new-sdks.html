Skills are the New SDKs

takeAgentic engineeringContext engineeringMCP & protocols

Gives a concrete threshold (40% context usage) for when an agent's performance degrades, and a concrete token-cost comparison between MCP tool definitions and skills' progressive disclosure

If you only read one thing

  • Context rot sets in around 40% context window usage ('the dumb zone'), so loading every instruction, MCP tool, and document upfront can make an agent perform badly before the conversation even starts.
  • 15 MCP servers can consume over 100,000 tokens per session just in tool definitions before any conversation happens; skills cut that by roughly 10x via progressive disclosure of metadata only.
  • LLM-generated skills currently hurt performance (more tokens, more reasoning time) versus human-written skills, per recently published research the speaker cites.
▣The system in one picture (ours, from the slides and the transcript)

The speaker frames skills as a fix for MCP-driven context bloat, but the savings assume human-written skills and a trusted source; his own cited research and marketplace warning cut against both assumptions (ours).

Longer context does not mean better performance

Skills use progressive disclosure to cut token cost

  • He contrasts 15 connected MCP servers, which he estimates consume over 100,000 tokens in tool definitions alone per session, against skills, which expose only metadata (a small front-matter block, under ~100 tokens) to the agent at runtime and load the full body (under ~5K tokens) only when activated.

03Skills vs MCP are complementary, not competing
Slide at 15:40 · click any slide to enlarge · 5 more from this section below

Skills vs MCP are complementary, not competing

  • Both are Anthropic-originated.
  • MCP defines what actions an agent can take and typically runs isolated in a separate environment; skills change how an agent thinks about a problem and can self-modify based on experience, running on the agent's own machine.
  • A skill can itself expose or wrap an MCP server.

“MCP kind of definitions for what actions the agent should take. In a sense that it doesn't change the agent definition”

04The ecosystem and its risks
Slide at 24:30 · click any slide to enlarge · 5 more from this section below

The ecosystem and its risks

  • The speaker states there are 26+ platforms supporting skills and cites the open-source Claude Agent Skills repository as the most-starred repository in the ecosystem, ahead of prior popular repos, built by a coding agent with roughly ten tools plus skills on top.
  • He flags risks: prompt injection in publicly shared skills, no process isolation compared to MCP, and marketplaces that lack verification, comparing the situation to early npm.

“actually the LM generated skills hurts the performance of LM in a sense that it uses more tokens”

“these marketplaces still lack the verification control. Just like how NPM was scary 10 years ago”

said at 25:01

Commentary (ours)

The claim that a general-purpose agent with ~10 tools plus skills can replace domain-specific agent builds (ours, extrapolating from his Open Agent example) implies the build pattern for enterprise agents may shift from 'build an agent per use case' to 'build one agent, ship skill libraries per domain' -- worth testing against a real vertical use case rather than taking on faith.
