Enterprise Agents Have a Structure Problem

Daga names the three failure modes that actually sink enterprise data agents (ambiguity over source of truth, stale context, unresolved per-team preference) and argues throwing a bigger model at the problem doesn't fix any of them

If you only read one thing

  • Bad agent answers usually trace to ambiguity, staleness, or preference, not model size (c1).
  • Build source-of-truth layers in order: semantic layer and canonical tables first (cheap, cover ~80%), database graph last (c3, c4).
  • Preference is still unsolved industry-wide; neither a semantic layer nor agent memory actually captures which metric definition an individual wants (c7, c8).

Bigger models don't fix bad agent answers

  • Daga says the instinctive fixes to a bad agent answer, a bigger model, more context, more knowledge-base files, don't address the real causes.
  • She identifies three underlying problems: ambiguity about which data source is authoritative, staleness of context as definitions and processes change, and unresolved individual or team preference on how to calculate a metric.

“The agent actually has these three main problems.”

02Structure sources of truth into a hierarchy
Slide at 02:40 · click any slide to enlarge · 2 more from this section below

Structure sources of truth into a hierarchy

  • Her fix for ambiguity is a three-tier hierarchy from cleanest to messiest: a curated semantic layer of KPI definitions, canonical parametric tables, and a full database graph connecting tables to columns to metrics.
  • She recommends enterprises build the first two layers first since they're easier to set up and cover most of the problem, leaving the graph, which is harder to build and maintain, for the remaining cases.

“It can't weight all the knowledge bases equally.”

said at 02:37

“I feel if an enterprise is approaching or adding sources of truth, they should start adding the first and the second layer first.”

said at 05:12

“These are easy to set up, solve I think 80% of the problems, and then the 20% can be solved by the database graph.”

said at 05:12
03Staleness needs a logged feedback loop
Slide at 05:30 · click any slide to enlarge · 4 more from this section below

Staleness needs a logged feedback loop

  • Context rots as processes, KPIs, and definitions change faster than teams can hand-update docs.
  • Daga's answer is a context lifecycle: embed live, frequently-updated data sources, and log every correction event (a wrong definition, a new filter) so it feeds back into updating the agent's context, paired with ongoing evaluation.

“the context gets rotten, or it gets deprecated, or processes change so often that it's hard to maintain dot MD files, or keep on updating your skills with the most latest context.”

said at 05:43

“creating this feedback loop or a context loop where you log, evaluate, update the context every or every so often is very important.”

said at 08:18
04Preference remains unsolved
Slide at 09:40 · click any slide to enlarge · 2 more from this section below

Preference remains unsolved

  • Different teams calculate the same metric differently and both are 'correct,' which is a subjective problem current approaches don't resolve.
  • She says a semantic layer still requires the user to specify which definition they want, and agent memory tools like a memory.md file store a preference but can't distinguish between competing metric definitions or route to the right one automatically.

“while this is a great question, I feel the industry still does not have a correct answer or correct way to solve the problem itself.”

said at 09:51

“agent memory, which is your mem zero or like storing memory.md file, but it still is not the best way. It stores your preference but it can't understand the distinction between two different metrics or which one to use when.”

said at 10:24

Commentary (ours)

The framing implies these three problems are sequential in difficulty (ambiguity solvable, staleness solvable with process, preference genuinely open), which is a useful triage lens for anyone scoping a data-agent build (ours).
