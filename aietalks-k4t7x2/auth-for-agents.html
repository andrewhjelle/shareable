You Didn't Ship a Bug. You Just Wrote It for a Human.

SpeakerRavi Madabhushi · Scalekit Watchyoutu.be/lMCxVorb9wM · 12 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. patternSecurityAgentic engineeringMCP & protocols

Madabhushi names a specific, checkable failure mode: MCP servers and OAuth scopes built for human actors don't constrain what an agent can do once it's authenticated, so agents end up over-permissioned by default

If you only read one thing

  • Most agents get more permissions and scopes than their actual job requires, because existing auth primitives don't support fine-grained scoping.
  • Traditional auth assumes whoever authenticates is who acts, and that the actor is deterministic; agents break both assumptions since they act on behalf of a user and behave non-deterministically.
  • Most MCP servers surface all available tools regardless of which user authorized the agent, letting the agent pick the wrong tool for its context.

A latency bug exposed an auth assumption built for humans

  • Madabhushi traces the talk back to a recurring latency spike caused by a 'last seen' timestamp being updated on every API hit.
  • Once agents started hitting their APIs, that update fired 60 times faster than expected because the system assumed a human update cadence, prompting him to question whether authentication and authorization need to be rebuilt for agents rather than patched.

“we realized that this last seen update is happening 60 times faster than what it would, and that is creating unnecessary pressure in our DB write system”

Agents get over-scoped by default

  • He states that most agents his company's customers build have far more permissions and scopes than their job requires, not from carelessness but because existing auth primitives don't support extremely fine-grained access, so broad-by-default becomes the norm.

03Two old auth patterns both assume actor equals principal
Slide at 04:10 · click any slide to enlarge · 1 more from this section below

Two old auth patterns both assume actor equals principal

  • Madabhushi describes the two existing identity patterns: a human authenticating and acting through their own session or API key, and a deterministic service account with fixed permissions.
  • Both rest on the same principle, that whoever authenticates is the one acting, and that every action ties back to permissions fixed at registration time.

“the fundamental philosophy that we've always maintained is whoever is authenticating is the one that is acting. Every action the program or the human takes is based on fixed set of permissions that actor was granted at some time.”

said at 03:32
04Agents break the actor-equals-principal assumption
Slide at 06:20 · click any slide to enlarge · 2 more from this section below

Agents break the actor-equals-principal assumption

  • He argues agents fundamentally differ because the principal (the user) is not the same as the actor (the agent acting on the user's behalf), and because the agent's behavior is not deterministic the way a human-written program's behavior is.
  • This means past behavior can't guarantee the agent won't do something different on its next run.

“in the case of agents, the principal is not the same as an actor. You need to give delegated access, so that the agent can act on behalf of the user.”

said at 05:48

“Just because an agent does certain things today, you can't be 100% certain that the agent can't do the same or the exact same thing tomorrow, day after, or even if it's the next immediate run.”

said at 06:21
05MCP servers over-expose their tool surface
Slide at 08:30 · click any slide to enlarge · 1 more from this section below

MCP servers over-expose their tool surface

  • Madabhushi says most MCP servers his company has worked with don't limit which tools an agent can access based on who authorized it; they surface the full set of tools the user or application supports and let the agent decide, which can lead the agent to pick the wrong tool.

“most of the MCP servers that we've worked with don't actually limit the tool context access to the agent based on which user authorized the agent. They typically surface all the tools”

said at 08:22
06Fine-grained, time-bound scopes and full audit visibility are the fix
Slide at 09:00 · click any slide to enlarge · 4 more from this section below

Fine-grained, time-bound scopes and full audit visibility are the fix

  • He recommends binding the agent (actor) to the principal at all times, giving agents their own identity with fine-grained, attribute- and context-level scopes rather than broad OAuth scopes, and enforcing least privilege with just-in-time elevation.
  • He also says teams need full visibility into every agent action, including who authorized it and for how long, because without that visibility you're only hoping the agent behaves.

“the actor, in this case, an agent, has to be bound to the principal at all times. And the agent should have its own identity. Agent should have extremely fine-grained credentials”

said at 09:03

“agents should be least privileged by default and they should be able to ask for just-in-time authorization if they want elevated scopes”

said at 10:55

“if you can't deterministically control what your agent can or cannot do, then you're just praying that agent doesn't end up doing what it's not supposed to do. And praying is not a strategy”

said at 11:59
