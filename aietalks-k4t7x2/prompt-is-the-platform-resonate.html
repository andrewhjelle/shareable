The Prompt is the Platform

SpeakerDominik Tornow · Resonate HQ Watchyoutu.be/DqtmZE6Hl0g
Agentic engineeringContext engineeringInfra & serving

If you only read one thing

  • Resonate's bet is that reusable value moves from a general-purpose implementation to an abstract specification, from which agents generate multiple bespoke, target-specific implementations.
  • Asking an agent to jump directly from an abstract spec to a concrete implementation (Rust/Postgres) produced a system that passed happy-path tests but broke under concurrency, process failure, and network failure.
  • Inserting a deterministic simulation environment that exposes normally-hidden facts (like whether a read was fresh or stale) let the agent design and verify the algorithm before writing the concrete spec and implementation.
01Reuse moves from implementation to specification

The speaker's working theory is that general-purpose implementations will increasingly be replaced by bespoke implementations generated on demand as a minimal extension of existing infrastructure, so teams should reuse a specification and derive a bespoke implementation from it rather than reusing a library or framework. For Resonate, this means the product is the specification/protocol, from which multiple server implementations (including partner-specific ones) are derived.

02Direct spec-to-implementation failed on a Postgres build

When the team first asked an agent to build a Resonate server in Rust on Postgres directly from the abstract specification, the agent produced a system that passed basic tests but broke on concurrency, process failure, and network failure. The team addressed this by inserting an intermediary concrete specification (data schema, indices, SQL queries, transaction boundaries), interactively derived with the agent but human-driven, after which the agent could implement a production system -- though the agent helped build the system without helping design it.

“the process failure. It broke on the network failure. The implementation was closer to a prototype, but not a production system”

▶ watch at 05:41

“but the agent did not help us design the system. And if the specification is a reusable product, then that's not enough”

▶ watch at 06:43
03Deterministic simulation lets the agent design, not just build

For a second target platform (NATS.io), the team instead asked the agent to first build a simulated implementation to discover the correct algorithm under partial failure, only writing the concrete specification and implementation after the algorithm was verified in simulation. The simulation environment models NATS.io's versioned key-value store, including that reads can return stale values that are still legal under the platform's consistency model.

“we gave the agent access to a deterministic simulation environment. And we gave it a different task. Do not build the production system. Build a simulated implementation”

▶ watch at 07:14

“That is not corruption. That is not a bug in the key value store. That is a valid read under the consistency model of the target platform”

▶ watch at 10:29
04Exposing hidden facts ("forbidden fruit") for agent debugging

The simulation records information the real platform hides from the algorithm -- whether a given read was fresh or stale, and what the latest value actually was -- which the algorithm itself must not depend on but which the agent can use to explain why a designed algorithm was wrong. Using this, the agent built a proof of concept verified by fuzz testing, then derived the concrete specification and finally the concrete implementation.

“That information is forbidden to the algorithm, but it is incredibly useful to the agent”

▶ watch at 15:09

“the agent built a proof of concept in the deterministic simulator, verified by fuzz testing”

Commentary (ours)

The distinction drawn -- agents helping build a design versus helping create one -- maps onto a broader question of where in a pipeline agents should be given genuinely open latitude versus constrained to fill in a human-authored decision; the simulation-environment technique looks like a reusable pattern for any domain with a well-defined but hidden correctness model (ours).
