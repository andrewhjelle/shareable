Lessons from Studying Every Memory System

takeMemoryProduct & UXContext engineering

This is a survey of how competing products' memory architectures diverged and converged, building toward an opinion about what remains unsolved, not one system explained end to end.

If you only read one thing

  • ChatGPT memory v1 (Feb 2024) put the burden of memory management on the user and suffered from staleness; the general lesson is that memory cannot be outsourced — every top consumer AI product builds it in-house (c1, c4).
  • Claude's profile is about 1,000 tokens updated every 24 hours versus ChatGPT's roughly 4,000 tokens updated every few days — a direct tradeoff between update cost and serving cost that the speaker frames as 'memory is a function of compute' (c2, c3, c5).
  • Even a well-resourced running-profile system has a 'massive context problem': it can't reason over rich existing context like email or in-person conversations, so it can hold factually wrong beliefs (e.g. a still-listed trip to a place the user never went) and isn't even curious about the contradiction (c6).

How memory evolved: ChatGPT v1 to v2

  • ChatGPT's first serious memory implementation (Feb 2024) let users tell it to remember facts, which were stored in a visible, deletable list and added to every conversation's context.
  • Khemani says the core flaw was that because every memory creation was visible, users felt responsible for managing memory themselves, and facts went stale (a since-past trip to Bengaluru stayed in his context indefinitely).
  • ChatGPT's v2 (April 2025) replaced this with an asynchronously updated 'running profile' — a dense, roughly 4,000-token summary refreshed every few days — which fixed the user-burden problem but not staleness (a still-listed Thailand/Turkey travel conflict persisted).

“The biggest one was that as a user, because you could see every time a memory was created, it felt like you were responsible for both creating memories while you were just trying to have a conversation”

said at 03:07
02Claude took the opposite approach, then converged
Slide at 08:10 · click any slide to enlarge · 1 more from this section below

Claude took the opposite approach, then converged

  • Claude's first memory version (August 2025) had no stored profile at all — just tools to search past conversations by keyword or time period, with every conversation starting fresh.
  • After Khemani's public comparison of the two architectures, Claude released v2 with its own running profile: visible to users (unlike ChatGPT's), about 1,000 tokens versus ChatGPT's 4,000, written as full sentences rather than dense keywords, updated every 24 hours, and editable.
  • ChatGPT later added its own conversation-search tool and made a version of its profile visible, converging toward the same general shape while keeping different implementation details.

“this profile was a,000 tokens. So it was much smaller than chat GPT's 4,000 tokens”

said at 08:16

“Claude's profile updates every 24 hours. For chat GPT, it's every few days. And Claude also let you let the user make explicit edits to this profile”

03Lesson: memory cannot be outsourced

Lesson: memory cannot be outsourced

  • Because every major product (ChatGPT, Claude, Gemini, coding agents like Claude Code) independently arrived at a different concrete memory architecture despite converging on the general shape of a running profile, Khemani concludes there is no single correct way to do memory, and no serious team should treat it as an outsourced, bolted-on component — it has to be built and evolved alongside the product.

“The implications of this is that memory cannot be outsourced. If you're a serious team, you do not outsource memory. It is something that you build alongside your product”

said at 11:25
04Lesson: memory is a function of compute
Slide at 15:20 · click any slide to enlarge · 1 more from this section below

Lesson: memory is a function of compute

  • A running profile has two costs: an update cost (how often and how much compute is spent regenerating it) and a serving cost (how many tokens it adds to every conversation).
  • Khemani reads ChatGPT's and Claude's designs as opposite points on this tradeoff curve — larger profile, less frequent updates versus smaller profile, more frequent updates — driven by real GPU constraints rather than by an ideal design.

“memory is a function of compute. What does that mean? Let's look at the costs associated with a running profile”

said at 11:56
05The unsolved problem: context, not architecture
Slide at 16:40 · click any slide to enlarge

The unsolved problem: context, not architecture

  • Khemani's closing argument is that even a perfect memory architecture is capped by how much context it can gather about the user.
  • His own example: ChatGPT's profile still lists him as having traveled to Turkey in 2025 (from a conversation weighing Thailand vs.
  • Turkey) despite him actually going to Thailand, a fact recorded in his email but never reasoned over.
  • He calls this a product problem, not a technology problem — these systems aren't built to notice or resolve such contradictions.

“So for me, none of this feels like 2026. And what I keep asking myself every day is when will personal AI feel like personal AI”

said at 18:14

“I still think we're very early. Memory for AI is just a three-year-old field”

said at 18:14

Commentary (ours)

The 'memory is a function of compute' framing is a useful lens for scoping a memory feature: the real design choice is where on the update-frequency/profile-size curve to sit, not whether to build a profile at all. (ours)
