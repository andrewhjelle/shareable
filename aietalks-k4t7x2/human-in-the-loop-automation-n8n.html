Human-in-the-Loop Automation with n8n

SpeakerLiam McGarrigle · n8n Watchyoutu.be/tDArkCqjA-c
Agentic engineeringMCP & protocolsMemory

If you only read one thing

  • n8n's AI agent node exposes each tool field individually to the model rather than raw API access, and its built-in memory node defaults to a 5-message context window that most users should raise (c4, c5, c6)
  • A human-review node sits between the agent and a destructive tool call; the agent doesn't even know the review step exists, it just calls the tool and n8n intercepts it, so tool descriptions must explicitly tell smarter models the check exists or they may refuse to call the tool at all (c1, c2, c3)
  • n8n's native MCP server can both read/write and execute published workflows from an external agent like Claude, and the speaker recommends splitting large agents into an orchestrator plus specialized sub-agents (calendar/email, GitHub, Jira), each on its own model (c7, c8)
01Building a Gmail/Calendar agent with memory

The workshop builds a chat-triggered AI agent connected to Gmail and Google Calendar as tools. Because the underlying model provider (OpenRouter) doesn't persist conversation state, n8n's simple memory node is used to store it, with a context window length that defaults to 5 messages -- a limit the speaker says should usually be raised, at the cost of paying for more tokens per turn.

“I just always use simple memory unless I'm doing something super fancy. Even though it says for beginners, no shame”

02Tools expose fields individually, not full API access

Unlike giving a coding agent broad API access to a service, an n8n tool node exposes only the specific fields you configure, so the agent can set only what you allow it to set -- at the cost of the builder having to configure every field ahead of time.

“when we're giving a something a tool in NADN, it has every single field individually. So it can only set the things that we tell it to specifically”

▶ watch at 26:50
03Human review intercepts destructive tool calls

Adding a human-review step before a destructive action (sending an email, creating a calendar event) makes it structurally impossible for the tool to execute without approval, delivered through whatever chat platform is wired up. The agent itself is not aware the review step exists -- it calls the tool as normal and n8n intercepts the call -- which the speaker says can make more capable models hesitant to call the tool unless the description explicitly tells them a human-in-the-loop check exists and it's safe to proceed.

“everything that we would consider like destructive or sensitive, we can add a human review step”

▶ watch at 41:21

“that tool can't be called without going through that. It's just in the way. We at NAND made that layer to just intercept it in the middle”

▶ watch at 50:30

“AIs that are a little smarter, they typically won't just send an email without asking unless you specifically tell it to”

04MCP server and scaling to sub-agents

n8n ships a native MCP server that can create, read, and also execute published workflows from an external agent such as Claude. For agents accumulating many tools, the speaker recommends using a sub-agent architecture -- one orchestrator agent delegating to specialized sub-agents (e.g., calendar/email, GitHub issues, Jira), each able to run a different, optimized model.

“it's able to create, read, do all that. It's actually also able to execute. So you could say to M, you could say to Claude,”

▶ watch at 62:09

“then you can have one agent that calls other specialized agents. So this agent we just made can go to be a calendar and email management sub agent”

Commentary (ours)

The human-review pattern is presented as a hard structural block ('a brick wall, nothing getting past it'), but the speaker's own answer to a phone-call/voice-agent use case is that it currently only works through chat platforms with buttons -- worth noting the mechanism doesn't yet generalize to every interface an agent might run in (ours).
