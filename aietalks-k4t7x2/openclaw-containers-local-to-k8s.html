Lobster Trap: OpenClaw in Containers from Local to K8s and Back

SpeakerSally Ann O'Malley · Red Hat Watchyoutu.be/F1DYkY1BlfM
Infra & servingSecurityAgentic engineering

If you only read one thing

  • Containers give agents reproducibility, secret isolation, portability across laptop/X86/Mac/Kubernetes, and volume-backed backup/recovery.
  • Podman secrets plus OpenClaw's own secret-ref feature create a double layer of separation so API keys never show up in logs.
  • An Nvidia team runs ~10 engineers' OpenClaw instances in Kubernetes for model evals, described as doing the work of six engineers for one person.
01Why run agents in containers

The speaker argues containers give an agent instance reproducibility, secret isolation, and portability across laptop, X86, Mac, and Kubernetes, backed by volumes for backup and recovery. She frames this as the same reasoning that applies to any containerized application, just now applied to persistent AI agent workloads.

“it's reproducible, you can isolate your secrets, it's portable across infra, I can run on my laptop, I can run it on my X86, I can run it on my Mac”

▶ watch at 04:08
02Secret handling: Podman secrets plus OpenClaw secret refs

She runs everything with Podman rather than Docker, using Podman's secrets feature to store API keys and mount them into the container as a reference rather than a plain env var. OpenClaw has its own secret-ref feature on top of that, so an API key becomes a pointer to a Podman secret. The same pattern extends to Kubernetes secrets, where a secret ref replaces a straight env var.

“I run everything with Podman, not Docker. Um but in theory you can do anything with Podman and Docker.”

▶ watch at 06:10

“Kubernetes has Kubernetes secrets and same thing, instead of just a straight env var, you have a secret a secret ref to an env var”

▶ watch at 07:14

“makes them Open Claw secret refs. Very cool feature of Open Claw. Definitely enable that. For every current credential, create a secret ref.”

▶ watch at 16:39
03A real production example: Nvidia's eval team

At PyTorchCon the day before the talk, a Red Hat contact at Nvidia described running model evals with OpenClaw: about 10 engineers each run their own OpenClaw instance in Kubernetes, periodically checking in on eval jobs, which the speaker's contact said was like doing the work of six engineers by himself. The speaker frames this as evidence agents free people for higher-value work rather than eliminating jobs.

“They are running their model evals with OpenClaw. They have about 10 engineers. They each have their OpenClaws running in Kubernetes”

▶ watch at 09:17

“We're not all losing our jobs, people. Like that's not happening. What's What that is enabling for his team is they get to do fun stuff, interesting stuff.”

▶ watch at 09:48
04A team onboarding vision and a Mac limitation

She proposes a company-standard 'curated baseline' OpenClaw image for new hires that bundles approved MCP servers, company authentication, and team-specific skills, which employees then personalize. She also notes a practical limitation: on Mac, containers run inside a VM, so spawning a container from within a container isn't currently something she's solved, unlike on Linux.

“It has your list of company approved MCP servers, your authentication that is approved through your company.”

▶ watch at 11:56

“whenever you're running a container on your Mac, you're running in a virtual machine”

▶ watch at 14:33

Commentary (ours)

The Nvidia example (10 engineers, claimed 6x leverage) is anecdotal and unverified, but the underlying pattern -- containerize the agent, use secret refs everywhere, lift local to Kubernetes -- is a reusable minimal-viable setup for anyone running agents as persistent services rather than one-off CLI sessions (ours).
