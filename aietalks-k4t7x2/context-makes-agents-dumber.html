Why More Context Makes Your Agent Dumber and What to Do About It

Draws on Qodo's production experience running agentic code review to argue that dumping more context degrades results (a 'lost in the middle' effect) and that fixing it requires context-optimization strategy, not bigger context windows

If you only read one thing

  • LLMs show a U-curve where initial and final inputs get weighted but middle context is effectively dropped, so dumping more context doesn't make agents smarter.
  • Context engines, hierarchical summarization, knowledge graphs, and iterative retrieval each trade off upfront indexing effort against scaling limits (e.g. context engines get unpredictable past 600-700 repos).
  • An 80/20 split -- high-reasoning models for open-ended research/discovery (80%) and cheaper deterministic models for final validation/summarization (20%) -- plus a mixture-of-agents-with-judge-agent pattern (used in Qodo's own PR review architecture) helps contain orchestration loops and reconcile conflicting agent outputs.

01The lost-in-the-middle problem
Slide at 02:30 · click any slide to enlarge · 4 more from this section below

The lost-in-the-middle problem

  • The speaker argues that context size is not the bottleneck; current LLMs show a U-curve pattern where the initial and final portions of provided context are used but content in between is effectively purged.
  • Qodo has been benchmarking this internally by controlling what context is given to code-review agents and checking whether mid-context material (e.g.
  • Jira links, MCP tool context) actually gets used, versus being dropped in favor of the start and end of the prompt.

“we see a pattern where it takes the initial inputs you provide, it takes the last inputs, but the in between context is basically removed”

said at 02:38
02Context-retrieval strategies and their tradeoffs
Slide at 05:10 · click any slide to enlarge · 3 more from this section below

Context-retrieval strategies and their tradeoffs

  • For messy large codebases, a context engine (search + ranking logic acting as a 'bouncer') helps, but indexing effort is moderate while scaling becomes unpredictable once a codebase spans roughly 600-700 repositories.
  • Other approaches include hierarchical summarization (per-file/folder summaries, requiring heavy LLM processing on every change), knowledge graphs (good for logical file dependencies but high upfront developer input), iterative retrieval (an index-like 'library card' approach with lower developer input and better results for non-product teams), and self-correction via a critic node that can trigger a retry when context appears lost.

“if you have a large messy code base it makes sense to create a context engine because it creates a search pattern it creates ranking logic”

said at 05:18

“if you start talking about 600 repositories or 700 repositories the mapping and the indexing starts to slow down and it becomes again unpredictable”

said at 05:50
03The orchestration paradox and the 80/20 fix
Slide at 08:20 · click any slide to enlarge · 3 more from this section below

The orchestration paradox and the 80/20 fix

  • As models get smarter, they can spend most of their tokens deciding how to solve a problem rather than solving it, hopping between methods in a research loop -- a failure the speaker calls the orchestration paradox.
  • Qodo's fix is an 80/20 hybrid: give agents high-reasoning 'latest and greatest' models freedom to research for about 80% of a task, but gate the remaining 20% (final validation, summarization) with more deterministic, restricted, cheaper models, backed by counters or timeouts to bound the research loop.

“most of the API tokens are wasted on finding a way to do it rather than doing it”

said at 08:24

“What our teams are doing is giving the latest and the greatest models or giving the agents power to research 80% of the time”

said at 09:25
04One agent overload vs. mixture of agents with a judge
Slide at 12:10 · click any slide to enlarge · 2 more from this section below

One agent overload vs. mixture of agents with a judge

  • Giving one large-context agent multiple tasks (e.g. testing, review, and multiple fixes at once) tends to cause it to get overwhelmed and silently drop some of the original tasks.
  • Qodo's alternative is mixture of agents: small specialist agents (e.g. security, coding, Jira-issue agents) each work their slice, and a judge agent reconciles their outputs so they combine into one coherent result instead of conflicting recommendations.

“maybe you give four tasks to the agent and somewhere down the line it focuses on two tasks. So you get great results for the two task but the other two just just get lost in the middle”

said at 12:33

“a judge agent help us to combine these and make one sense out of it instead of getting so many things which doesn't make sense together”

said at 14:10
05Qodo's PR review architecture
Slide at 14:30 · click any slide to enlarge · 8 more from this section below

Qodo's PR review architecture

  • Qodo's own code-review system implements this pattern: a context collector gathers context from PRs, the context engine, and other tools, then distributes relevant slices to specialized sub-agents (security, code-diff, Jira-issue agents, etc.), and a judge agent evaluates their combined output against relevance criteria, including checking PR history and prior developer feedback, before surfacing results to developers.

“we have a context collector which actually goes and collect context from the PRs it could collect context from the context engine”

said at 14:41

Commentary (ours)

The 80/20 split is really a cost-and-failure-mode argument disguised as a ratio -- the more interesting transferable claim is that orchestration loops from smarter models are a new failure category distinct from hallucination, and probably needs its own detection/guardrail layer as models keep getting more capable at 'finding better methods' (ours).
