One Login to Rule Them All: Cross-App Access for MCP

SpeakerGarrett Galow · WorkOS Watchyoutu.be/EmhRyw6xeT0 · 23 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. patternMCP & protocolsSecurityAgentic engineering

Directly relevant to anyone rolling out MCP servers/clients (Claude Code, Cursor) across a team: explains why per-tool OAuth consent doesn't scale, why IT loses visibility into which MCP servers and AI agents are in use, and why leftover...

If you only read one thing

  • MCP's OAuth-based consent flow requires a separate approval per tool per user, and at team scale this becomes dozens of people managing dozens of consent screens with no IT visibility into which MCP servers or AI clients are in use.
  • Leftover OAuth access and refresh tokens can leave MCP server access valid for days, weeks, or months after an employee's SSO access is revoked, since most companies don't use SCIM for full revocation.
  • WorkOS's cross-app access (XAA) fix uses the identity provider as a trust broker issuing short-lived ID Jag tokens (about 5 minutes) so access auto-expires if the SSO session is locked, but it only solves authentication, not authorization/scoping, and Microsoft Entra doesn't support it yet.

01Per-tool consent screens don't scale to a team

Per-tool consent screens don't scale to a team

  • Using MCP servers with a client like Cursor means clicking through a consent screen for every tool, which the speaker describes as something users click through without reading, sometimes having to repeat for no clear reason.
  • Multiplied across a user connecting to a half dozen or a dozen MCP servers and then across a whole team, this becomes dozens of people spending significant time managing consent screens.

“You have this nice little consent screen that you're not going to read. You're just going to say okay. And you're going to get redirected back. And you need to do this for every single tool, which is frankly pretty annoying.”

“as a user you might log into a half dozen or a dozen MCP servers. Um, but when you combine that together across your team, you basically have dozens and dozens of people spending all this time managing all these”

02MCP's OAuth model assumes apps don't trust each other, but companies already have SSO

MCP's OAuth model assumes apps don't trust each other, but companies already have SSO

  • MCP's consent-screen pattern comes from OAuth's original assumption that two systems don't trust each other and therefore need explicit per-app consent, which conflicts with how companies actually operate today using single sign-on through an IDP like Okta or Entra.
  • This also means IT teams cannot tell which MCP services or which AI agent clients (Cursor versus an arbitrary alternative) an employee is actually using.

“the way OAuth was kind of invented around was a thing of like, you don't trust, you know, these two systems don't trust each other, so you have to like provide this consent”

said at 03:05

“They basically can't determine, uh, you know, which AI agents you can actually use, right?”

said at 04:09
03Leftover access tokens create a standing-access security gap
Slide at 06:20 · click any slide to enlarge

Leftover access tokens create a standing-access security gap

  • When an employee's SSO access is revoked or a device is compromised, the speaker notes that OAuth access and refresh tokens issued to MCP servers can remain valid independently of the IDP, since most companies don't use SCIM for full revocation -- meaning access can persist for days, weeks, or even months after it should have been cut off.

“you still have these access tokens, these refresh tokens even in most cases that give you standing access to these services. That means you might have access for, uh, days or weeks or even months.”

said at 05:43
04Cross-app access (XAA): the IDP brokers trust via short-lived ID Jag tokens
Slide at 06:30 · click any slide to enlarge · 7 more from this section below

Cross-app access (XAA): the IDP brokers trust via short-lived ID Jag tokens

  • The proposed fix, cross-app access (XAA), has the identity provider act as a trust broker between an MCP client and an MCP server that both already trust it via SSO.
  • The client exchanges a refresh token for an ID Jag (identity JWT authorization grant) token from the IDP, then exchanges that for a normal OAuth access token from the MCP server's authorization server -- and because that access token is typically short-lived (around 5 minutes), the client must keep re-requesting it as long as the SSO session stays active, which cuts off access automatically once the session is locked.

“what's the solution to this? The solution is cross-app access, otherwise known as XAA.”

said at 06:14

“Stands for identity JWT authorization grant. It's very big mouthful. Effectively, it just means a token issued by an IDP that can be used across services to uh manage access.”

said at 10:26

“that token will expire after 5 minutes, but you don't need the human to do anything. You can basically rerun this ID Jag flow plus the exchange and get a new access token as needed.”

said at 12:30
05Current gaps: no authorization scoping, and Microsoft Entra not yet supported
Slide at 16:50 · click any slide to enlarge · 8 more from this section below

Current gaps: no authorization scoping, and Microsoft Entra not yet supported

  • In Q&A, the speaker confirms XAA by default solves authentication only, not authorization/scoping (a user still gets whatever permissions they already have in the target app), and that Microsoft has not yet added XAA support inside Entra, though WorkOS is working with them on it.

“Question is this solves authentication, not authorization. Does this do anything to to help with that? Um by default, no.”

said at 17:05

“Microsoft doesn't hasn't yet added XAA support inside of Intra. Um that's something we're working with them on.”

said at 19:10

Commentary (ours)

The authentication-not-authorization caveat matters for any team assuming XAA closes the least-privilege gap -- it currently just removes the manual consent click, not the scope of what the agent can do once connected (ours).
