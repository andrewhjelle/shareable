Walks through a working architecture for a two-stage research-then-write agent system: when to use a single agent with tools instead of multi-agent handoffs, how MCP skills use progressive disclosure to manage context budget, why the eva...

If you only read one thing

  • The workshop frames the workflow-vs-agent decision around whether a system needs to take autonomous action and react to its environment, illustrated by a client case where a single agent with tools was chosen over a multi-agent system specifically to avoid handoff errors between agents (c2, c3).
  • Context quality degrades well before a model's nominal context window limit -- noticeable degradation is cited starting around 200,000 tokens even on million-token-context models -- and their MCP-based skills rely on progressive disclosure, loading only a name and description until a skill is actually invoked (c1, c4).
  • In their LinkedIn-writing pipeline, the reviewer runs in a separate context window from the writer to avoid self-bias, synthetic eval data is only ever generated as input (never as the output being judged), and the LLM judge is calibrated by aligning it against a human-labeled dev/test split before trusting its scores (c6, c7, c8).

This traces three separate design choices from the workshop (agent-vs-workflow, context budgeting via skills, and the writer/reviewer/judge eval loop) laid side by side as one architecture, though the talk never presents them as a single connected system (ours).

01When workflow beats agent

When workflow beats agent

  • The speakers define an agent, using an Anthropic framing they favor, as a system that needs to take actions and react to what happens in its environment -- anything short of that is better built as a simpler, more controllable workflow.
  • In a client project for a CRM marketing chatbot, the client initially wanted a multi-agent system, but the team built a single agent using tools instead, arguing that splitting the decision across separate agents would have introduced handoff errors and reliability problems.

“It's just when it needs to take actions and more importantly when it can react to what happens in the environment”

said at 09:56

“splitting decisions across different agents as the client wanted would have been would have caused a lot of issues whether it is information or just handoff errors with tool calls”

said at 15:08
02Context rot and skill-based delegation

Context rot and skill-based delegation

  • The speakers describe context quality degrading well before a model's advertised context window limit, citing a noticeable worsening starting around 200,000 tokens even for models rated for a million tokens, which they attribute partly to how long-context training data is constructed.
  • Their system manages this budget by exposing workflow instructions as MCP-based agent skills rather than always-loaded prompts: a skill's name and description are the only thing loaded until a matching query invokes it, after which the full content loads and is then discarded.

“this happens much before the actual context window limit of like 1 million tokens, for example. It worsens quite fast after like 200,000”

said at 17:12

“when Claude just like shows you the skill, um it doesn't load the entire information. It is only uh load the name and the description of the skill.”

said at 61:03
03Curating few-shot examples and separating writer from reviewer

Curating few-shot examples and separating writer from reviewer

  • For the LinkedIn-writing workflow, the team deliberately kept few-shot examples few and varied by topic, length, and structure, since every example in the system prompt adds cost, latency, and potential context degradation.
  • Their evaluator-optimizer loop uses two separate LLM calls with two distinct context windows -- one for the writer, one for the reviewer -- specifically because LLMs tend to be biased toward favoring content they already wrote themselves.

“the key idea is to use high-quality and representative uh few-shot examples and make them as varied as possible in things such as topic, length, structure”

said at 79:29

“We have the the writer and the reviewer, where basically the writer first writes the draft, and the reviewer with a completely different context window takes the draft and and reviews it”

said at 81:37
04Rules for building and calibrating an eval judge

Rules for building and calibrating an eval judge

  • When generating synthetic data for the eval dataset, the speakers stress never asking an LLM to directly generate the output being judged -- only the input -- since the whole point is to evaluate the real system's actual output.
  • The LLM judge itself is treated as a binary classifier that must be calibrated against a human-labeled dev/test split, with the explicit goal of aligning the judge's pass/fail decisions with a human domain expert's judgment before trusting it on new data.

“when you want to generate like synthetic data of some sort, never ask the LLM to directly generate the output. Always ask it to help you generate the input, but never the output.”

said at 100:24

“our final goal is to align the element judge with the domain expert. And how we will do that? We will do that by testing it against the dev test data set splits.”

said at 104:09
05Result: scoring below a human baseline for AI slop

Result: scoring below a human baseline for AI slop

  • Running a generated LinkedIn post through a public AI-slop detector, the speakers reported the output scored as less 'sloppy' than a human-written baseline post on the same tool, offered as informal evidence that their guideline-plus-profile-plus-few-shot approach avoids the generic AI-writing patterns they set out to eliminate.

“And hit analyze and yay, no not not slob. And this is actually lower and less sloppy than a human.”

said at 74:48

Commentary (ours)

(ours) The slop-detector demo (c9) is a single anecdotal run against one third-party tool, not a systematic eval, and the speakers' own AI-evals section argues exactly this kind of one-off 'vibe check' doesn't scale -- worth noting the gap between their stated methodology and this particular demo.
