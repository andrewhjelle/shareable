From Blind Spots to Merged PRs: Continuous Agentic Performance Optimization

SpeakerMay Walter · Hud Watchyoutu.be/JJGbw4ggaFs
Agentic engineeringCoding agentsInfra & serving

If you only read one thing

  • Google's 2026 DORA metrics show AI adoption boosts individual effectiveness but not team throughput, and software delivery instability rises.
  • An agentic workflow that runs weekly against production data, scores opportunities by ROI, applies a fix, and reruns tests to verify impact before a human reviews it.
  • Getting to a trustworthy autonomous pipeline required crossing an 80-90% confidence threshold, categorically different from using an agent interactively in an IDE.
01AI makes individuals faster but not teams, and breaks things more

Walter cites Google's 2026 DORA metrics showing the biggest measured impact of AI adoption is individual effectiveness, while team throughput stays roughly flat and software delivery instability increases. She frames the talk's project as an attempt to also use AI to close the resulting stability gap, not just to build faster.

“the biggest impact of AI adoption on engineering is individual effectiveness”

02The 'leaky bucket' problem: investigation time is a black box

She describes a recurring pattern where performance issues are ignored until they become a crisis, largely because the investigation phase to find and scope an issue is unpredictable in duration and hard to prioritize. The team built a weekly automated agentic workflow, running against real production context, to score and flag high-ROI performance opportunities without requiring someone to stop and investigate manually.

“that mostly happens because the research phase is a black box. It could take an hour or weeks and we have to pay that debt”

▶ watch at 03:36
03Three failure modes the workflow had to guard against

Walter names three recurring problems with agent-proposed fixes: 'plausible unverified' fixes that sound right but don't actually work when tested, difficulty with complex ClickHouse queries, and 'lazy fixes' like catching an exception instead of addressing its root cause. Solving these required grounding the agent in actual production data rather than letting it theorize.

“the agent would suggest a fix. It sounds right. It would look fairly real and then after we verified it it it just didn't work”

▶ watch at 08:47
04Closing the loop: fix, rerun tests, verify impact, then hand to a human

The workflow's key step is that the agent applies a fix, reruns tests, and confirms the measured impact on the affected flow before a human reviewer ever sees it, so the human is reviewing a verified result rather than a proposal. Walter says this shifted the team from opening dozens of unreviewed PRs (which no one wanted) to a prioritized, human-readable report surfacing only the highest-ROI, lowest-risk opportunities.

“the agent actually fixes it reruns the tests and sees the impact that it had on that specific flow that was optimized”

▶ watch at 07:44

“no one wants to wake up for, you know, a rain of 80 pull requests, as small as small as they can be. That's just not how people operate.”

▶ watch at 16:01
05Function-level production context, not just service metrics

She describes building 'prod-to-code' context that connects runtime data to the function and file level where coding agents actually reason, rather than leaving it at the service/endpoint level metrics like P90 latency, CPU, and memory. This was paired with a query language over that data plus a set of reusable 'skills' for specific investigation types (500 errors, memory spikes) to reduce variance in results.

“our context is running on a function level, and it is also connected to the endpoint or event consumer or cron job that ended up starting this task”

▶ watch at 11:52
06Autonomous automation requires a much higher trust bar than interactive coding

Walter closes by distinguishing agentic engineering used interactively, where a human is present to steer and catch mistakes, from an autonomous automation that runs unsupervised. She says reaching the point where the team trusted the automation's output required crossing roughly 80-90% confidence, which she calls dramatically different from using an agent directly as an engineer.

“getting to that agentic engineering automation level requires crossing towards the 80-90% trust, and it's something that is dramatically different than using an agent directly as an engineer”
