MCP Tasks (async): Why Aren't Any Agents Supporting Them?

SpeakerCornelia Davis · Temporal Watchyoutu.be/s4r6nk5WsZw
MCP & protocolsAgentic engineeringInfra & serving

If you only read one thing

  • The MCP tasks spec was marked experimental in November and is genuinely complex to implement durably, which is the real reason no client supports it yet (c1, c2).
  • V1's task-list endpoint has no filter, so it breaks down once an agent has a million tasks running (c4).
  • V2 (coming July) drops task list and the long-running session in favor of a stateless client-update endpoint, but shifts the durability burden onto the client, which must persist task IDs itself; scaling to millions of tasks is still unsolved (c6, c7, c8, c9).
01Why no client has implemented MCP tasks yet

Davis frames the talk around a simple answer: the MCP tasks specification that shipped in November was marked experimental, and the spec itself requires that once a task is launched it must be durable across client crashes, server crashes, and disconnected humans. Implementing that durability requirement is what makes client-side support hard enough that, as of the talk, she says no one has built it.

02Demo: a purchase-order task survives the backend being down

Davis demos a purchase-order workflow where invoice processing runs as a long-running MCP task with a human-approval step, implemented on top of Temporal. The task's lifecycle moves through working, input-required, and back to working before completing or failing. In the demo, a purchase order submitted before the backend servers were even started still went through once they came up, illustrating the durability requirement in practice.

“It has working. It can go into an input required. From input required, it can go back to working, and then eventually it'll complete or be canceled or fail.”

“even though my servers weren't running, that submission did go through”

03V1's task list doesn't scale

In tasks V1, a client that loses its connection can call task list to recover what tasks exist on the server. Davis says that works with a handful of tasks but has no filter, so a client would have to page through a million tasks at the back end to find the one it cares about once an agent fleet is running at scale.

“what happens if you've got a whole slew of agents out there and you've got a million tasks at the back end”

▶ watch at 13:29
04V2 goes stateless but pushes durability onto the client

Citing a May blog post from the Agoric AI Foundation (where MCP now lives), Davis says V2 makes the protocol's core stateless and moves tasks into an extension. Task list is removed and the awkward long-running session for input-required is replaced with a client-initiated update call, similar to a Temporal signal. Because list is gone, the spec now says clients should persist task IDs themselves, though it stops short of a hard 'must' -- and without persisting the ID, a client has no way to recover the task.

“one of the things that made me jump up and celebrate a little bit is that the protocol is going stateless”

▶ watch at 16:01

“Task list has gone away. Good. Wasn't particularly useful anyway, especially at large scale.”

▶ watch at 17:04

“clients should persist task IDs, but it also points out that if you don't persist task IDs, there is no way to get it back”

▶ watch at 18:37
05What's still unsolved

Davis says V2 is a real improvement but still doesn't scale to millions of tasks, since every client would still be polling each task individually. She's exploring the spec's notifications protocol, which would let clients subscribe to a single endpoint for change notifications instead, and plans a reference implementation in FastMCP within a month or two.

“even though this is better, it still doesn't scale to the millions”

▶ watch at 22:12

Commentary (ours)

The live demo (server killed mid-task, still resolves) is a real durability proof, but it's Davis's own client-side implementation on top of Temporal, not a reference implementation the wider ecosystem is using -- so the reliability shown here doesn't yet generalize to other MCP clients until someone ships equivalent client-side support in FastMCP or elsewhere (ours).
