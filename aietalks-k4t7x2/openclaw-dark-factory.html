Dark Factory: OpenClaw Ships Faster Than You Can Read the Diff

SpeakerVincent Koc · OpenClaw Watchyoutu.be/pmoDeA3RBZY
Agentic engineeringCoding agentsOpen source

If you only read one thing

  • OpenClaw peaked at roughly 800 commits/day project-wide across 10-15 core maintainers, with the speaker personally hitting close to 3,000 commits in a day (c1, c2).
  • A 2,700-commit overnight 'great refactor' touching 82% of the codebase was only recoverable because AI-generated unit tests, even though over-fit, gave a reliable green/red signal once everything was ripped apart and reassembled (c3).
  • Running many parallel agent sessions as 'swim lanes' shifts the real bottleneck from tokens to the operator's own compute and attention, and judging whether a session is on track becomes an intuitive, almost tone-of-voice skill (c4, c5, c7).
01Commit velocity at OpenClaw

OpenClaw's maintainers ship at what the speaker frames as factory-line velocity: roughly 800 commits a day project-wide across about 10-15 core maintainers who all have day jobs elsewhere, and on one specific day the speaker personally hit close to 3,000 commits.

“OpenClaw where we're pushing at the peak, we were doing 800 commits a day”

02The great refactor

A late-night decision to restructure the codebase into a plugin architecture (so, for example, a model provider like OpenAI or Anthropic could own its own isolated piece of code) resulted in roughly 2,700 commits and close to a million lines of code changed, touching 82% of the core codebase, before plugins launched.

“2,700 commits later, uh close to a million lines of code change, uh touching 82% of the core code base, plugins were launched”

▶ watch at 08:17
03Running multiple agents as swim lanes

The speaker manages agent work as parallel 'swim lanes' (five to twenty at a time), treating himself as a factory manager rather than a line worker: some lanes run low-supervision maintenance work (fixing tests) while others require active back-and-forth on specific features or bugs. He states that tokens are no longer the constraint; the bottleneck is his own available compute and attention to supervise all the running sessions, and heavy use of git worktrees (up to 70-80 active at once) became its own operational headache.

“imagine you're a factory manager and you have a production line below.”

▶ watch at 09:49

“tokens are no longer the problem. Um depends who you ask. What really ends up becoming the problem is just raw compute and my brain space”

▶ watch at 10:50

“I end up with like something close like 70 or 80 active Git work trees in any given day on my machine and that's kind of hell”

▶ watch at 11:21
04Judging agent output by intuition

The speaker describes developing an intuitive sense, built from a large volume of prior 'token maxing,' for when a swim lane has gone off track -- not from what the agent is doing but from how it explains itself, comparing it to noticing when a person starts to bullshit.

“there's times where I'm looking at the swim lane. I'm like, This sounds off. It doesn't sound off because of what it's doing. It sounds off because of how it's explaining itself to me”

▶ watch at 12:24
05Managing PR volume and what's next

The project has accumulated a very large backlog of PRs (the speaker cites roughly 6,000), and every new maintainer tends to independently attempt a clustering/deduplication approach; the volume of duplicate PRs on one issue is itself treated as a signal that the underlying problem is significant. The speaker's closing framing is that 2025 was about maximizing token usage, while 2026 is about token efficiency and not wasting them.

“there's this kind of running joke that every maintainer that joins the project decides to try and tackle like, Oh my god, we have 6,000 PRs. How are we going to solve it?”

▶ watch at 14:26

“2025 was about token maxing. 2026 is about not wasting them. It's about token efficiency.”

▶ watch at 16:00

Commentary (ours)

The claim that tokens stopped being the bottleneck and operator attention/compute became the limiting factor is a useful counter-signal to the industry's continued focus on token cost -- if this pattern generalizes, the next wave of tooling investment may need to target session-supervision UX rather than further token-cost reduction (ours).
