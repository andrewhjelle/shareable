Why complexity explodes past one agent

A production war story: stale cache, wrong risk ratings

  • In a five-agent credit-decisioning system, a credit-score agent wrote a score of 750 to the database while a risk-assessment agent read a cached value of 680 for the same customer 500 milliseconds later, because the cache wasn't invalidated after the write.
  • This caused 20% of decisions to carry incorrect risk ratings before the team traced it back to the caching layer over two days.

“In 3 days' time, we started seeing weird approvals. Uh 20% of the decisions had incorrect risk ratings.”

“Credit score agent calculated a score of 750 and wrote to the database. The risk assessment agent, on the other hand, read from the database 500 milliseconds later and got a score of 680 for the same customer.”

03Choreography vs. orchestration as a decision, not a default
Slide at 06:10 · click any slide to enlarge · 8 more from this section below

Choreography vs. orchestration as a decision, not a default

  • Choreography (agents coordinate through published events, no central controller) scales well and is loosely coupled but is described as a debugging nightmare without strong observability.
  • Orchestration (a central coordinator calls each agent directly, manages state, retries, and logging, and agents never call each other) trades autonomy for traceability.
  • The speaker's rule of thumb: simple workflow with high autonomy needs favors choreography; complex workflow with low autonomy tolerance favors orchestration.

“However, the nightmare of choreography is debugging. When something fails, you're playing detective with no real clue.”

said at 06:50

“Agents are dumb. They just take the input, they do the work, they return the output. The orchestrator does all the smart coordination.”

said at 08:58

“Simple workflow, high autonomy, you go with choreography. You need complex workflow with low autonomy tolerance, you go with orchestration.”

said at 10:01
04State: replace shared mutable writes with immutable, versioned handoffs
Slide at 15:10 · click any slide to enlarge · 2 more from this section below

State: replace shared mutable writes with immutable, versioned handoffs

  • Instead of multiple agents writing to the same record (which produces lost updates and stale reads), each agent hands off an immutable, versioned state object that is appended, not updated, letting failures be traced by walking back through prior versions.
  • Data contracts between agents (e.g., an analysis agent rejecting a handoff if a confidence score is below 0.7) catch bad data at the handoff boundary instead of several agents downstream.

“It prevents race conditions on shared state. No stale reads. It provides a clear lineage.”

said at 14:45

“If confidence is below 0.7, it will reject the handoff.”

said at 15:47
05Failure recovery: circuit breakers and saga-style compensation
Slide at 16:40 · click any slide to enlarge · 8 more from this section below

Failure recovery: circuit breakers and saga-style compensation

  • A circuit breaker wraps each inter-agent call and opens after repeated failures (the example given is five in a row), so the system fails fast instead of retrying into a timeout each time, then tests recovery with a single request after a cooldown.
  • Separately, a saga/compensation pattern gives every agent both an execute and a compensate method, so the orchestrator can walk backward through completed steps and undo them if a later agent fails.

“If agent B fails repeatedly, say five times in a row, the circuit breaker opens.”

said at 16:49

“Every agent has two methods, execute and compensate. Execute does the work. Compensate rolls it back, undoes it.”

said at 18:54
