From Chaos to Choreography: Multi-Agent Orchestration Patterns That Actually Work

SpeakerSandipan Bhaumik · Databricks Watchyoutu.be/2czYyrTzILg
Agentic engineeringInfra & servingMemory

If you only read one thing

  • Going from one agent to five agents doesn't add linear complexity: the speaker states it makes the system "25 times more complex" because coordination connections grow combinatorially (c1).
  • A real credit-decisioning deployment hit a stale-cache race condition, one agent wrote a 750 credit score while another read a cached 680 for the same customer 500ms later, causing 20% of decisions to carry incorrect risk ratings (c2, c3).

01Why complexity explodes past one agent

The speaker argues that adding agents is not like adding features: coordination complexity grows combinatorially rather than linearly, since each additional agent adds potential connections, race conditions, and failure points between agents.

“it doesn't get just five times harder. It gets 25 times more complex. Coordination complexity grows exponentially.”

02A production war story: stale cache, wrong risk ratings

In a five-agent credit-decisioning system, a credit-score agent wrote a score of 750 to the database while a risk-assessment agent read a cached value of 680 for the same customer 500 milliseconds later, because the cache wasn't invalidated after the write. This caused 20% of decisions to carry incorrect risk ratings before the team traced it back to the caching layer over two days.

“In 3 days' time, we started seeing weird approvals. Uh 20% of the decisions had incorrect risk ratings.”

03Choreography vs. orchestration as a decision, not a default

Choreography (agents coordinate through published events, no central controller) scales well and is loosely coupled but is described as a debugging nightmare without strong observability. Orchestration (a central coordinator calls each agent directly, manages state, retries, and logging, and agents never call each other) trades autonomy for traceability. The speaker's rule of thumb: simple workflow with high autonomy needs favors choreography; complex workflow with low autonomy tolerance favors orchestration.

“However, the nightmare of choreography is debugging. When something fails, you're playing detective with no real clue.”

“Agents are dumb. They just take the input, they do the work, they return the output. The orchestrator does all the smart coordination.”

“Simple workflow, high autonomy, you go with choreography. You need complex workflow with low autonomy tolerance, you go with orchestration.”

04State: replace shared mutable writes with immutable, versioned handoffs

Instead of multiple agents writing to the same record (which produces lost updates and stale reads), each agent hands off an immutable, versioned state object that is appended, not updated, letting failures be traced by walking back through prior versions. Data contracts between agents (e.g., an analysis agent rejecting a handoff if a confidence score is below 0.7) catch bad data at the handoff boundary instead of several agents downstream.

“It prevents race conditions on shared state. No stale reads. It provides a clear lineage.”

▶ watch at 14:45

“If confidence is below 0.7, it will reject the handoff.”

▶ watch at 15:47
05Failure recovery: circuit breakers and saga-style compensation

A circuit breaker wraps each inter-agent call and opens after repeated failures (the example given is five in a row), so the system fails fast instead of retrying into a timeout each time, then tests recovery with a single request after a cooldown. Separately, a saga/compensation pattern gives every agent both an execute and a compensate method, so the orchestrator can walk backward through completed steps and undo them if a later agent fails.

“If agent B fails repeatedly, say five times in a row, the circuit breaker opens.”

▶ watch at 16:49

“Every agent has two methods, execute and compensate. Execute does the work. Compensate rolls it back, undoes it.”
