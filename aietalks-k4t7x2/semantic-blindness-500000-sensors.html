Semantic Blindness: 500,000 Sensors Confused an LLM

SpeakerRaahul Singh & Vanč Levstik · Phaidra Watchyoutu.be/EUsPvBeIx70
Vertical AIContext engineeringEvals & benchmarks

If you only read one thing

  • Naive sharded LLM search over equipment names produced horrible recall and hallucinated phantom equipment; the old approach's correctness dropped from 80% at 64 GPUs to about 30% at 460,000 GPUs.
  • The fix uses an LLM only to plan (produce a structured scope + filter) while a deterministic tree-indexed resolver does exact set operations, restoring 100% correctness across scales and real production systems with zero failures in 66 test cases.
  • This cut token cost from 116 million tokens for a single validation pass down to 390,000, and made per-query cost flat (about 9,000 tokens) whether the system has 64 GPUs or 460,000.
01The problem: near-identical names at massive scale

Phaidra builds agents that let data center operators query their infrastructure in natural language. At gigawatt scale, a facility can have 400,000+ GPUs plus power meters, chillers, and other equipment, and naming conventions vary by customer from simple to cryptic (e.g., "CH3 something something six"). This exceeds LLM context windows and defeats naive approaches once systems move past demo scale.

“at 1 gigawatt scale factories you will see 400,000 plus GPUs and to support those GPUs you have power meters, you have chillers, you have other equipments”

▶ watch at 01:33
02Both naive LLM search and vector RAG fail at scale

Semantic/vector search fails because equipment names are often nearly identical strings differing by one character, giving poor recall. Pure LLM approaches also hit an internal frequency penalty that causes the model to cut off output when asked to list many similar names in a row (e.g., listing 100 GPUs). Sharding equipment across parallel LLM calls doesn't fix this either -- it produces horrible recall and hallucinated phantom equipment that doesn't exist while silently dropping equipment that does.

“the problem is often times the names are so similar that semantic search just fails.”

▶ watch at 02:05

“If you keep on outputting very similar names over and over again, or very similar tokens, uh more accurately, over and over again, there are internal penalties in the LLM which just shut off their output.”

▶ watch at 02:36
03The fix: LLM plans, deterministic code resolves

Because data center equipment forms a shallow, wide hierarchy (data center to hall to aisle to row to rack to device), Phaidra's system uses the LLM only to convert a vague query into a structured plan (scope + filter), then a deterministic resolver runs exact set operations over pre-indexed subtrees to produce the final result set -- a two-to-three step process instead of an open-ended agentic loop.

“the lesson for new built AI native systems runs a little bit the other way”

▶ watch at 13:28

“The simple heuristic that usually works, if you can write down the structure or the rules, it's a 1.0 job”

▶ watch at 14:31
04Measured results: accuracy restored, cost collapses

Head-to-head testing (same model, same data, three runs per case) showed the old sharded approach degraded from 80% correctness at 64 GPUs to about 30% at 460,000 GPUs, while the new approach held 100% correctness across all scales and across 66 real-world cases on six production systems with zero failures. Token cost for a full validation pass at 1GW scale dropped from 116 million tokens to 390,000, and per-query cost stayed flat at roughly 9,000 tokens regardless of system size.

“we got 80% correctness at 64 GPUs, and that dropped to about 30% when the GPU grew to 400 460,000”

“On the other hand, the our new approach has maintained correctness with 100% accuracy across all of those um tests that we give it.”

“the old approach burned 116 million tokens for just a single validation pass while still having a lot of errors”

“the cost of the query was 9,000 tokens a query where the system was 64 GPUs or 460,000”

Commentary (ours)

The team's framing of an inversion on Karpathy's software 1.0/3.0 trend -- new AI-native systems starting almost pure 3.0 (everything in the prompt) and maturing back toward 1.0 for whatever proves reproducible -- is a useful heuristic for other teams building agents over structured data: use the LLM's context-window flexibility to find what's worth hardening into code, then harden it (ours).
