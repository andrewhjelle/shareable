If you only read one thing

  • Human conversational turn-taking happens around 300ms; agents taking over 500ms are noticeable and over 1-2 seconds cause people to hang up, which sets the latency budget for the whole pipeline (c1, c2).
  • Component targets: STT state-of-the-art is around 6% word error rate with Together's models hitting P90 ~100ms transcript completion; LLM should target ~200-300ms time-to-first-token, which caps usable model size at roughly 8-30B parameters (c3, c4, c5).

Why voice, and why it's hard: the latency budget

  • The speaker frames voice as a new interface (not just automating hold-queue calls) since humans learn to talk before they read.
  • Human turn-taking cues happen around 300 milliseconds; an agent taking over 500ms becomes noticeable, and users hang up if it takes one to two seconds, which sets the real-time constraint the whole system must meet.

“when humans are having a conversation, we respond to each other's cues in something like 300 milliseconds.”

said at 02:35

“it's taking more than 500 milliseconds to respond, you'll start to notice. If it takes a second, if it takes 2 seconds, people will just hang up.”

Speech-to-text: word error rate and streaming-native architectures

  • State-of-the-art STT models run around 6% word error rate on open benchmarks, and errors on names or drug names can't be corrected downstream since the LLM and TTS will carry the mistake forward.
  • Together's own models hit a P90 of about 100ms for completing a transcript after an utterance ends.
  • He also notes an architectural shift from batch models like Whisper (trained on 30-second clips, requiring chunking workarounds) toward streaming-native encoders (citing a recent Nvidia model) that use short look-ahead windows and cached activations.

“state-of-the-art models are typically in the 6% word error rate on open benchmarks.”

said at 05:10

“for some of the models that we run on Together, we we get sort of consistently P90 of like 100 milliseconds”

LLM sizing is constrained by the latency budget

  • The key LLM metric is time-to-first-token, targeted around 200-300ms so tokens can start feeding the TTS model immediately; that budget effectively caps usable model size to roughly the 8-30 billion parameter range, since going bigger burns the latency budget and going smaller hurts intelligence and tool-calling quality.

“a good size model typically ends up being in this 8 to 30 billion range.”

said at 08:12
04Co-location cuts network latency substantially
Slide at 12:50 · click any slide to enlarge · 1 more from this section below

Co-location cuts network latency substantially

  • Beyond engine latency, network latency between geographically separated models matters -- e.g., roughly 75ms round-trip for US-to-Europe.
  • Co-locating the STT, LLM, TTS models and the agent orchestrator in the same data center can drop that to about 5ms, yielding a 30% latency reduction on an already latency-optimized pipeline.

“that drop from 75 milliseconds to five basically gets you a 30% reduction in already a fairly optimized voice agent setup”

said at 13:20
05Speech-to-speech models: promising but not yet production-ready for tool calling
Slide at 14:20 · click any slide to enlarge · 8 more from this section below

Speech-to-speech models: promising but not yet production-ready for tool calling

  • An alternative to the cascading STT-LLM-TTS pipeline is a single speech-to-speech model (e.g.
  • OpenAI's real-time API, Nvidia's Voice Chat), which preserves tone/emotion information lost in text conversion and enables full-duplex, human-like backchanneling.
  • The main reason these aren't yet widely used in production is that they still struggle with instruction following and tool calling, pushing teams back toward pipeline architectures; teams also fine-tune smaller LLMs on use-case-specific data to raise tool-calling quality while staying within the latency-driven size budget, and some adopt a 'thinker-talker' pattern where a small LLM handles conversation and hands off via a single tool call to a larger, more capable model.

“The reason why most of these models are not used in production too much is because they have they still have trouble with instruction following and tool calling.”

said at 14:55

“we do see customers fine-tune smaller LLMs with their kind of use case specific data so that they can get tool calling quality to go up while remaining a model that is relatively small.”

said at 18:00

“this thinker talker pattern where you might have a small LLM that is handling all of the conversation”

said at 21:35

Commentary (ours)

The 8-30B parameter ceiling driven by latency budget, not capability, is a useful constraint to flag whenever a vendor pitches a frontier-scale model for a real-time voice product -- the latency math may rule it out before quality does (ours).
