patternAgentic engineeringContext engineering

Gives a concrete checklist (trigger, structure, steering, pruning) for auditing whether a Claude/agent skill is actually working, rather than just accumulating skill files

If you only read one thing

  • Decide per-skill whether it's user-invoked or model-invoked: model-invoked skills add context load (a description in every request) but are more flexible; user-invoked skills add cognitive load on the person but remove invocation unpredictability.
  • Keep skill.md small by splitting steps from reference material and hiding branch-specific reference behind external context-pointer files so only the relevant branch loads into context.
  • Use 'leading words' (short well-known terms like 'vertical slice') repeated in the skill text to steer agent behavior, and split multi-step skills like plan mode into separate skills to force more legwork per step.

01User-invoked vs model-invoked skills is the first design decision
Slide at 04:50 · click any slide to enlarge

User-invoked vs model-invoked skills is the first design decision

  • Every skill can be invoked manually by the user, but a skill can also carry a description that lives in the agent's context so the model can decide to invoke it itself.
  • The speaker calls this description a context pointer, and notes it can be hidden from the agent via a 'disable model invocation' flag, making the skill user-invoked only.

“the description of the skill always ends up in the agent's context, and the agent can look in that and go, "Okay, based on that description, I'm going to invoke the skill”

said at 03:14

“this then is tip number one. Decide if your skill is user invoked or model invoked”

said at 04:39
02Model-invoked skills trade context load for flexibility
Slide at 05:00 · click any slide to enlarge · 1 more from this section below

Model-invoked skills trade context load for flexibility

  • Every model-invoked skill added to an agent's environment adds a description that costs tokens on every request and increases what the speaker calls context load; a hundred model-invoked skills means a hundred descriptions in context.
  • User-invoked skills instead raise cognitive load on the person, who must remember which skill to call.
  • His own skills repo favors user-invoked to avoid the unpredictability of a model choosing not to follow a context pointer, unlike the Superpowers skill set, which is primarily model-invoked.

“every time you add a model invoked skill into your agent's environment, it increases what I'm going to call the context load on that agent”

said at 04:39

“Superpowers is primarily model invoked skills. It gives the agent superpowers. Whereas my skills, I much prefer to be in full control”

said at 05:41
03Structure: split steps and reference, hide branch-only material
Slide at 05:00 · click any slide to enlarge

Structure: split steps and reference, hide branch-only material

  • He describes skills as composed of two units: steps (the procedure) and reference (supporting material).
  • The core technique for keeping skill.md small is identifying which reference material is only needed on one branch of the skill's use and moving it behind an external context pointer to a separate markdown file, rather than including it in the main file every time.

“if you feel like your skill is going to be used in lots of different ways, then take the reference material that's relevant for those branches and hide them behind context pointers”

said at 11:24
04Steering agents with leading words and hidden future steps
Slide at 05:00 · click any slide to enlarge

Steering agents with leading words and hidden future steps

  • To fix agents not doing what's specified, he recommends packing meaning into short, well-known terms ('leading words' like 'vertical slice') that the agent repeats in its reasoning traces, which then changes its behavior; you can verify the technique worked by checking whether the term shows up in the reasoning trace.
  • Separately, when an agent under-invests effort in an early step (e.g., asking clarifying questions before eagerly jumping to a plan), splitting that step into its own skill so the agent doesn't see the next step increases legwork on the current one.

“you put the leading word in the skill itself in the text, and then the agent will repeat the leading word back to itself as part of its operations, as part of its thinking tokens”

said at 12:28

“this is a really cool technique for increasing legwork on the step that you're on by hiding the future goal, hiding the future steps”

said at 16:06
05Pruning: duplication, sediment, and no-ops
Slide at 05:00 · click any slide to enlarge

Pruning: duplication, sediment, and no-ops

  • Final failure modes to prune are duplicated material (no single source of truth), 'sediment' from multiple contributors adding to a shared file without deleting stale content, and 'no-ops' -- text that appears to instruct the agent but doesn't actually change behavior, tested by deleting a paragraph and checking if the output changes.

“make sure that you don't repeat that in several places or like cover multiple steps in multiple places. Just make sure each part has a single source of truth”

said at 17:07

“What would happen if you just deleted that paragraph? Well, the agent would probably still write a decent like long commit message”

said at 18:40

Commentary (ours)

The leading-words technique is essentially the same mechanism as few-shot/keyword priming in prompt engineering, just applied at the skill-authoring layer instead of the per-request prompt -- worth testing directly against Anthropic's own skill-authoring guidance for overlap (ours).
