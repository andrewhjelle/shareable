CI/CD Is Dead, Agents Need Continuous Compute and Computers

SpeakerHugo Santos and Madison Faulkner · Namespace / NEA Watchyoutu.be/VktrqzQgytY · 18 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. Quotes are verbatim from the talk transcript with the time they were said.
patternAgentic engineeringCoding agentsInfra & serving

Useful for deciding whether to keep speeding up existing CI/CD pipelines or redesign the workflow around agent harnesses, stateful validation loops, and a pre-merge queue as agent-generated PR volume outpaces human review capacity

If you only read one thing

  • Agent-generated code has spiked GitHub commit volume; the speakers' own team already sees PR volume at 4x historical levels, which they call impossible for a human reviewer to keep up with.
  • The proposed replacement has no PRs: work starts from an intent/spec, runs through an agent harness (Cloud Code, Amp, Cursor, or Factory) with fast internal validation, then queues in a pre-merge ledger for external validation.
  • External validation is shifting from human reviewers to other agents (e.g. a security-focused LLM), which requires a stateful environment so the validation loop doesn't restart from scratch each time.

01CI/CD strain under agent-generated code volume

CI/CD strain under agent-generated code volume

  • The speakers argue traditional CI/CD (PR review, GitHub Actions build/test/deploy, iterate on failures) was built for a human cadence of one or two changes a week per developer.
  • At agent scale, GitHub commit activity has 'gotten absolutely crazy,' and their own team's PR volume is now four times what it was, which they say makes it impossible for a human reviewer to look at every single PR.

02A no-PR architecture: intent, harness, pre-merge ledger

A no-PR architecture: intent, harness, pre-merge ledger

  • The proposed replacement starts from a written intent/spec (in a ticket or Slack message) rather than a diff, and feeds it into an agent harness -- named examples include Cloud Code, Amp, Cursor, and Factory -- which checks out a known commit, implements the plan, and runs internal validation (build/test) against the repository's own assets before asking a human to continue or stop.

03Validation shifts from human review to agent judges

Validation shifts from human review to agent judges

  • The speakers describe external validation moving from human reviewers to other agents -- for example a security-focused LLM or an API-conformance LLM -- providing feedback that the main harness incorporates back into the code.
  • Because this validation runs repeatedly and quickly, they argue it needs to run in a stateful environment so it isn't restarting from scratch each time, and cite Mitchell Hashimoto's public writing on what he'd change about GitHub as corroborating outside opinion.

04What's left of CI in this model

What's left of CI in this model

  • The speakers say CI doesn't disappear but shifts: validating that code works is no longer a separate phase but part of every iteration of the loop, and coordination/governance move into the agent harness rather than a standalone CI system.
  • They also predict agents may work on multiple commit candidates in parallel for the same plan once the loop is fast enough, since the ledger's tip keeps moving.

“the agents may actually be working on multiple commits at the same time to address the same plan.”

“CI still matters, but it's just shifted because the principles of uh well, for example, does does the code actually work? No longer is a separate phase, but it's just part of this loop.”

Commentary (ours)

The framing treats the PR as a human-review artifact that stops making sense once code generation is cheap and continuous -- the harder open question the talk doesn't fully resolve is how a human stays meaningfully 'in the loop' for external approval once review volume is already 4x and headed higher (ours).
