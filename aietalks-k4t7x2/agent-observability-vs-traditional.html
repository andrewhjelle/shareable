Lays out concrete technical reasons agent traces need different infrastructure than tools like Grafana/Datadog: gigabyte-scale traces, 20MB individual spans, and the need for full-text indexing (Tantivy) rather than just metrics aggregation

If you only read one thing

  • Agent observability differs from traditional observability because agents are non-deterministic and traces are far larger and messier (up to 1GB traces, 20MB individual spans) (c1, c2, c3).
  • Braintrust built a custom database with a forked Tantivy full-text index rather than using ClickHouse, because ClickHouse couldn't handle the text-indexing workload needed to query trace content (c4, c5).
  • The best agent teams involve non-technical domain experts (clinicians, wealth advisors, lawyers) directly reviewing traces and writing natural-language grading justifications, unlike traditional observability's purely technical audience (c6, c7).

01Traditional observability is about uptime, agent observability is about behavior quality
Slide at 05:10 · click any slide to enlarge · 2 more from this section below

Traditional observability is about uptime, agent observability is about behavior quality

  • Traditional observability tools like Grafana and Datadog measure latency, error counts, and whether a deterministic application is up or down.
  • Agent observability needs to additionally answer qualitative questions -- was the response grounded in gathered context, were the right tools used, was the output aligned to a brand standard -- because agents are non-deterministic and can take different paths for the same input.

“agents are non-deterministic, whereas applications are deterministic”

02Agent traces are a harder systems problem
Slide at 07:20 · click any slide to enlarge · 8 more from this section below

Agent traces are a harder systems problem

  • Agent traces are semi-structured, contain large amounts of unstructured text, and can be enormous: entire traces can exceed a gigabyte and individual spans can reach 20 megabytes.
  • This scale and structure makes agent trace ingestion, indexing, and real-time querying a fundamentally different systems problem than traditional metrics/trace pipelines.

“they can be an agent trace could be over a gigabyte in size. We've seen that”

“even with our own customers, an individual span can be 20 megabytes in size”

03Braintrust built a custom database rather than reuse ClickHouse
Slide at 17:00 · click any slide to enlarge

Braintrust built a custom database rather than reuse ClickHouse

  • Braintrust previously used ClickHouse but moved away from it because it couldn't adequately support the text-based indexing their workload needed, so they built their own database including a write-ahead log for instant trace visibility and a forked open-source Rust engine called Tantivy for full-text search across trace content, unified through a SQL-like query language.

“We used to use ClickHouse actually. Yeah. We moved away from it.”

04Agent observability pulls in non-technical domain experts
Slide at 12:00 · click any slide to enlarge · 1 more from this section below

Agent observability pulls in non-technical domain experts

  • Traditional observability's audience is systems and product engineers.
  • Agent observability, done well, also involves non-technical subject-matter experts like clinicians, registered nurses, wealth advisors, and lawyers directly reviewing agent traces and grading outputs in natural language because they are closest to the users or the problem domain.

“It's very technical people that align with traditional observability. Uh that could not be further from the truth for agent observability if you're doing it well”

said at 11:58

“we have folks that that are clinicians or registered nurses or wealth advisors or or or lawyers. We have seen them operate in our platform looking through traces”

said at 13:00
05Observability and evals treated as one system, plus emerging topic clustering
Slide at 13:00 · click any slide to enlarge · 8 more from this section below

Observability and evals treated as one system, plus emerging topic clustering

  • Braintrust treats observability and evals as the same underlying problem, differing only in that evals have known inputs run in batch while observability handles unknown inputs in real time.
  • About a month before the talk, Braintrust rolled out a feature that runs a lightweight LLM over incoming traces to perform embedding and clustering for topic modeling, surfacing usage patterns, intent, and sentiment.

“we kind of think of observability and evals as the same problem. The only difference between evals is that you're running them in batch and you know the inputs ahead of time”

said at 13:12

Commentary (ours)

The framing of observability and evals as the same system distinguished only by batch-vs-real-time and known-vs-unknown inputs is a clean mental model worth reusing when scoping any internal agent-monitoring buildout (ours).
