Pinecone Just Demoted Vector Search. Here's the Knowledge Layer.

SpeakerNate B Jones · Nate B Jones Watchyoutu.be/lqiwQiDglGk
AgentsAI industry

If you only read one thing

  • Pinecone shipped Nexus/NoQL admitting vector search alone isn't enough for agents, while SAP spent over a billion euros on non-LLM knowledge infrastructure (Dremio + Prior Labs) and Page Index claims 98.7% accuracy on FinanceBench by never chunking documents into vectors at all.
  • Pinecone says agent 'rediscovery' -- refetching and resummarizing context it already processed -- can eat up to 85% of agent compute.

01Four vendors, one memory problem

In the same few weeks, Pinecone shipped a product acknowledging vector search alone isn't enough, SAP spent over a billion euros on AI infrastructure with none of it going to LLM chatbot builds, Google made knowledge architecture the headline at Cloud Next, and Cloudflare shipped a memory product for agents. The host reads this cluster of moves as the infrastructure layer racing to fix a shared problem: agents burn context re-deriving things they should already know.

“they shipped a product that basically says vector search is not enough on its own, which is a very strange thing for a vector database company to ship”

02Classic RAG was built for chatbots, not agents

Classic vector-search RAG was built for question-answering, where the answer lives in a couple of paragraphs and exact wording doesn't matter. Agents instead run tasks -- opening tickets, checking policy, drafting responses -- and need a full bundle of context (customer record, policy, entitlement, prior tickets) assembled correctly, which classic RAG leaves the agent to reassemble from scratch on every run.

“That loop works because the answer usually lives in a couple of paragraphs in the source material, and the user doesn't need the exact wording from the source material to get their job done.”

▶ watch at 03:34

“It needs the customer record plus the policy plus the entitlement plus the prior tickets all assembled into the right shape.”

▶ watch at 05:05
03Page Index: don't chunk, use document structure

Page Index argues that chunking flattens documents into vectorized math and throws away structural meaning -- a clause's meaning can be overridden by a definitions section 40 pages away. Its alternative is a hierarchical, embedding-free tree of the document that the model reasons through, which it claims hits 98.7% accuracy on the FinanceBench evaluation.

“the structure of the document carries the meaning and when you flatten it into vectorized math chunks, you throw the meaning away.”

▶ watch at 07:37

“there's no vector similarity and they claim to hit 98.7% accuracy on a evaluation for finance called finance bench by using this tree approach to docs”

▶ watch at 08:07
04Bigger context windows don't fix the problem

The host argues that larger context windows give the model more room but don't decide what's authoritative, don't enforce permissions, and don't preserve document hierarchy -- citing Chroma's published research that model performance degrades ('context rot') as context gets larger and more cluttered.

“Chroma has published research showing model performance degrades as the context gets larger and more cluttered”

▶ watch at 13:45
05The recommended sequence: bundle first, database second

Rather than picking a vector database and then figuring out what to store in it, the host recommends first writing down the exact bundle of fields an agent needs for its task, then choosing retrieval primitives (vector search, document trees, tabular reasoning, graphs) to deliver that specific bundle.

“write down the bundle your agent needs, not relevant context. That's very vague. Write down the specific thing the agent needs.”

▶ watch at 15:19

“The point is you're choosing primitives because they deliver your bundle, not because they trended on LinkedIn last week.”

▶ watch at 16:20
