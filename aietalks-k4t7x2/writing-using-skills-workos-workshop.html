Full Walkthrough: Writing & Using Skills

A hands-on workshop with a working eval harness that fails a skill if it scores worse than a no-skill baseline, plus a real example of a skill regressing performance by being too prescriptive

If you only read one thing

  • Provide a handful of constraints rather than prescriptive step-by-step instructions in skill.md, and remember the description field is a routing rule for the LLM, not documentation for humans.
  • WorkOS runs an evals framework that fails a skill if its graded output is worse than the no-skill baseline; one presenter found his own next.js installer skill made results worse by being too dogmatic about how cloud code should already work.
  • At roughly 60 engineers, sharing skills across a team surfaces real governance friction (forking, review burden, staleness); WorkOS's answers include public/internal skill repos, a plugin marketplace, and zipping a skill folder into a .skill file so non-technical teammates can drag it into Claude Desktop.

The workshop frames skill-writing as a loop: author with constraints and a machine-readable description, manage runtime context with progressive disclosure and sub-agents, then grade the result against a no-skill baseline before sharing it at team scale (ours).

01How to write the skill itself

How to write the skill itself

  • The presenters recommend writing constraints ('never be vague,' 'cite a specific line and git commit reference') rather than being overly prescriptive about exactly how a task should be done, calling over-prescription a common failure mode.
  • They also stress that a skill's front-matter description exists for the model, not the human reader: it's the routing rule the LLM uses at runtime to decide whether the skill is relevant to the current task.

“if you provide just three constraints and say, "Never be vague." or "When you cite code, it always has to have a specific line and a Git commit reference with it." then you'll get better performance”

said at 09:19

“descriptions are routing rules, right? They're they're less for us and they're more for the AI to determine when to use it.”

02Managing context: progressive disclosure and sub-agents

Managing context: progressive disclosure and sub-agents

  • To avoid bloating the context window the way a large claude.md file does, skills can reference additional markdown files that only load when relevant to the current task (progressive disclosure), such as loading a testing.md file only for testing-related runs.
  • Separately, sub-agents are recommended when a chunk of work needs its own standalone context so it doesn't consume the main task's context window, reporting back only a summary.

“you can do the same thing in skills, but you can do it in a better way. And that is specifically with progressive disclosure.”

said at 44:12

“I want it to have its own standalone context so that it can go do like a bunch of work on on something and then that's not eating the context window”

03Gating execution on a confidence score

Gating execution on a confidence score

  • One technique demonstrated is having a skill (an 'ideation' skill) track its own confidence score across dimensions like problem clarity and success criteria, asking the user follow-up questions until it reaches a high-confidence threshold (demoed live at 95% or above) before starting the actual work.

“I'm 95% or above confident. I've mapped most of this problem space in my head, and now we can start work.”

said at 46:49
04Evaluating skills like code

Evaluating skills like code

  • WorkOS built an evals framework that runs a task with and without a given skill and fails the skill if its graded score comes out lower than the no-skill baseline.
  • One presenter described discovering through his own evals that an over-prescriptive next.js installer skill made results worse, since cloud code was already good at next.js without heavy guidance -- though he flagged the specific drop figure he cited as illustrative, not a real measured number.

“it'll fail if that grade is less with the skill than it was without”

said at 30:12

“I was making it worse by being too dogmatic about what I wanted it to do and it led to like a 30% drop I think in like overall accuracy based on these numbers I made up”

said at 69:38
05Sharing and governing skills at team scale

Sharing and governing skills at team scale

  • An audience member working at a roughly 60-engineer company described real friction once skills spread informally across a team: disagreement over where to store them, fear of review burden from shared-skill pull requests, and forked variants with near-duplicate descriptions.
  • WorkOS's own answer has included a public skills repo, an internal plugin marketplace, and packaging a skill folder as a renamed .zip-to-.skill file so non-technical teammates can drag it directly into Claude Desktop.

“So we're all at the moment with we've got I think 60 engineers. People are writing their own skills.”

Commentary (ours)

The governance question from the audience (60 engineers, forked skills, review burden) doesn't get a clean answer from the presenters -- their own team is still solving it ad hoc with multiple marketplaces rather than a single system, which suggests skill governance is still an open problem industry-wide, not just at WorkOS (ours).
