Make your own event-sourced agent harness using stream processors

SpeakerJonas Templestein · Iterate Watchyoutu.be/vi-2nasppAg · 64 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. Quotes are verbatim from the talk transcript with the time they were said.
patternAgentic engineeringInfra & servingMCP & protocols

Lays out a specific architectural pattern for a custom agent harness: every side effect is an event in a durable log, agent state is derived by a synchronous reducer over that log, and cross-agent/cross-process capabilities are added by ...

If you only read one thing

  • The stated design goal is an agent harness that is purely event-sourced -- 'aka debuggable' -- where every side effect becomes a logged event, in contrast to harnesses where side effects only show up in separate hosted traces.
  • The core abstraction is a synchronous reducer function that derives agent state from the event stream, with a built-in circuit breaker that pauses a stream once it sees more than 100 events in a second to catch infinite loops; the live demo service itself ran with no authentication.
  • The speaker argues against before-hooks (citing real performance regressions and broken context caching from before-hooks in another system) and instead proposes that cross-agent services like a prompt-injection checker plug in via the event stream itself, since MCP has no way to proactively hook into an agent's loop.

01Design goal: event-sourced, debuggable, extensible harnesses

Design goal: event-sourced, debuggable, extensible harnesses

  • The speaker's stated goal for a homegrown agent harness is to make it purely event-sourced, which he equates with debuggable, because in his experience most agent systems only partially event-source themselves and have side effects visible only in separate hosted traces.
  • He also wants the harness to be extensible by the agent itself, not just by humans, and eventually composable across contributors.

02A fully open demo with a circuit breaker for infinite loops

A fully open demo with a circuit breaker for infinite loops

  • The live demo service (events.iterate.com) ran with no authentication at all, exposing all event streams to the workshop room by design.
  • To guard against a real failure mode -- agents or plugins accidentally emitting endless streams of events -- the service automatically pauses ('circuit breaks') a stream once more than 100 events arrive in a single second, until someone manually resumes it.

“None of what we're doing today is safe, by the way. There's no authentication, you'll see.”

“if you put more than 100 events in a second or something, it is just going to circuit break and then the stream will be paused until somebody”

03Core abstraction: agents as reducers over an event stream

Core abstraction: agents as reducers over an event stream

  • The described programming model treats an agent as a stream processor: a synchronous reduce function that takes the current state and a new event and returns updated state, deriving whatever 'world state' the agent needs purely from the event log.
  • Side effects (like making an LLM request) are deliberately kept out of the reducer and run in a separate after-append hook, so a program that resumes after being offline can catch up on state without re-triggering side effects for every past event.

“the way I think about what we're really doing is we're we're writing a stream processor”

said at 30:24

“you can write the entire logic of your program as effectively a reduce function. This is this is synchronous and it just it just looks at all the new events as they come in and then it updates the state.”

said at 30:55
04A design rule: no before-hooks

A design rule: no before-hooks

  • The speaker states plainly that the system has no before-hooks, calling this very important, and contrasts it with the built-in server-side circuit-breaker logic, which is the only mechanism allowed to stop an event from being appended at all.
  • He argues against before-hooks in general, citing real performance regressions and cost increases in another system ('open claw') where before-hooks broke context caching.

“there's no before hook. This is very very important.”

said at 58:29

“I think there were some instances in in open claw for example some massive performance regressions and and cost increases where you know you can you can break uh you can break context caching quite easily with before hooks.”

said at 59:00
05Distributing capability: code-as-event workers and services outside MCP

Distributing capability: code-as-event workers and services outside MCP

  • A demonstrated capability lets any client append an event containing a small script (a reducer plus an after-append hook) that then runs automatically as a live processor on that stream -- shown live by appending an event whose JavaScript makes the stream reply 'pong' to any 'ping.' The speaker argues this event-stream approach is needed for cross-agent services like a prompt-injection checker because MCP currently has no way to proactively hook into an agent's loop.

“I have appended this event here that just has a little bit of JavaScript in it. And this little bit of JavaScript uh just makes it respond with pong whenever it encounters something with ping.”
