AI Agents for Performance: Ship Faster, Pay Less

SpeakerRajat Shah · Netflix Watchyoutu.be/CgsWxRUY5Eo
Agentic engineeringInfra & serving

If you only read one thing

  • An agent fed raw profiler output identified an O(n^2) pattern consuming 8.8% of CPU time and produced a mergeable code-review fix in under 5 minutes (c1, c3).
  • Once cataloged, the same anti-pattern was found reused across 7 different services via cross-repo search, with 0.5-4.6% CPU savings if fixed across all of them (c2).
  • Recommends a durable pattern catalog stored as plain markdown in a central git repo rather than a vector database, with canary verification and human approval kept as the final gate before any fix merges (c4, c5, c6).
01Feeding raw profiler output to an agent

The premise tested was whether an LLM agent, given the same raw call-stack profiling data a human performance engineer would spend roughly 20 minutes manually reading, could identify hot paths and produce a fix faster. In one live test, the agent identified an O(n^2) implementation consuming 8.8% of CPU time during the profiling window and, given the git commit running in production, checked out the repo, located the code, and produced a code-review-ready fix in under 5 minutes.

“it knows that this is consuming 8.8% of the CPU time during that uh uh period of profiling”

02One fix, reused across services

Beyond fixing a single instance, the agent was able to search across repositories for the same anti-pattern once it had identified it once. In one case a bad pattern (a counter object recreated on every iteration of a hot path) was found reused in seven different services via cross-repo code search, with an estimated 0.5% to 4.6% CPU-cycle savings if fixed across all of them.

“it could have savings between 0.5 to 4.6% of CPU cycles”

▶ watch at 13:32
03A shared pattern catalog as fleet-wide memory

Because individual agent invocations don't retain much memory, the team built a growing catalog of confirmed patterns and anti-patterns that any agent can query. The recommendation is to keep this catalog as plain markdown files in a centralized git repo rather than a vector database, so it stays both human- and agent-readable and can be seeded from prior findings, public sources, and internal performance playbooks.

“you can start with just a markdown files in a in a centralized Git repo”

▶ watch at 17:11
04Guardrails before anything merges

The confidence bar for the agent is deliberately kept at sending a code review, not pushing directly to production, given the risk of modifying code that's already running correctly without full business-context awareness. Fixes are verified with canary deployments comparing CPU, latency, and error rate between old and new code over about 10 minutes, on the framing that the profiler gives an estimate and the canary gives ground truth, with a human making the final merge decision.

“I'm still keeping the confidence uh bar to just send a code review and not directly uh push it to production.”

▶ watch at 19:14

“Profiler gives the estimate, canary gives ground truth.”

▶ watch at 23:23
05Where to start

The talk lays out a maturity path from fully manual profiling, to introducing an LLM for identification only, to a fixed, scheduled workflow (level 2 orchestration: profile, analyze, canary, propose fix) that the talk mainly covers, up to a more autonomous level 3 where the agent plans and reasons rather than following a fixed workflow. The explicit recommendation is to start at level one/two and only add more autonomy once sandboxing and evaluation are invested in, since level 3 requires much heavier security guardrails against prompt injection.

“Start with level one. Try to move to level two and you get maximum benefits.”

▶ watch at 32:41

Commentary (ours)

(ours) The catalog-as-markdown-in-git approach is presented as deliberately low-tech; the harder unstated problem is catalog curation at scale, since a shared file that many services and agents write into can itself become noisy or contradictory as it grows, which the talk doesn't cover.
