From Writing Code to Designing Systems: How the Developer Role is Changing

SpeakerChris Noring · Microsoft Watchyoutu.be/GdvKNwMcfd0
Agentic engineeringCoding agentsMCP & protocols

If you only read one thing

  • Proposes starting in the CLI (not the editor) as the new developer entry point, using the editor mainly as a control board for streams from CLI, editor, and GitHub (c1).
  • Recommends a three-tier guardrail stack -- Agents.md for repo-level intent, skills as strict repeatable contracts, and custom agents as reasoning orchestrators with tools and personas -- to prevent agents from producing unreviewable 'AI slop' (c2, c3, c4).
  • Shows delegation running in sandboxes that produce draft PRs for human review, both via CLI /delegate and GitHub issue 'assign to agent', framing this as how a developer becomes a 20x developer -- provided the guardrails are in place (c6, c7, c8, c9).
01CLI as entry point, editor as control board

Noring proposes a workflow shift: instead of starting in an editor, developers start in a CLI tool (GitHub Copilot CLI or an equivalent like Claude Code) because they no longer need to open an editor first. The editor becomes a secondary 'control board' that listens to streams from the CLI, the editor itself, and GitHub repos, rather than the primary place code gets written.

“as developers, the CLI could be a good entry point because I don't start my editor anymore because I don't need to”

▶ watch at 03:08
02Guardrails: Agents.md and skills

The first guardrail is an Agents.md file in every repo, giving high-level guidance on repository intent, application architecture, and constraints -- including what agents should never do. The second is skills: strict, self-contained, repeatable contracts (a folder with a skill.md and front matter) meant to constrain agents to a fixed recipe rather than letting them improvise.

“Agents.md. Should have this in all your GitHub repos or whatever kind of repo structure you have.”

▶ watch at 07:47

“a skill is called by an agent, it has a strict contract, it's self-contained because it just lives in a folder”

▶ watch at 09:52
03Custom agents extend skills into orchestrators

When a skill isn't enough -- because skills can't orchestrate themselves with other skills -- Noring introduces custom agents: higher-level constructs with a persona, the ability to use multiple skills and MCP servers, and the ability to reason and plan. Custom agents are further constrained by an explicit 'tools' declaration that limits what they're allowed to do (e.g., a researcher agent restricted to reading and web search, without file edit access).

“a skill is limited in what it can do. It can't really orchestrate itself with others. That's when you need an agent”

▶ watch at 12:57

“Tools is an important concept, because that's able to constrain the agent what it can do or not”

▶ watch at 14:29
04Scaling through delegation from CLI or GitHub UI

Once guardrails are in place, delegation happens two ways: calling /delegate from the CLI against a proper GitHub repo, or clicking 'assign to agent' on a GitHub issue. Both paths run the agent in a sandbox that cannot break out and do arbitrary things, and both produce a draft PR that brings a human back into the loop for review before merge.

“Most of our agents work in sandboxes, or all of them, right? So, they can't really break out of the sandbox and do a bunch of weird stuff, but they can create a PR”

▶ watch at 18:05

“I can assign to agent. So, essentially, if I'm in the user interface for a repo, I can just say”

▶ watch at 19:37

“we have approval gates ourselves, and we can probably add more approval gates. And the agent is literally asking us for a review before”

▶ watch at 21:09
05The payoff: 20x developer, provided guardrails hold

Noring closes by framing this stack as making a developer 20 times more productive -- but warns that 20 times more code without the right guardrails could just as easily become 20 times more slop.

“we are 20 times the developer we used to be. Providing of course we provided the right guardrails, right? Because 20 times more code, that could be 20 times more slop”

▶ watch at 22:12

Commentary (ours)

The talk's real argument isn't 'use agents' but 'the guardrail stack is now the engineering work' -- Agents.md, skills, and custom agents are presented as a maturity ladder rather than alternatives, which is a useful framing for teams still treating prompts as throwaway instructions instead of versioned contracts (ours).
