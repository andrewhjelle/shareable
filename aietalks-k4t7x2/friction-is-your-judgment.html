The Friction is Your Judgment

If you only read one thing

  • Coding agents are addictive and create an illusion of increased efficiency; because output volume rises, engineers lose the time to stop and ask whether an implementation is actually the best approach, and team composition shifts from writing-constrained to review-constrained.
  • Agents excel more at libraries (tightly constrained, clearly defined problems) than products (many interacting concerns that don't fit the agent's context window, making it reasonable locally but 'demented' at global scale); the fix is building an agent-legible codebase -- modularization, no hidden magic like ORMs or server actions, and mechanical enforcement like unique function names for token efficiency.
  • Some changes, like database migrations or permissioning, should never ship without a human making the judgment call; the talk's core reframe is that friction isn't the enemy of shipping -- it's the mechanism by which judgment steers the process.

01The addiction and the illusion of efficiency

The addiction and the illusion of efficiency

  • Ronacher and Poncela Cubeiro describe coding agents as addictive: engineers never know if the next prompt will fix the product or break it, and keep prompting anyway.
  • They argue the deeper problem is that fast output tricks engineers into believing they're more efficient, when in practice they have less time to stop and ask whether their current approach is the best one.
  • At the team level, every engineer's code-producing capacity now outstrips their reviewing capacity, changing the composition of who participates in the engineering process.

“these tools are super addictive. You never know if that next prompt is going to be the one that makes your product work and you've added a new”

02Agents optimize for shipping, not for the code you'd write

Agents optimize for shipping, not for the code you'd write

  • Because agents are reinforcement-learning trained to make progress and pass tests, they write code a human engineer typically wouldn't -- for example, silently falling back to default config instead of failing loudly.
  • The speakers argue this produces more failure conditions than human-written code because agents don't feel the discomfort that would normally stop a human from shipping code like that.

“these machines, they they optimize towards making progress, towards shipping stuff, towards unblocking themselves. And as a result, they're creating many more failure conditions than human written code normally would do”

said at 07:48
03Why agents do better on libraries than products

Why agents do better on libraries than products

  • The team found agents excel more at building libraries, which tend to have clearly defined problems and tight API constraints, than at products, which have many interacting concerns (UI, permissions, billing, feature flags) that don't fit in the agent's context window.
  • The result is that the agent reasons well locally but loses track of the global structure.

“for libraries, they tend to excel a lot more. And this makes sense because intrinsically when you're building a library, you tend to have a very clearly defined problem that you're trying to solve”

said at 09:22

“locally, the agent tends to be very reasonable, but when it gets to the global scale, it becomes a bit demented”

said at 10:25
04Building an agent-legible codebase

Building an agent-legible codebase

  • Their response is to treat the codebase itself as infrastructure that must be legible to the agent: modularizing not just components but code flow itself, avoiding hidden magic like ORMs or React server actions that obscure intent from the agent, and mechanical enforcement rules like one SQL query interface, one UI primitives library, and unique function names, which the team says also improves token efficiency when the agent greps the codebase.

“your code base has now become infrastructure. And as such, you have to design it in the way so that it is also legible for the agent, and it can make the most of it”

said at 10:25

“using React server actions or using ORM instead of raw SQL, what this does is that it hides intent from the agent. And if the agent can't see something, it can surely not respect it”

said at 11:59

“we we enforce unique function names. And the reason for this is not just more legibility for you and the agent, but it's actually also the token efficiency”

said at 13:02
05Reserve judgment calls for humans, and reframe friction

Reserve judgment calls for humans, and reframe friction

  • The team built tooling that separates mechanical, auto-fixable issues from changes that require a human judgment call, giving database migrations as an example that should never ship without a human weighing production data size and locking.
  • They close by arguing friction should be viewed positively rather than eliminated: it's the mechanism through which judgment and experience steer the process, the same way SLOs intentionally add friction to force teams to think about reliability needs.

“the friction actually in many ways is what's necessary on a physical level to steer. Like, without friction there's no steering, and and that is really necessary”

said at 17:40

“we don't think that a database migration should ever go in without a human making a judgment call on this because it very much depends on the locks, the size of the data in production”

said at 14:36

Commentary (ours)

The libraries-vs-products distinction is offered as an observed pattern from their own 12 months of practice, not a controlled comparison, so the causal claim (context-window fit explains the gap) is their working hypothesis rather than something independently measured (ours).
