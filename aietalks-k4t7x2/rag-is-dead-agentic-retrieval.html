It goes deep on one technique, embeddings as amortized cache-compute versus repeated per-session grep, rather than presenting a full end-to-end system.

If you only read one thing

  • Cursor's own blog posts report 12.5-24% higher answer accuracy and measurable retention/dissatisfaction gains from semantic search built on Turbopuffer, despite Twitter claiming RAG is dead.
  • Claude Code dropped its early local vector DB approach (per Boris Cherney) and instead relies on per-session grep, which the speaker frames as cache-compute: repeated re-discovery cost vs. upfront indexing cost.
  • Citing Jeff Dean, retrieval's real job even with huge context windows is narrowing a trillion tokens down to 'the right million,' not eliminating retrieval.

This reframes the RAG-vs-grep debate as an amortization question: grep re-pays a discovery cost every session while an index pays it once, and both are just ways of narrowing a huge corpus down to the useful slice (ours).

Defining rag vs. agentic search

  • The speaker distinguishes the popular narrow reading of RAG (simple one-shot vector search into an LLM) from the fuller retrieval-augmented-generation definition that also includes full-text search, BM25, grep, regex, and filters.
  • Agentic search, commonly associated with tools like Claude Code and Codex, is defined as giving an agent tools to progressively and iteratively find and reason over context rather than a single retrieval call.

“it's really giving the agents a set of tools to kind of progressively and iteratively find and reason over context”

Cursor's measured gains from semantic search

  • Cursor indexes codebases by chunking and embedding them, using Merkle-tree hashing to avoid re-chunking/re-embedding shared code across a team, backed by Turbopuffer.
  • Cursor's internal benchmark reported roughly a 12.5-13.5% average increase in answer accuracy across models from adding semantic search, and close to a 24% increase for its Composer model (pre-Composer 2).

“on average across models I think it's like a 12 and a half or 13 and a half percent increase in answer accuracy”

Small-looking numbers, real product impact

  • An online A/B test Cursor ran showed about a 2.6% increase in code retention and a 2.2% decrease in dissatisfied user requests in large codebases from having semantic search available.
  • The speaker notes these percentages look modest only because semantic search doesn't get used on every query, not because the effect is weak.

“it's almost like a 2.6% retention code retention in large code bases and there's a 2.2% decrease in dissatisfied user request”

04Claude Code's grep-only approach and its cost

Claude Code's grep-only approach and its cost

  • Per a tweet from Boris Cherney, Claude Code experimented with a local vector DB early on but abandoned it, relying instead on repeated per-session grep-read-assess loops to rediscover the same codebase understanding.
  • The speaker frames semantic search/embeddings as 'cache compute': Cursor's upfront indexing cost is paid once, while Claude Code-style grep pays a repeated token cost (an example subtask alone used around 6,000 tokens) every session, across every developer, every day.

“Cloud Code doesn't use vector search as covered by the tweet from Boris Cherney”

said at 06:09

“in early iterations of Cloud Code they actually did use rag in their local vector DB but they found that it just didn't really work out for them”

05The real point of retrieval at scale
Slide at 10:30 · click any slide to enlarge

The real point of retrieval at scale

  • The speaker cites a Jeff Dean remark that large context windows don't remove the need for staged retrieval: even at a trillion-token context, you still need a lightweight mechanism to narrow that down to millions of relevant tokens.
  • Turbopuffer frames its own role as helping customers go from trillions of stored tokens down to the right hundred-thousand, ten-thousand, or million tokens to pass into a model's context window.

“the exact quote is you don't need a trillion at once, you need the right million”

said at 10:18

Commentary (ours)

The framing of embeddings as 'cache compute' is the sharpest reusable idea here -- it reduces the RAG-vs-agentic-grep debate to an amortization question (how many repeated queries justify upfront indexing cost) rather than a philosophical one, which is a cleaner lens for picking a retrieval architecture (ours).
