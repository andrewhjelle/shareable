The maturity phases of running evals

patternEvals & benchmarksAgentic engineering

Lays out a maturity progression for building agent evals -- documented vibe-checks, then LLM-as-judge, then tool-call/trace-level evaluation, then a production-trace flywheel -- useful for deciding what eval investment matches a team's c...

If you only read one thing

  • Evals should target an agent's specific known failure modes rather than exhaustive unit-test-style coverage of every possible input (c1).
  • Start with documented human vibe-checks (thumbs up/down plus a written justification), then scale that judgment with LLM-as-judge -- but evaluate the judge itself so it stays aligned with human judgment (c2, c3, c8).
  • As agents gain tool calls, especially CRUD operations against external systems, evals must capture full traces and grapple with representing external system state offline without overwriting production data (c5, c6).

01Evals target failure modes, not exhaustive coverage

Evals target failure modes, not exhaustive coverage

  • The speaker distinguishes evals from unit tests: unit tests aim for exhaustive coverage, while evals should start from an agent's known failure modes (identified by the builder or a subject matter expert) rather than trying to test every possible scenario, which would be infinite.

“Evals are not unit tests where whereas unit tests are very exhaustive in in how you perform them”

02Stage one: vibe-checking with documented justification

Stage one: vibe-checking with documented justification

  • Starting with informal 'vibe checks' is acceptable, but the speaker recommends having a human (ideally a subject matter expert) give a thumbs up/down on sample outputs plus a written justification for that judgment.
  • The justification is what later gets used to scale that domain expertise into automated grading.

“you should make that human annotator um perform a justification for why they chose that thumbs up up or thumbs down”

said at 07:49
03Stage two: scaling judgment with LLM-as-judge
Slide at 09:30 · click any slide to enlarge

Stage two: scaling judgment with LLM-as-judge

  • Once failure modes are understood from human annotations, teams can use LLM-as-judge techniques to automate scoring at scale, sometimes combined with deterministic code-based checks (e.g., too many tool calls or tokens).
  • The speaker warns that an LLM judge isn't automatically trustworthy just because it's an LLM -- judge outputs should themselves be evaluated against what a human would decide, and should be gathered from production or UAT traces rather than synthetic tests.

“just because you put a robe and a cloak on an LLM, that doesn't make it inherently more trustworthy”

said at 10:24

“I would embrace LLM as judge, but also perform a lot of evals on the LLM as judge so that like it's it's very aligned with what a human would decide”

said at 17:43
04Production traces should feed the eval flywheel
Slide at 11:50 · click any slide to enlarge · 1 more from this section below

Production traces should feed the eval flywheel

  • The speaker recommends treating evals as re-running production rather than running isolated tests, capturing real production traces into the evaluation dataset to build a flywheel: capture traces, diagnose issues, feed examples back into offline experiments, and use results to guide agent improvements.

“Think about evals like rerunning production because ultimately we want to be confident as we run, uh, run these workloads in in production”

said at 11:27
05Stage three: tool calls and CRUD operations complicate evals
Slide at 12:30 · click any slide to enlarge · 2 more from this section below

Stage three: tool calls and CRUD operations complicate evals

  • As agents move beyond simple model calls to tool use, the speaker separates context-gathering tools (which inject data into the LLM) from CRUD-based tools (create/read/update/delete against external systems).
  • CRUD tools make evals harder because it's difficult to represent what state an external system was in at the time an eval input was created, and running evals live risks overwriting production data.

“There is context gathering tools that are just, uh, gathering data and injecting that into the LLM. And then there is CRUD-based tools where you're creating, reading, updating, or deleting information”

said at 13:01

“really challenging to represent the state that the other external systems were were in at the time that eval input was created”

said at 14:34
06What's emerging next
Slide at 18:00 · click any slide to enlarge

What's emerging next

  • The speaker points to two emerging patterns: automated topic modeling at scale to surface failure modes in production without manual review, and running evals through coding-agent CLIs (e.g., Claude Code paired with an eval provider's CLI) to automate the eval workflow itself.

“performing topic modeling at scale to make sure that you're uncovering those failure modes automatically in production”

said at 17:11

Commentary (ours)

The CRUD-eval state-representation problem the speaker flags as 'not completely solved' looks like the next real bottleneck in agent evals once teams move past simple text-in/text-out tasks -- worth tracking which vendors ship a credible mock-state or timestamped-query solution first (ours).
