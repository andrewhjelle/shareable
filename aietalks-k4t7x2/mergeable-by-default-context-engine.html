patternContext engineeringAgentic engineeringMCP & protocols

Explains one technique in depth, the context engine rules for access gating, surfacing conflicts, and never caching answers, illustrated with before/after benchmark numbers rather than a full end-to-end system.

If you only read one thing

  • Naive RAG causes 'satisfaction of search': agents stop once they find something that looks like an answer, risking missed conflicting or more important information elsewhere, similar to a radiology diagnostic bias (c1)
  • On a benchmark task (implementing Anthropic's adaptive thinking mode), Unblocked's context engine cut a 2.5-hour, 21-million-token agent run to 25 minutes and 10 million tokens; roughly 90% of agent time went to context collection rather than code writing, and output tokens -- not input tokens -- turned out to be the real performance drag (c2, c8, c7)
  • Two hard-won lessons: surface conflicts the engine can't resolve instead of hiding them, and never cache/reuse a past answer, since code, docs, and reasoning change constantly (c3, c4)

Why naive RAG and bigger context windows aren't enough

  • The talk names three myths: that naive RAG over docs is a context engine, that wiring up more MCP servers solves the problem, and that a bigger context window will fix it.
  • The 'satisfaction of search' term, borrowed from radiology, describes agents stopping once they find a plausible-looking answer -- like a dangerous missed diagnosis -- rather than continuing to search for the real, possibly-buried information.

Benchmark: 25 minutes vs. 2.5 hours

  • On an ambitious task (implementing Anthropic's new adaptive thinking mode across a codebase), an agent without the context engine took 2.5 hours and 21 million tokens, largely because incorrect first attempts required multiple correction loops.
  • With the context engine active it took 25 minutes and 10 million tokens.
  • The speaker separately notes that roughly 90% of an agent's time goes to context collection rather than code writing, and that output tokens, not input tokens, are the bigger drag on performance.

“without um the context engine, it took 2 and 1/2 hours to finish this task with 21 million tokens, which is a lot of tokens. Um but with the context engine, it took only 25 minutes and 10 million tokens”

03Hard-won lessons: surface conflicts, never cache answers

Hard-won lessons: surface conflicts, never cache answers

  • Unblocked's team initially resolved conflicting information using naive strategies and hid the cases it couldn't resolve, which they now consider a mistake -- unresolved conflicts should be surfaced and learned from.
  • They also warn against caching a context engine's answer to reuse for similar future questions, since code, docs, and the reasons behind decisions change constantly.

“we hid conflicts instead of surfacing them. So, um by con- by hiding conflicts, I don't mean that we just ignored the conflicts”

said at 23:26

“when when a context engine supplies an answer, um do not cache the answer and try to serve that same answer up again uh to a similar question”

said at 24:27
04Access control has to flow up to answers
Slide at 17:30 · click any slide to enlarge · 2 more from this section below

Access control has to flow up to answers

  • Because organizations have private Slack channels and repositories with restricted access, Unblocked's context engine only surfaces private-channel information to a user if that user already has access to it, and the resulting answers stay private to them.

“when when Unblocked answers questions, uh it will use private channel information, but it won't it it will only use that information if the person that's asking the question has access to it”

said at 17:12

Where the context engine pays off most

  • The speaker says the biggest return comes from using the context engine during the planning phase of a task, before code is written, alongside use cases like code review, ticket enrichment, triage, and incident management.
