Mergeable by default: Building the context engine to save time and tokens

SpeakerPeter Werry · Unblocked Watchyoutu.be/5ID22ACI7IM

If you only read one thing

  • Naive RAG causes 'satisfaction of search': agents stop once they find something that looks like an answer, risking missed conflicting or more important information elsewhere, similar to a radiology diagnostic bias (c1)

01Why naive RAG and bigger context windows aren't enough

The talk names three myths: that naive RAG over docs is a context engine, that wiring up more MCP servers solves the problem, and that a bigger context window will fix it. The 'satisfaction of search' term, borrowed from radiology, describes agents stopping once they find a plausible-looking answer -- like a dangerous missed diagnosis -- rather than continuing to search for the real, possibly-buried information.

“that's that's kind of like a dangerous thing medically, because uh there might be other indicators for things like cancer that get missed”

02Benchmark: 25 minutes vs. 2.5 hours

On an ambitious task (implementing Anthropic's new adaptive thinking mode across a codebase), an agent without the context engine took 2.5 hours and 21 million tokens, largely because incorrect first attempts required multiple correction loops. With the context engine active it took 25 minutes and 10 million tokens. The speaker separately notes that roughly 90% of an agent's time goes to context collection rather than code writing, and that output tokens, not input tokens, are the bigger drag on performance.

“without um the context engine, it took 2 and 1/2 hours to finish this task with 21 million tokens, which is a lot of tokens. Um but with the context engine, it took only 25 minutes and 10 million tokens”

03Hard-won lessons: surface conflicts, never cache answers

Unblocked's team initially resolved conflicting information using naive strategies and hid the cases it couldn't resolve, which they now consider a mistake -- unresolved conflicts should be surfaced and learned from. They also warn against caching a context engine's answer to reuse for similar future questions, since code, docs, and the reasons behind decisions change constantly.

“we hid conflicts instead of surfacing them. So, um by con- by hiding conflicts, I don't mean that we just ignored the conflicts”

▶ watch at 23:26

“when when a context engine supplies an answer, um do not cache the answer and try to serve that same answer up again uh to a similar question”

04Access control has to flow up to answers

Because organizations have private Slack channels and repositories with restricted access, Unblocked's context engine only surfaces private-channel information to a user if that user already has access to it, and the resulting answers stay private to them.

“when when Unblocked answers questions, uh it will use private channel information, but it won't it it will only use that information if the person that's asking the question has access to it”

▶ watch at 17:12
05Where the context engine pays off most

The speaker says the biggest return comes from using the context engine during the planning phase of a task, before code is written, alongside use cases like code review, ticket enrichment, triage, and incident management.

“definitely and especially during the planning phase, okay? This is where you get the biggest bang for buck unquestionably”
