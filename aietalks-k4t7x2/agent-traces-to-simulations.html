From Agent Traces to Agent Simulations

SpeakerRustem Feyzkhanov · Snorkel AI Watchyoutu.be/Ib5t2RLtxvM
Agentic engineeringEvals & benchmarks

01Why every company needs its own benchmark

The speaker argues every company needs a benchmark as the only reliable way to evaluate, release, and improve agents, and that it must mimic real tools, APIs, policies, and workflows rather than being a generic test. Snorkel positions itself as a data-as-a-service company that builds these benchmarks at scale, running millions of agent simulations per month.

02Traces are useful, but not repeatable

Traces (input prompt, actions taken, output) are good for finding failures in production but hard to use for comparing configurations, because re-running against production yields a different database state, different tool versions, and other drift, so it's never a true apples-to-apples comparison.

“it's hard to make sure that everything is repeatable because you will get different database state, different tool versions, and so on”

▶ watch at 02:06
03Public benchmarks orient, private benchmarks ship

Public benchmarks like SweepBench, TerminalBench, and computer-use benchmarks are narrowly scoped to specific domains and mostly report pass rate, which is useful for judging model frontiers but not for shipping. A private benchmark that reflects a company's own use cases, tooling, and policies is what's actually used to release.

“public benchmark is useful to orient and build your prior, but your private benchmark is useful to ship”

▶ watch at 03:41
04The Oracle solution and reward hacking risk

Each benchmark task pairs the agent's run with an Oracle solution, run through the same environment, to confirm the task is actually solvable before an agent is judged against it. Benchmark tasks can still fail in several ways during development, including agents reward-hacking a simulation once they detect they're in one.

“when Oracle solution runs, it runs through the whole sequence, but just instead of running the real agent, it runs Oracle”

▶ watch at 06:51

“Agent can try to reward hack simulation environment because it can understand that it's in simulation and it can hack it.”

▶ watch at 12:03
05Verification methods and where fixes belong

Verifiers can be deterministic checks, LLM/harness/agent-as-judge, or subject-matter-expert review of specific disagreement cases, chosen depending on the use case. When simulation reveals a bug, the fix should be placed in the correct layer of the stack (harness, skill, structured-output schema) instead of defaulting to stuffing more instructions into the prompt.

“Sometimes you can use LLM as a judge, or even harness as a judge, or agent as a judge to evaluate basically whether the uh trace quality was successful”

▶ watch at 11:02

“with simulation, you control the full stack. You can evaluate the full stack. And you can make sure that fix lives in the correct place.”

▶ watch at 14:10

Commentary (ours)

(ours) The framing of "benchmark as software with its own CI" is the load-bearing idea here; the specific Harbor file format is secondary and likely to be superseded, but the discipline of tagging task difficulty and gating release on it is portable to any team building agents.
