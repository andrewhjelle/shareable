Velocity Sickness: What Happens When Your Whole Team Gets 10x Faster

SpeakerMatt Dailey · Ref. Watchyoutu.be/Kz4QJmNrVXU
Agentic engineeringCoding agentsContext engineering

If you only read one thing

  • Four "velocity sickness" symptoms appear as teams speed up with AI: too many PRs to merge, engineers/agents moving in uncoordinated directions, discarding agent context ("agent bankruptcy"), and letting agents make decisions that should stay with the engineer (c1, c2, c3).
  • The proposed fix is a "decision layer": work in shared, durable docs instead of isolated, ephemeral chats, so key decisions get made explicit and agents can stay stateless and reproducible (c4, c5, c6).
  • Predicts engineering becomes multiplayer by default, and recommends sharing your plan doc with a teammate before letting an agent implement it (c7, c8).
01Four symptoms of velocity sickness

The speaker defines velocity sickness as the stress caused by sudden AI-driven output increases, at both the individual and team level, resulting in output without impact. He lists four problems: too many PRs to merge and reconcile, engineers and agents sprinting in uncoordinated directions, "declaring agent bankruptcy" (discarding a day's worth of agent sessions and re-running the same work), and the most important one, engineers ceding ownership of code by letting agents make critical decisions.

“The first one, too many PRs to merge. This is the like classic first problem you hit when you start adopting AI as an engineer.”

02Docs, not chat, for the decision layer

The speaker argues that pre-AI engineering had two modes, planning and implementation, and that AI has collapsed implementation into something agents do, leaving planning and polish as the human work. Chat interfaces were built for implementation and are by default isolated and ephemeral, so decisions made inside them aren't shared with the team; a tool built for this new "decision layer" should instead be built around durable, shared docs.

“So let's think about what a tool built for the decision layer would look like. It'd be a tool built for docs and not chat.”

03Separating the agent (action) from the doc (state)

The core structural change is to pull state out of the agent session and into the doc: the agent becomes the action, and the doc becomes the state. This lets new, stateless agents spawn from the same shared context, and means a team member can reconstruct project state by reading the doc rather than an agent's chat history.

“What you want is to separate the the agent as the action and the doc as the state.”

▶ watch at 13:28
04What changes in practice

Applying this, the speaker predicts engineering work becomes multiplayer by default, since the decision layer is inherently more collaborative than heads-down implementation. He recommends explicitly sharing a plan doc with a teammate before handing it to an agent to implement, rather than moving straight from plan to agent execution.

“I think the future of engineering is multiplayer. It's going to be multi multiplayer by default sooner than we think.”

Commentary (ours)

(ours) The "agent as action, doc as state" framing is the sharpest reusable idea here; it's also effectively Ref's product pitch, so the specific claim that docs solve agent-bankruptcy and ownership problems is worth testing against a team's actual review overhead before adopting it wholesale.
