Using Spec-Driven Development for Production Workflows

SpeakerErik Hanchett · AWS Watchyoutu.be/IddXPepIAS4
Agentic engineeringCoding agentsContext engineering

If you only read one thing

  • Spec-driven development means writing requirements and design documents in markdown before any code is generated, which the speaker frames as guiding an eager 'AI intern' rather than letting it improvise.
  • The AWS Kiro flow moves through requirements (EARS format) to a design doc with diagrams to a task list, with property-based tests generated against the requirements, and a human expected to review and edit at each stage.
  • MCP servers can feed existing Jira/Asana tickets and requirements docs into the spec generation step so product-manager work isn't duplicated.
01What spec-driven development is and why it helps

The speaker defines spec-driven development as writing structured specifications and a design document in markdown before any code is written, arguing this works well with LLM coding assistants because it gives them guardrails. He compares uninstructed coding agents to overeager AI interns that need explicit direction or they 'go off the rails.'

“structured specifications are created before any code is written. That's the definition of really the specs or the requirements of this spec-driven development”

▶ watch at 00:30

“So, you really need to guide them. Because if you give them just a little bit of of leeway, they will go off the rails”

▶ watch at 01:02
02Practical cautions: context size, skills, and human review

He warns against putting too much or too little information in agents.md/claude.md steering files, recommends using on-demand 'skill' instruction files during the spec-driven flow, and stresses that the human remains the reviewer of every generated design and requirements document because responsibility for errors falls on the human, not the agent.

“I would be very careful not to put too much information or too little information in that. Kind of like that Goldilocks zone of information is what you need”

▶ watch at 03:30

“if something goes wrong, you are the person that are going to be blamed for it, not the agent”

▶ watch at 05:42
03The Kiro workflow: requirements to design to tasks

AWS's Kiro IDE/CLI walks through a requirements phase in EARS format with clarifying questions, then a design document with mermaid diagrams, then an implementation task list that includes property-based tests run against the requirements and design docs. The speaker recommends stopping to manually edit each generated document and often asks the tool to promote the first four tasks into an MVP.

“it creates this uh requirements phase where it's in this ears format and it gives you the introduction, like the requirements, the user stories”

▶ watch at 10:51

“once it creates this task list, I tell it, Please take the top four tasks, put them at the top, and create an MVP for me first”

▶ watch at 12:26
04MCP feeds specs from existing ticket systems

The speaker connects Kiro to MCP servers so that existing product-manager tickets and requirements documents in tools like Jira or Asana can be pulled directly into the spec-generation step, reducing duplicated writing. He notes this can be configured either in the steering/agents.md file or specified at the start of a spec task.

“you can have something like in Jira or Asana, all your tickets, all your uh large requirements docs, and then you can have it being pulled into your Spec Driven Development Flow”

▶ watch at 13:58

Commentary (ours)

The repeated instruction to manually edit generated specs before implementation is the load-bearing step most teams skip under time pressure, and it's the one the talk claims determines whether the downstream code is trustworthy (ours).
