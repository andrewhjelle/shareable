Context Is the New Code

SpeakerPatrick Debois · Tessl Watchyoutu.be/bSG9wUYaHWU · 27 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. Quotes are verbatim from the talk transcript with the time they were said.

Useful for teams deciding whether to formalize prompts, skills, and agent

If you only read one thing

  • Debois argues context (prompts, skills, agent.md files) is now the artifact developers write, including skills that encode multi-step workflows like figuring out a project's package manager before acting.
  • He recommends treating context like code: lint it, get LLM feedback on clarity, and run LLM-as-judge evals -- but since evals are non-deterministic, track pass rates as error budgets rather than pass/fail.
  • He warns that most skills in public marketplaces are low quality, and that agents load agent.md/skill.md unrestricted even inside a sandbox, so teams need a separate context filter plus scanning tools like Snyk for credentials and injected instructions.

01Context replaces code as the thing you write

Context replaces code as the thing you write

  • Debois says he barely touches code directly anymore -- he tells the AI what to do, and increasingly turns reusable pieces of logic into skills instead of hand-written code.
  • His example: a skill that tells the agent to first figure out a project's package manager and ecosystem, then walk through setup steps with the user, replacing what would otherwise require a lot of custom coding.
  • He frames this as a DevOps-style shift, asking what a 'context development lifecycle' looks like the way 2009-era DevOps asked what it would mean for ops to look more like dev.

02Testing context like code: linting, judges, and error budgets

Testing context like code: linting, judges, and error budgets

  • He argues teams need to start writing evals -- tests for context, not just code -- borrowing the idea from AI engineering but applying it to coding-agent setups where it's still uncommon.
  • He describes layered checks: linting-style validation of skill format, an LLM that reads your context and gives Grammarly-style feedback on clarity, and LLM-as-judge checks that can be given tools to actually run the generated code (e.g., curl a new endpoint) rather than just reading it.
  • Because eval runs are non-deterministic, he recommends running each test multiple times and tracking results as an error budget rather than expecting a single pass/fail.

03Distributing context hits the same quality problem as package registries

Distributing context hits the same quality problem as package registries

  • As skills get packaged and shared through registries and marketplaces, Debois says the overwhelming majority of what's published is low quality.
  • He frames this as a reason to look at what others are doing for inspiration, not to install skills wholesale, and expects the ecosystem to face the same dependency-conflict and versioning problems that code packages already have.

“the reality is 99.9, and I mean that in a very sincere way, of the skills is crap”

04Running context in production needs its own security layer

Running context in production needs its own security layer

  • Debois says scanning tools like Snyk now check context for exposed credentials and third-party dependency issues, mirroring code-supply-chain security.
  • He describes testing his own sandboxed agents and finding they actively probe for exploitable things like environment variables, and notes that agent.md and skill.md files load unrestricted regardless of sandbox settings -- so he recommends a separate 'context filter,' functioning like a web application firewall, to catch prompt injection and malicious patterns before they reach the agent.
