Feedback Loops are All You Need

SpeakerMehedi Hassan · Granola Watchyoutu.be/ON5LIT0M4do · 10 min SourceRecording of this talk at AI Engineer (2026), published on YouTube by the conference. Quotes are verbatim from the talk transcript with the time they were said.
patternProduct & UXContext engineeringCoding agents

Describes concrete infrastructure choices for taking an LLM chat feature from demo to production: building an internal tracing tool instead of buying observability, and converting a desktop Electron app into a deployable web shell to run...

If you only read one thing

  • A one-shot chat feature broke immediately in production: web search was too slow, follow-up emails didn't match the user's voice, and one prompt couldn't serve every persona (sales vs. engineering vs. HR).
  • Vendor web search adds token cost that bubbles up per query and can silently degrade overnight when a provider ships an update outside your control, so Granola built its own tracing tool for full visibility into tool calls.
  • Converting the Electron app's front end into a web shell let every PR get a preview link so LLM agents like Cursor can self-test and screenshot changes, which the talk frames as building a feedback loop rather than one-shotting better.

This traces how Granola's shipped-but-broken chat feature pushed them to build in-house tracing and a testable web shell, both of which feed the talk's feedback-loop thesis (ours).

01Generic chat features break fast in production

Generic chat features break fast in production

  • Granola's product philosophy is best-in-class meeting notes that stay out of the user's way.
  • When the speaker one-shotted a chat feature onto that product and shipped it, users immediately hit problems: web search was too slow, follow-up emails didn't read like the user's own writing, and the same prompt gave sales, engineering, and HR users answers tuned for the wrong role.

02Vendor web search is riskier than it looks

Vendor web search is riskier than it looks

  • Adding a web search tool looks like one line of code, but token usage and cost bubble up fast on complex queries and can blow up context, making per-chat cost infeasible at millions of users.
  • The provider is also outside Granola's control: an overnight model update degraded web search quality with no visibility into why, leaving switching providers as the only lever.

“the token usage and token cost can bubble up quite a lot, especially for complex queries. It's going to blow up your context.”

said at 03:06

“shipped an update and for some reason web search degraded and it was completely out of our control.”

said at 03:37
03Building in-house tracing to open the black box

Building in-house tracing to open the black box

  • Rather than buy a SaaS observability product, Granola built its own tracing tooling, using LLMs to build it quickly, to get full visibility into every tool call from start to finish -- which tools fired, why, and at what cost.
  • The UI was built to serve product, data, and CX staff, not just engineers, so people can diagnose failures without writing complex queries against raw logs.

“we started building our own tracing tools. And obviously, thanks to LLMs, you can actually one-shot these things.”

said at 04:38
04Turning a desktop app into a testable web shell

Turning a desktop app into a testable web shell

  • Because Granola is an Electron desktop app that can only run one instance at a time, testing multiple feature variants in parallel created friction.
  • The team turned the Electron front end into a web shell deployed online, so every pull request gets a preview link, and coding agents like Cursor now test changes and upload screenshots to the PR automatically.

“we took our Electron app and we turned the front-end of the Electron app into a web shell. And this was deployed online.”

said at 07:12

“because LLMs can now self-verify their work, these guys are now like once we open a PR, Cursor goes and tests it, uploads a screenshot into our PRs, which speeds up the testing so much more.”

said at 07:44
05The thesis: feedback loops, not one-shotting

The thesis: feedback loops, not one-shotting

  • The talk's closing argument is that the fix for an LLM feature that misbehaves isn't trying to one-shot a better prompt -- it's building a feedback loop, described as feeling like playing tennis with the LLM, so the shipped product reflects many tested iterations rather than a single untested guess.

“the answer isn't to one-shot better. It's about figuring out how you can make that feedback loop where it kind of feels like playing a tennis game with LLM.”

said at 08:46

Commentary (ours)
