Loop Engineering from First Principles

patternAgentic engineeringCoding agents

Argues for building agentic loops on control-theory primitives (sensor, controller, actuator, incremental change) instead of blind bash-loop prompting, and gives a concrete internal example: a scheduled GitHub Actions workflow using AST ...

If you only read one thing

  • Piping a prompt in a loop to a coding agent without control produces 40,000-line PRs nobody wants to read, and this approach is only viable with an unlimited token budget most teams don't have (c1, c3).
  • The recommended architecture borrows from control theory: a sensor measures current vs. desired state, a controller picks a small incremental change, and an actuator applies it, which avoids over-steering and destabilizing the codebase (c4, c5).
  • HumanLayer's internal loop runs as a scheduled GitHub Actions workflow and refuses to open a new PR while a prior PR from the same loop is still open and unreviewed, guaranteeing at most one open PR per loop at a time (c7, c8).

02Borrow from control theory: incremental change, not one big leap
Slide at 06:20 · click any slide to enlarge · 4 more from this section below

Borrow from control theory: incremental change, not one big leap

  • The talk maps agentic loops onto a classic control-theory loop: a sensor measures the current state of the codebase against a defined set point (desired state), a controller turns the resulting error into a small control signal, and an actuator applies that incremental change.
  • The stated benefit of incremental change over trying to reach the end state in one shot is avoiding over-steering and destabilizing the system.

“control loops change a system incrementally instead of just trying to get straight to the end state immediately all at once and risk blowing everything up”

said at 06:13
03Design around what you can measure, incrementally change, and get feedback on
Slide at 09:00 · click any slide to enlarge · 8 more from this section below

Design around what you can measure, incrementally change, and get feedback on

  • The three questions used to decide whether a control loop fits a problem are: can you find something measurable, can you apply changes incrementally, and can you get feedback on the quality of each change.
  • The controller step should stay deterministic where possible, on the reasoning that sending an agent to do deterministic code's job is avoidable even though it's technically possible.

“The key questions are, can we find something we can measure? Can we apply changes incrementally? And can we get feedback on the quality of those changes?”

said at 08:47

“I don't think you should ever send an agent to do deterministic code's job, but you certainly can”

said at 11:23
04Run loops as scheduled CI workflows
Slide at 13:30 · click any slide to enlarge · 5 more from this section below

Run loops as scheduled CI workflows

  • The recommended way to actually run a loop is as a GitHub Actions (or GitLab/CircleCI) workflow rather than a standalone bash loop, because CI already has access to the codebase, secrets, and scheduling/dispatch primitives.
  • HumanLayer's internal example schedules a single sense-control-actuate iteration once a day to migrate RPC procedures to the Effect library, producing one small, low-risk PR each morning.

“my recommendation is to use GitHub actions or your GitLab or your CircleCI or whatever else you're using because it has access to your code, it has access to your secrets, and it has great dispatch and scheduling primitives”

said at 13:26
05Flow control keeps loop output reviewable
Slide at 16:00 · click any slide to enlarge · 3 more from this section below

Flow control keeps loop output reviewable

  • To stop unreviewed loop PRs from piling up while the team is away, each loop workflow checks for an existing open PR carrying its label before running and shuts down if one is found, since an unreviewed prior PR means no human has re-steered the loop yet.
  • This guarantees at most one open PR per loop at a time; with roughly 150 RPC procedures to migrate, doing them strictly one at a time would take about 6 months, motivating running multiple procedures or multiple parallel workflow instances at once.

“This way we have exactly one PR at most open per loop at a time. No stacking, no duplication, hopefully no conflicts.”

said at 15:59

“I have 150 RPC procedures to migrate. If I do one at a time, it's going to take 6 months, which is way longer than I want to wait.”

said at 16:30

Commentary (ours)

(ours) The talk's central move is treating the loop's control signal itself as an engineering artifact (deterministic sensor via AST grep, a version-controlled feedback file, PR labels for workflow identity) rather than trusting an agent to self-regulate end to end, which is a meaningfully different design stance from the 'just prompt a loop' framing it's arguing against.
