Loop Engineering from First Principles

SpeakerKyle Mistele · HumanLayer Watchyoutu.be/xIt_mTQp6mY
Agentic engineeringCoding agents

If you only read one thing

  • Piping a prompt in a loop to a coding agent without control produces 40,000-line PRs nobody wants to read, and this approach is only viable with an unlimited token budget most teams don't have (c1, c3).
  • The recommended architecture borrows from control theory: a sensor measures current vs. desired state, a controller picks a small incremental change, and an actuator applies it, which avoids over-steering and destabilizing the codebase (c4, c5).
  • HumanLayer's internal loop runs as a scheduled GitHub Actions workflow and refuses to open a new PR while a prior PR from the same loop is still open and unreviewed, guaranteeing at most one open PR per loop at a time (c7, c8).
01The cost of blind loop hype

The talk pushes back on the industry narrative that piping a prompt in a loop to a coding agent is how software gets built now, citing Boris Cherny (Claude Code's creator) saying his entire job is now writing loops to prompt Claude. Left unconstrained, this approach produces PRs on the order of 40,000 lines that nobody reads, and it's only affordable without an unlimited token budget if you work at a frontier lab.

“if we're doing this, we're still building 40,000 line PRs that just nobody wants to read, right?”

02Borrow from control theory: incremental change, not one big leap

The talk maps agentic loops onto a classic control-theory loop: a sensor measures the current state of the codebase against a defined set point (desired state), a controller turns the resulting error into a small control signal, and an actuator applies that incremental change. The stated benefit of incremental change over trying to reach the end state in one shot is avoiding over-steering and destabilizing the system.

“control loops change a system incrementally instead of just trying to get straight to the end state immediately all at once and risk blowing everything up”

▶ watch at 06:13
03Design around what you can measure, incrementally change, and get feedback on

The three questions used to decide whether a control loop fits a problem are: can you find something measurable, can you apply changes incrementally, and can you get feedback on the quality of each change. The controller step should stay deterministic where possible, on the reasoning that sending an agent to do deterministic code's job is avoidable even though it's technically possible.

“The key questions are, can we find something we can measure? Can we apply changes incrementally? And can we get feedback on the quality of those changes?”

▶ watch at 08:47

“I don't think you should ever send an agent to do deterministic code's job, but you certainly can”

▶ watch at 11:23
04Run loops as scheduled CI workflows

The recommended way to actually run a loop is as a GitHub Actions (or GitLab/CircleCI) workflow rather than a standalone bash loop, because CI already has access to the codebase, secrets, and scheduling/dispatch primitives. HumanLayer's internal example schedules a single sense-control-actuate iteration once a day to migrate RPC procedures to the Effect library, producing one small, low-risk PR each morning.

“my recommendation is to use GitHub actions or your GitLab or your CircleCI or whatever else you're using because it has access to your code, it has access to your secrets, and it has great dispatch and scheduling primitives”

▶ watch at 13:26
05Flow control keeps loop output reviewable

To stop unreviewed loop PRs from piling up while the team is away, each loop workflow checks for an existing open PR carrying its label before running and shuts down if one is found, since an unreviewed prior PR means no human has re-steered the loop yet. This guarantees at most one open PR per loop at a time; with roughly 150 RPC procedures to migrate, doing them strictly one at a time would take about 6 months, motivating running multiple procedures or multiple parallel workflow instances at once.

“This way we have exactly one PR at most open per loop at a time. No stacking, no duplication, hopefully no conflicts.”

▶ watch at 15:59

Commentary (ours)

(ours) The talk's central move is treating the loop's control signal itself as an engineering artifact (deterministic sensor via AST grep, a version-controlled feedback file, PR labels for workflow identity) rather than trusting an agent to self-regulate end to end, which is a meaningfully different design stance from the 'just prompt a loop' framing it's arguing against.
