Scaling GitHub for your Agents

SpeakerSam Morrow · GitHub Watchyoutu.be/0n3MKk7r60w
MCP & protocolsSecurityContext engineering

If you only read one thing

  • GitHub's MCP server started with 100+ tools that made agents 'confused and forgetful' per LangChain's prior research, and even after adding toolsets and dynamic tool selection, 'everyone used the default settings.'
  • Optimization cut initial tool-load context by about 49% and shaved over 75% of output tokens off tools like list-pull-requests, pushing tool-call success above 95%.
  • The server now handles 7-8 million tool calls a week from 126 contributors, but plaintext access tokens stored where agents can access them remain a live security risk.
01Too many tools broke agents

GitHub's MCP server launched with over 100 tools, which the speaker calls too many even at the time. LangChain had already published research earlier that year describing the same problem: more tools shoved into context make agents confused and forgetful, not better.

“we picked, I think, over 100 tools. And certainly at the time, that was just too many”

▶ watch at 02:03

“LangChain had already produced research uh they published in February that year, you know, of the exact kind of problems we were seeing”

▶ watch at 02:03
02Configuration options went unused

GitHub tried toolsets, dynamic tool selection, and an unreleased RAG-style tool search to let users limit which tools loaded. Despite these options, users overwhelmingly stuck with default settings, which the speaker calls a partial specification problem since MCP client tooling doesn't expose ways to filter by things like the read-only hint.

“Everyone used the default settings. It was really annoying because like in a way we had all these elegant solutions”

▶ watch at 03:38
03Cutting context and output tokens

By focusing tools on general use cases and grouping CRUD operations, GitHub cut the initial context load by about 49%, later reducing it further. A separate push to shrink tool outputs cut more than 75% of the tokens used by the list-pull-requests tool alone.

“we cut the amount of context used by focusing the tools more specifically to the general case. And based on usage to like about 49% reduction of the initial load”

▶ watch at 05:15

“just by tailoring exactly what comes with the list pull requests, it's like actually lost more than 75% of the tokens used in the output”

▶ watch at 05:45
04Reliability: tool call success rate

A push to reduce tool failures brought the success rate to roughly 95%, though the speaker notes not all failures are preventable since agents don't always know which repos they have write access to.

“we made a big push to reduce tool failures as well. And the success rate is roughly, I think, over 95% at this point”

▶ watch at 06:47
05Security and scale

Many users run MCP with plaintext access tokens that are stored where the agent can access them, are frequently long-lived, and are often over-privileged. Despite the risk, GitHub's remote server has scaled to roughly 7-8 million tool calls a week, with 126 contributors and over 2,300 issues/PRs on the open-source project.

“we've a lot of people using plain text access tokens for MCP in the wild. And uh usually they're stored somewhere the agent can access. They're frequently long-lived. They're often over-privileged”

▶ watch at 08:19

“we've been able to scale to this point we serve around 7 million tool calls a week”

▶ watch at 14:35

“we've got 126 contributors now and over 2,300 issues and PRs which it's been over seven a day like every single day for over a year now”

▶ watch at 18:13

“nearly 30,000 stars and uh we're fast approaching 8 million tool calls a week”
