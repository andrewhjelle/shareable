We Cut 94% of AI Coding Tokens With a Local Code Index

SpeakerRajkumar Sakthivel · Tesco Watchyoutu.be/dRmWYHuIJxM
Context engineeringCoding agentsLocal models

If you only read one thing

  • A measured query sent 45,000 tokens of context to the model, but only about 5,000 of them were actually relevant; 90% of AI coding cost is input tokens, not output.
  • A local hybrid search index (semantic + keyword search, chunked by function/class, scored and filtered) cut a FastAPI benchmark from 83K to 4.9K tokens per question, a 94% reduction, while keeping 90% answer accuracy.
  • Combining semantic and keyword search cuts the miss rate from about 1-in-4 (either search alone) to about 1-in-10 together, but recall dropped to nearly zero on a 396-file codebase where files serve multiple purposes.
01The problem: most sent context is wasted

A measured typical query on the speakers' project sent 45,000 tokens of context to the model, of which only about 5,000 tokens were actually relevant to answering it -- the other 40,000 were paid for on every query without being useful.

“We measured typical query on our project. It was sending 45,000 tokens of context, but the part of actually mattered is about 5,000 only”

02Input tokens, not output, drive cost

The talk states that 90% of AI coding cost comes from input tokens (files, search results, context sent in) versus 10% from output. Because of this ratio, cutting output by 75% (via shorter model answers) saved only about 8% of total cost, while cutting input by 94% saved about 61% of total cost -- the same underlying math producing very different results depending on which side is optimized.

“This is the most important slide. 90% of your AI cost is input. Files, search results, context you send in. Only 10% is output”

▶ watch at 02:39

“if you cut the output by 75%, you can save about eight 8% total. But, if you cut input by 94%, you can save about 61% total. Same math, but different result”

▶ watch at 02:39
03The fix: a local hybrid semantic-plus-keyword search index

The team built a local search layer that chunks code into functions/classes/methods, runs a semantic (meaning-based) search and a keyword (exact-match) search simultaneously and combines the results, compresses matches down to name plus description, tracks call relationships between functions, and scores every result so low-scoring ones are dropped before being sent to the model. Semantic search alone misses roughly 1 in 4 relevant results (it matches meaning but misses exact names), and keyword search alone misses a similar share (exact names but not related concepts); combined, the miss rate drops to about 1 in 10.

“By themselves, both searches miss about one in four results. Together, they miss about one in 10”

▶ watch at 05:14
04Results: 94% fewer tokens on a benchmark, tracked real-world savings

On an open-source FastAPI project (53 files, 20 developer-style test questions), the tool cut context from 83K tokens per question to 4.9K tokens per question, a 94% reduction, while retaining 90% answer accuracy. A separate real-project usage report over 247 queries recorded 12.4 million tokens saved (about $186 not spent), with 84% of the savings attributed to the search layer and the rest to compression.

“We tested an open-source real project, FastAPI, 53 files, 20 real questions a developer would ask. Without using our tool, 83 uh K tokens per questions. With our tools, uh 4.9 K tokens per questions. That is 94% less”

▶ watch at 06:16

“247 queries. 12.4 million tokens saved. Nearly 186 not spent. Most of the savings, 84% came from search layer”

▶ watch at 09:25
05Limits: struggles on large, multi-purpose codebases

On a larger, mixed-purpose codebase of 396 files, recall dropped almost to zero. The approach works well when files each do one thing but struggles when files do many things; the speaker also notes the 94% figure is a worst-case comparison against reading full files every time, so real savings against smarter tools like Claude Code will be lower.

“We tested on large projects with 396 files. The recall dropped almost zero. If your files each do one thing, it works well. If your files do many things, it struggles”

▶ watch at 07:49

Commentary (ours)

The 94% figure is explicitly framed by the speaker as a worst-case baseline (full-file context) rather than a like-for-like comparison against context-aware tools, so the real-world number for teams already using Claude Code's built-in file selection is probably meaningfully lower than 94% -- the 61%-vs-8% input/output framing is the more transferable takeaway (ours).
