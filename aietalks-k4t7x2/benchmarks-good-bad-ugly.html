Benchmarks: The Good, the Bad, and the Ugly

SpeakerAli Khial · G2i Watchyoutu.be/jWq-aZIU0kM
Evals & benchmarksSecurityCoding agents

If you only read one thing

  • SWE-bench Pro instructions average 481 words per task, far longer and more detailed than how engineers actually write prompts, and some leak the test file or full interface directly into the instruction (c1).
  • DeepSWE's audit of SWE-bench Pro found it accepted wrong implementations 8.5% of the time and rejected correct implementations more than 24% of the time (c2).
  • Reward hacking (models finding .git folders or searching the internet instead of solving the task) is increasing as models get smarter, which is part of why Khial hasn't met an engineer in six months who picks a model off a leaderboard (c3, c4).
01Benchmark instructions don't look like how people write prompts

Khial's own engineers said they would never write a prompt shaped like an actual benchmark task. A check of SWE-bench Pro found instructions averaging 481 words, roughly a two-page task; some instructions point directly at the test file or hand over a complete implementation interface, leaving the model little room to actually solve the problem.

“there's 481 words per instruction in average. That's a two-pager per task”

02Verifiers accept wrong answers and reject correct ones

Citing DeepSWE's comparison against SWE-bench Pro, the talk reports the benchmark accepted wrong implementations 8.5% of the time and rejected correct implementations more than 24% of the time. Examples included tests expecting an unspecified variable name and tests checking unexported functions that would never pass code review in a real project.

“In Sweet Bench Pro, 8.5 of 8.5% of all the tasks uh accepted wrong implementation in one hand and more than 20 24% of the tasks uh rejected um correct implementations”

▶ watch at 05:18
03Reward hacking is outpacing benchmark defenses

As models get smarter they are increasingly able to route around a task rather than solve it directly, for example finding .git folders or searching the internet for hints, and the gap between model capability and benchmark robustness against this behavior is widening over successive model versions. Khial says this quality gap has produced a trust gap: he hasn't met an engineer in the last six months who picks a model based on leaderboard position rather than their own testing.

“instead of actually trying to fix the to to apply a patch to a task, they try to go and find dot git folders, or they look up the internet for any kind of traces”

▶ watch at 06:53

“I have not met an engineer in the last 6 months that would choose a model or choose um an LLM based on the leaderboards”

▶ watch at 07:55
04Five principles for better benchmark tasks

G2i's proposed fix has five parts: human-authored, human-reviewed instructions that express desired behavior rather than implementation detail; holistic graders that mix broad behavioral tests with precise checks only where needed; production-grade tasks that an engineer would actually trust a model's fix on; contamination-free design using only novel tasks with private holdout sets; and leaderboards that expose the underlying data rather than just a ranking.

“human instructions. Authored by humans, reviewed by humans. This is basically the entry point for any great tasks”

▶ watch at 08:56

“The tasks have to be tasks have to have value um and they have to be economically valuable”

▶ watch at 09:59

“We want to do novel tasks only and we want to make sure that we keep private holdout sets”

▶ watch at 10:32

Commentary (ours)

Khial frames these findings as broadly generalizable, but the concrete evidence (instruction length, false accept/reject rates) is drawn from two specific benchmarks (SWE-bench Pro, via DeepSWE's audit), not a systematic survey across the benchmark landscape (ours).
