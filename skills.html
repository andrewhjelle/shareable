What teams build as agent skills, and what we replicate

Functional analysis only: we read public descriptions to understand mechanisms, wrote them up in our own words, and will replicate from these specs. Zero code copied. Sampling: Public READMEs only (VoltAgent/awesome-agent-skills full listing ~300 named entries across ~40 vendor groups; ComposioHQ/awesome-claude-skills full listing including its 70+ Composio connector skills; karanb192/awesome-claude-skills directory; claudemarketplaces.com category page and install-count top). No code cloned, no SKILL.md files read; entries used for names/URLs and public one-line descriptions only. Class descriptions and mechanisms are ours, inferred from what teams publish under each label rather than from any skill's internal text. Long-tail categories (blockchain, HR, telecom) omitted as out of scope for the target stack.

If you only read one thing
  • Research and synthesis loop (week): The whole stack (daily briefs, world model, weekly synthesis, deep dives, forecasts) is a research loop; a first-class version replaces most ad-hoc prompting.
  • Office and PDF document generation (day): Briefs, house-projects, kids' prep, and the beauty client work all end in shareable HTML or PDF; native DOCX/XLSX/PPTX unlocks handing artifacts to family and clients in their format.
  • Browser automation with real session (day): Gmail drafts, LinkedIn read, TryNectar delta pulls, and future Skylight/portal work all need a real logged-in browser; Playwright is already wired but not encoded as a skill.
  • Meta: skill and subagent scaffolding (day): The stack already lives or dies by skills (threshold-*, world-model-*, beauty-co-daily); a first-class creator plus a discovery index makes the next skill cheap and the current set searchable.
  • Data and query wrapper (local + Postgres) (week): Trading logs, world-model state, atlas nodes, and briefs corpora all want typed access rather than filesystem grep; this is the missing spine between intake and transform.

The vendor baseline, skill by skill

A skill is a directory whose SKILL.md carries YAML frontmatter plus a Markdown body. Required frontmatter is `name` (lowercase, hyphens, must match the dir name, up to 64 chars) and `description` (up to 1024 chars, should say what the skill does AND when to fire). Optional fields: `license`, `compatibility` (env requirements), `metadata` (freeform string map), `allowed-tools` (space-separated pre-approved tool list, experimental). Loading is progressive in three tiers: (1) frontmatter of every installed skill is preloaded at agent startup (~100 tokens each) so the description acts as the trigger classifier; (2) when the agent decides to activate, only that skill's full SKILL.md body is loaded (target under 500 lines, under 5000 tokens); (3) sibling files under scripts/, references/, assets/ are pulled in on demand as the body cites them. The pattern encourages putting bulky reference material, code, and templates in sibling files so activation cost stays cheap and the model only pays for what a given run needs.

behavior-shapingtrivial to replicate

discernment-nudge

Add a short 'things worth a second look' block after consequential answers so the user is invited to challenge them.

Mechanism (ours, functional)
  1. 1. Deliver the full answer with no defensive hedging in the body.
  2. 2. Classify whether the answer is actable and consequential.
  3. 3. If yes and no earlier nudge, add a blank line and a fixed lead-in.
  4. 4. List two or three concrete follow-up questions the user could paste back, each referencing a specific number or claim.
  5. 5. Stop; no wrap-up sentence after the nudge.

Design insight: Separates the answer from the challenge so the model does not weaken its own response with hedges but still hands the user a lever to push back. Mirrors Andrew's 'level me up, do not induce cognitive surrender' rule.

skill-creator

Bootstrap, evaluate, and iterate on new or existing skills, including trigger-quality optimization.

Mechanism (ours, functional)
  1. 1. Interview the user for intent and pull it into a first-draft SKILL.md with frontmatter and body.
  2. 2. Write two or three realistic test prompts into evals/evals.json.
  3. 3. Spawn parallel test runs: with the skill installed vs a baseline without.
  4. 4. Write quantitative assertions while the runs execute.
  5. 5. Aggregate results, launch an eval viewer for human review, iterate, then optionally run a description-optimization pass.
  6. 6. Package as a .skill file.

Design insight: Treats skill-writing as an ML-style loop with a real eval harness and human-in-the-loop grading, rather than a one-shot prompt draft.

Mechanism (ours, functional)
  1. 1. Create: run a Node script using the preinstalled docx npm package.
  2. 2. Edit: unzip the .docx, patch word/document.xml, rezip; use merge_runs.py first to defrag text runs so find-and-replace works.

doc-coauthoring

Walk the user through a three-stage doc-writing loop: gather context, draft and refine, then reader-test.

Mechanism (ours, functional)
