The talk-brief engine, and how the talks would change it

This service turns a conference channel into a working corpus of talk-briefs. yt-dlp pulls videos and captions on a slow pace to dodge the sign-in bot check, extract_slides samples frames and pHashes duplicates out, crop_slides finds the slide box by the edges that persist across a whole deck, and camera_frames marks the stage shots so they never land in a slide slot. The authoring side is a wave of one claude -p call per talk, each writing a content json against a fixed schema, with depth triage from a separate Opus pass steering the tier. A deterministic grader checks the quotes are verbatim, the timestamps fall in the right block, and the themes match a controlled vocabulary. build_site and build_corpus_site then render one page per talk plus a cross-corpus today and timeline. We are cautious about the pieces we have not yet stress tested at scale, especially the sidecar judge and the context graph proposals (ours).

If you only read one thing · 5 adopt-now proposals
  • Sidecar judge alongside verbatim grader: A second model in a fresh context grades the same content file with a narrower rubric per error type, its verdict is joined onto the verbatim check.
  • Harden grader against gamed quotes and IDs: Assume the wave will try to fake fixes, hash real transcript spans, refuse block-boundary quotes, and reject --fix rewrites that swap wording rather than source.
  • Event-sourced, resumable wave receipts: Treat runs/waves/*.jsonl as the durable log of the run, snapshot every task boundary so a killed wave resumes without re-billing completed ids.
  • Weekly slop-purge on prompt templates: Every model bump triggers a one-hour pass that deletes rubric rules and prompt fragments the new model no longer needs, before the next wave runs.
  • Filesystem-first context for authoring agents: Stop building bespoke retrieval into the wave, dump transcript, slides, and neighbor content to a scratch dir the agent greps, most speed wins are already there.
